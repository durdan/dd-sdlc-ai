Publish/subscribe

Publish each message once to a topic; a broker gives every interested subscriber its own copy, so new listeners never change the sender.

1 · The problem

What goes wrong without it, shown happening.

When a service tells others about an event by calling them directly, it must know every receiver: its address, its API and how it fails. Each new receiver means a change to the sender and a redeploy. Microsoft's pattern page describes exactly this: the sender "must know the identity and endpoint of every consumer, deliver messages to each consumer, and manage failures individually."

2 · The naive fix

The obvious approach and why it breaks.

The obvious fix is a loop over the receivers. Now the caller waits for the slowest one, and a failure half-way leaves some receivers told and others not: retrying the loop sends duplicates to the ones that already succeeded, skipping it loses the event for the rest. Moving the loop to a background thread hides the wait but keeps the coupling. Giving each consumer its own queue and having the sender write to all of them, as Microsoft notes, "increases routing complexity and doesn't scale well."

3 · The pattern

Its parts and the role of each.

A publisher sends a message to a topic (an input channel). Each interested consumer has a subscription (an output channel), and the broker copies every message into every subscription. In Google Cloud Pub/Sub's words, a subscription "represents an interest in receiving messages on a particular topic", and "each subscription receives a copy" of the topic's messages.

PartJob
PublisherSends each message once; does not know who listens
TopicNamed feed of messages; the input channel
SubscriptionOne per consumer; behaves like that consumer's own queue; may carry a filter
SubscriberReceives from its subscription and acknowledges when the work is done
Dead-letter topicHolds messages that repeatedly fail, for inspection

Filtering lets a subscription receive only part of a topic. Google Cloud Pub/Sub filters on message attributes, not the data, and automatically acknowledges messages that do not match; a subscription's filter cannot be changed after creation. Amazon SNS filter policies act on message attributes or on a JSON body; with no filter policy, a subscriber receives every message.

4 · How it works

The normal flow, step by step.

The publisher's job ends when the broker acknowledges the publish. Delivery is either pull, where the subscriber asks the broker for messages when it has capacity, or push, where the broker calls the subscriber. Google Cloud Pub/Sub pushes each message as an HTTPS POST; a 102, 200, 201, 202 or 204 response acknowledges it, and any other status is a negative acknowledgement, after which delivery backs off exponentially (100 ms to 60 s). A subscriber has a configurable ack deadline; an unacknowledged message keeps being delivered until its retention expires. Amazon SNS delivers by push to SQS, Lambda, HTTP(S), email, SMS, mobile push and Firehose.

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

Duplicates. Google Cloud Pub/Sub offers at-least-once delivery by default (exactly-once is also available), so "a message might be delivered more than once". Acknowledge only after the work is done, and make subscribers idempotent, for example by recording processed message ids.

Poison messages. A dead-letter topic on a Pub/Sub subscription receives messages after a maximum number of delivery attempts (default 5, between 5 and 100; approximate). Amazon SNS attaches an SQS dead-letter queue to a subscription; without one, messages that fail after retries are discarded.

Ordering. Pub/Sub gives no ordering guarantee by default. With message ordering enabled on the subscription and an ordering key on the messages, messages sharing a key are delivered in order; a redelivery triggers redelivery of all later messages for that key, even acknowledged ones, and order may not be preserved into a dead-letter topic.

Slow consumers. For live updates to many clients, one slow connection must not hold up the rest. A gateway can buffer up to a limit, drop messages or disconnect clients that stay behind, or coalesce to the latest value when only the current state matters (for example a position on a map). Microsoft's guidance also recommends broker flow-control limits on unacknowledged messages per subscriber.

6 · Trade-offs

What it costs, when not to use it, and its main variants.

The main variant is durability. Managed brokers such as Google Cloud Pub/Sub, or SNS fanning out to SQS queues, retain or retry messages so a subscriber that was down catches up, at the cost of duplicates and more moving parts. Redis Pub/Sub and core NATS are at-most-once: only subscribers connected at the moment of publishing receive a message, and nothing is stored. Microsoft lists when the pattern may not suit: only a few consumers needing very different data; near real-time interaction or a synchronous reply (use request-reply); strict guaranteed ordering; or a single atomic transaction across publisher and consumers (use a local transaction or a saga).

Durable broker or fire-and-forget?

Durable (Cloud Pub/Sub, SNS to SQS)Fire-and-forget (Redis Pub/Sub, core NATS)
Holds messages for subscribers that are downOnly subscribers connected now receive it

More moving parts and latencyFast and simple

When not to use it

  • A few consumers that each need very different data
  • The caller needs an answer now: use request-reply
  • Everything must be processed in one guaranteed order
  • Publisher and consumers must commit in one transaction

7 · In the wild

Real implementations and where our own systems use it.

Microsoft's Azure Architecture Center documents the Publisher-Subscriber pattern. Google Cloud Pub/Sub provides pull, push and export subscriptions, filters, ordering keys and dead-letter topics. Amazon SNS sends messages from publishers to topics and on to subscribers; its documented fanout scenario subscribes several SQS queues to one topic so each receives identical notifications to process at its own pace. Redis Pub/Sub is at-most-once, with Redis Streams recommended for stronger guarantees; it also supports glob-style pattern subscriptions and, from Redis 7.0, sharded pub/sub. Core NATS is at-most-once fire-and-forget, with JetStream as its persistence layer.

8 · Related patterns

What it is confused with or combined with.

A pub/sub topic gives every subscription a copy. A log (event streaming) keeps events for replay with order per partition key. A queue shares work so each message is handled by one worker; each pub/sub subscription is effectively a queue for its consumer. The transactional outbox publishes reliably alongside a database write, idempotent consumers absorb at-least-once duplicates, and backpressure deals with consumers that cannot keep up.

9 · Recap

Three takeaways.

Publish once; the broker copies to every subscription. Expect duplicates and disorder, and make subscribers idempotent. Plan for slow and broken consumers with dead letters, limits and coalescing.

Recap

  • Publish once; the broker copies to every subscription
  • Expect duplicates and disorder: idempotent subscribers
  • Plan for slow and broken: dead letters, limits, coalescing
