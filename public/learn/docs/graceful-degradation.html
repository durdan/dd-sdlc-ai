Graceful degradation

When an optional part of a request fails, serve a reduced but working answer instead of an error, and keep that reduced path simple, monitored and tested.

1 · The problem

What goes wrong without it, shown happening.

A product page is built from several services: product details, price and stock, reviews and recommendations. If the page waits for all of them and fails when any one fails, the least important service decides the availability of the whole page. A slow recommendations service turns into an error page, although everything a shopper needs to buy the product was working.

2 · The naive fix

The obvious approach and why it breaks.

Raising the timeout and retrying makes the failure slower, not rarer, and the retries add load to a service that is already struggling. The real mistake is treating every dependency as required, so the response is all or nothing.

3 · The pattern

Its parts and the role of each.

Classify each feature as critical (the request fails without it) or optional (the request can succeed without it). AWS Well-Architected calls this transforming hard dependencies into soft ones, and notes that it is as much a business discussion as a technical one. Each optional call then gets a time budget and a fallback.

PartJob
ClassificationWhich features are critical, which are optional
GuardA short time budget per optional call
FallbackLast-known-good data, a sensible default, or hide the feature
Feature switchLets operators turn an optional feature off by hand
Metrics and alertsCount every degraded response so degradation is never silent

Coarser options follow the same idea: a read-only mode when writes are unavailable, and a static page served from a CDN as a last resort.

4 · How it works

The normal flow, step by step.

The page fetches the critical data in parallel. It gives the recommendations call a small budget (200 ms in the example). When nothing arrives in time it abandons the call, takes the last good list from a cache, records a degraded response, and returns a normal page that labels the content honestly ("popular right now" rather than "picked for you"). 5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

Overload. Google's SRE book describes load shedding: as a server approaches overload it drops a proportion of traffic, for example by returning HTTP 503, and drops low-priority work such as background synchronisation while keeping interactive sessions. Graceful degradation goes further by reducing the work done per request; switching optional features off under load is sometimes called a brownout.

Fallbacks that spread the failure. Amazon's Builders' Library describes a fallback from a cache to direct database queries that worked for months, until the caches failed together and the database locked up. A fallback must not shift far more load onto a shared system.

Untested and silent paths. The SRE book warns that the code path you never use often does not work, recommends monitoring and alerting when too many servers enter degraded mode, keeping the mode simple, and having a way to turn it off quickly. Chaos experiments and game days exercise these paths on purpose.

Where it still goes wrong

  • Silent degradation: nobody notices for weeks
  • A fallback path never exercised, broken when needed
  • Degraded mode trips when it is not needed
  • Test it: game days and chaos experiments

6 · Trade-offs

What it costs, when not to use it, and its main variants.

Stale data is better than nothing only when it cannot mislead; never present an old price as current. Automatic triggers react quickly but can trip when they should not; manual switches are slower. Amazon's Builders' Library prefers making the primary path more resilient, or turning fallback into failover by running both paths continuously so neither goes untested. Some functions should not degrade at all: AWS notes that for payment processing, consistency may matter more than availability.

The choices

ChoiceTrade-off
Stale data or hide itSomething useful, but possibly wrong
Automatic or manual switchFast reaction, or fewer false trips
Fallback or failoverRarely used path, or one exercised all the time
Degrade or failSome features must be correct or nothing

7 · In the wild

Real implementations and where our own systems use it.

Google's SRE book covers load shedding and graceful degradation in "Addressing Cascading Failures". AWS Well-Architected makes it best practice REL05-BP01, and links to the Builders' Library article "Avoiding fallback in distributed systems" as a caution. Pete Hodgson's feature toggles article describes kill switches that let operators gracefully degrade non-vital functionality, such as an expensive recommendations panel under heavy load. Netflix's Chaos Monkey randomly terminates instances in production so that services are built to tolerate failure.

In the wild

  • AWS Well-Architected REL05-BP01: hard into soft dependencies

8 · Related patterns

What it is confused with or combined with.

Timeouts decide when to give up on an optional call. A circuit breaker skips calls to a failing dependency and goes straight to the fallback. Bulkheads keep optional calls from consuming the resources the critical path needs. CDN caching supplies static and stale pages. Feature flags are the manual switch. Load shedding applies the same thinking to your own overloaded servers.

9 · Recap

Three takeaways.

Decide what is critical. Give everything else a budget and a simple fallback that cannot overload anything. Alert on degradation, and rehearse it on purpose.

Recap

  • Decide what is critical; everything else is optional
  • Give optional features a budget and a simple fallback
  • Alert on degradation, and rehearse it on purpose
