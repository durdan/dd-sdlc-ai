WhatsApp messaging

A relay, not an archive: billions of people's messages pass through servers that cannot read them and do not keep them once delivered.

1 · Overview

What it is, who uses it, and the one idea everything depends on.

WhatsApp is a messaging app that, by its own account, more than three billion people in over 180 countries use. The idea everything depends on is that the server is a relay. It moves end-to-end encrypted messages, holds each one only until the recipient's device collects it, and then deletes it. Message history lives on the user's devices.

This case study combines WhatsApp's own publications (website, blog, privacy policy, encryption whitepaper, engineering posts) with two conference talks from 2012 and 2014 by WhatsApp engineer Rick Reed. Talk-based details are dated and marked as such. Where we fill gaps with our own design, we say so.

2 · Requirements and scale

What users need, the quality targets, and back-of-envelope numbers.

The quality targets are ours, written from the product: exactly-once, in-order delivery to people who are often offline; visible delivery state; privacy from everyone including the operator; good behaviour on cheap phones and poor networks; and every linked device receiving every message.

The detailed numbers are from March 2014, the last time WhatsApp published server-level figures. They are dated, but the ratio that matters still holds: connections, not messages, decide how many chat servers you need.

Scale, from WhatsApp's own statements

3B+people use WhatsApp, in 180+ countries (whatsapp.com, 2026)
2B+users, February 2020
465Mmonthly users, March 2014 talk
19B in · 40B outmessages a day, March 2014 talk
147Mconcurrent connections, March 2014 talk
~1Mphones per chat server, March 2014 talk

What the system must do (our wording)

  • Deliver every message exactly once, in order, even if the recipient is offline for days
  • Show the sender what happened: sent, delivered, read
  • Nobody but the two ends can read a message, including WhatsApp
  • Work on cheap phones and poor networks: small frames, fast reconnects
  • Every linked device gets every message, even with the phone switched off
  • Photos and videos as fast as text, without the server seeing them

Back of the envelope (our arithmetic)

~220K/smessages in, average (19B ÷ 86,400 s, 2014)
342K/speak messages in, per the 2014 talk
~2×out vs in: groups and receipts fan out
~150chat servers for 147M connections at ~1M each (2014)

3 · Context

Who and what the system talks to (C4 level 1).

Every user is both sender and receiver. Outside WhatsApp, the system depends on the phone platforms' push services to wake apps that the operating system has suspended, and on mobile networks to verify phone numbers at registration. WhatsApp does not publish its providers; those boxes are illustrative.

4 · Containers

The deployable parts and 3–5 paths through them (C4 level 2).

WhatsApp has never published a container diagram. Ours is reconstructed from the encryption whitepaper (Noise Pipes transport, key distribution, client fan-out, server fan-out for groups, media blob store, app-state sync), the multi-device post, the privacy policy (offline queue), and the 2014 talk (chat, offline storage, push, group, account and media services).

PathWhat happens
ConnectOne long-lived connection per device, encrypted with Noise Pipes (Curve25519, AES-GCM, SHA-256). The server stores only each client's public authentication key.
SendThe sender encrypts one copy per recipient device and per own device (client fan-out). Groups use sender keys: one ciphertext, fanned out by the server.
OfflineUndelivered messages are kept encrypted for up to 30 days, deleted on delivery.
MediaEncrypted with a fresh AES-256 key, uploaded to a blob store; the message carries key, MAC key, hash and pointer.
Multi-deviceEach device has its own identity key; app state is synced through an encrypted server-side copy.

5 · Deep dive

Inside the most interesting component (C4 level 3).

The components inside a chat server come from the 2012 and 2014 Erlang Factory talks: one Erlang process per connection, routing between nodes via pg2 process groups with single-hop delivery, services split into partitions with work assigned by key, Mnesia tables fragmented so each record lives on one node and accessed mostly with async_dirty, an offline store with a write-back cache and variable sync delay, and monitoring that treats message-queue backlog as the sign of a bottleneck (alerts usually above 500k). How the boxes connect is our reconstruction. The 2012 talk took a server from about 200k connections to 2 million, almost entirely by removing contention, mostly through BEAM patches.

6 · Core flows

Two or three requests that matter, step by step.

Offline friend. The tick meanings are WhatsApp's product behaviour: one grey tick when the server has the message, two grey when it reaches the recipient's device, two blue when read. The server deletes its copy once delivered. Message ids that make resends safe are our design assumption; WhatsApp has not documented its wire protocol.

First message. The whitepaper describes X3DH as used by WhatsApp: the initiator fetches identity key, signed prekey and one one-time prekey for each device, which the server then deletes; computes ECDH(IA,SB) ‖ ECDH(EA,IB) ‖ ECDH(EA,SB) ‖ ECDH(EA,OB); and derives root and chain keys with HKDF. It can send immediately, even if the recipient is offline. Each message key is derived from a hash ratchet, and each round trip adds a Diffie-Hellman ratchet, giving forward secrecy.

7 · Data and caching

What is stored where, for how long, and what is never stored.

On the server: account and device records with linking signatures, public keys, undelivered ciphertext (up to 30 days), encrypted media (forwarded media is kept temporarily to speed up later forwards), and an encrypted app-state copy shared by a user's devices. Never on the server: plaintext messages, private keys, or chat history after delivery. A newly linked device receives an encrypted history bundle from the phone; the key arrives end-to-end encrypted and is deleted after import.

8 · Growth

How the same design grows from launch to its current scale.

The 2014 talk is a snapshot of a small team running a large system: about 550 servers, roughly 150 chat servers with about a million phones each, and a team described as “small (~10 on Erlang)” handling both development and operations. Facebook announced its agreement to acquire WhatsApp on 19 February 2014, citing over 450 million monthly users. End-to-end encryption by default followed in April 2016, two billion users in February 2020, multi-device in July 2021.

9 · Failure modes

What breaks, what users see, and what protects them.

Offline recipients are the normal case, not a failure. The 2014 talk names its stress sources plainly: world events (especially football), server failures (usually RAM), network failures and bad software pushes. It also describes the 22 February 2014 outage: a back-end router glitch led to mass node disconnects and reconnects, a novel unstable state, and the first full stop and restart in years. Stale device lists are handled by Sender Side Backfill: the server compares a hash of the sender's device list with its own records and the sender re-encrypts for missed devices within a short window.

What fails, and what users see

FailureWhat protects them
Recipient offline for daysStore and forward, 30-day queue, push to wake (published)

10 · Patterns used

The named patterns, each linked to its pattern walkthrough.

Sharding (partitioned services, fragmented tables), backpressure (write-back cache absorbing overload, backlog alerts, push rather than polling), retries made safe by idempotency (our design: client-chosen message ids), and timeouts on every call (the 2014 talk: “make calls w/ timeouts only”). Store and forward is the core messaging pattern throughout.

Patterns used

  • Store and forward: queue ciphertext until the device collects it
  • Sharding: partitioned services and Mnesia fragments, one node per record
  • Backpressure: write-back cache, queue-length alerts, push instead of polling
  • Retry with idempotency: client message ids make resends safe (see Retry and Idempotency)
  • Timeouts on every call, as the 2014 talk recommends (see Timeout)

11 · Key decisions

The choices that shaped it, with the alternatives and trade-offs.

Erlang on FreeBSD suited millions of lightweight, mostly idle connections, at the price of patching the runtime. Making the server a relay limited what could leak but moved history and backups to the client. Encryption by default ruled out server-side reading of content. Per-device sessions in multi-device avoided sharing a key across devices at the cost of the sender encrypting N copies. Sender keys keep group sends to a single upload, but every member clears its sender key and starts again when someone leaves.

Key decisions

DecisionWhy, and what it cost
Erlang on FreeBSDCheap processes, SMP scaling, non-stop running; but runtime patches were needed
Server as relay, not archiveLess to store and to leak; history and backup become the client's problem
End-to-end by default (2016)Nobody can read messages in transit; server-side search and moderation become impossible
Client fan-out per device (2021)No shared device key; the sender does N encryptions per message
Server fan-out for groupsOne upload per message via sender keys; everyone re-keys when a member leaves

12 · What we would build first

An MVP cut and our recommendations.

Our recommendation, not WhatsApp's: a WebSocket per device, Postgres for accounts, devices and public prekeys, a per-device queue for undelivered messages that is deleted on the delivery receipt, client-chosen message ids, libsignal for X3DH and the Double Ratchet, and encrypted media in object storage. Add groups with sender keys and multi-device once one-to-one messaging is solid.

We left out the widely repeated claim that WhatsApp's wire protocol is a modified XMPP (“FunXMPP”): it comes from reverse engineering and community discussion, not from WhatsApp.

What we would build first (our recommendation)

  • One connection per device: WebSocket over TLS, one lightweight process or task each
  • Postgres for accounts, devices and public prekeys
  • A per-device queue for undelivered messages, deleted on delivery receipt
  • Client-chosen message ids; receipts for sent, delivered and read
  • libsignal for X3DH and the Double Ratchet: never roll your own crypto
  • Media to object storage as encrypted blobs; groups and multi-device later
