Cursor pagination

Page through a large, changing list by remembering exactly where the last page stopped, instead of counting how many rows to skip.

1 · The problem

What goes wrong without it, shown happening.

The usual first design is LIMIT 20 OFFSET 10000: page number times page size. It has two problems. It gets slower with depth, because the database cannot jump to row 10,000; the PostgreSQL manual notes that rows skipped by OFFSET still have to be computed inside the server, so a large offset might be inefficient. And it is wrong when the list changes: an insert above the client's position pushes a row it has already seen onto the next page (a duplicate), and a delete pulls a row it has not seen back onto a page it has already read (a skip).

2 · The naive fix

The obvious approach and why it breaks.

Remembering the last value of the sort column (say created_at) and asking for rows strictly older fixes speed and drift, but timestamps are not unique. If a page boundary falls inside a group of rows with the same timestamp, < skips the rest of the group and <= repeats the rows already shown. PostgreSQL's own advice applies: LIMIT needs an ORDER BY that constrains the rows into a unique order.

3 · The pattern

Its parts and the role of each.

Keyset (seek) pagination sorts by the wanted column plus a unique tie-breaker, and continues from the last row's values: WHERE (created_at, id) < ($last_created_at, $last_id) ORDER BY created_at DESC, id DESC LIMIT 21. PostgreSQL compares row constructors left to right, stopping at the first unequal pair, which is exactly the tie-break you need. With an index on (created_at, id) the database seeks straight to the position, so page 500 costs the same as page 1.

PartJob
Cursor codecEncodes the position (and optionally sort, filters, a version or snapshot id), signs it, and decodes it on the way back
Query builderTurns the position into a seek predicate with a unique tie-breaker
IndexMatches the sort exactly, so the seek reads only the rows returned
Page shaperCaps the page size, fetches one extra row to set has_more, builds next and previous cursors

The cursor is opaque: clients pass it back unchanged and must not parse it. The Relay connections spec says the cursor “should be considered opaque by the client”. That leaves the server free to change the encoding, the index or the sort.

4 · How it works

The normal flow, step by step.

Fetch limit + 1 rows; if the extra row exists there is a next page. Return the page, has_more, a next cursor from the last row and a previous cursor from the first. To go backwards, flip the comparison and the sort, fetch, and reverse the rows. Stripe exposes this pair as starting_after and ending_before, each taking an object id; they are mutually exclusive. The numbers in the sequence (20 per page, 12 rows on the last page) are illustrative.

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

Sharded data. An offset has no global meaning across shards. A keyset does: send the same seek to every shard, take limit rows from each, merge, keep the top limit, and build the next cursor from the last row kept. Ranked or personalised feeds. Scores change between requests, so seeking on a score drifts. Put the ranking seed or a snapshot id plus a position in the cursor, and keep the ranked list for a short time, so later pages continue the same ranking. (This is a general design approach, shown illustratively.)

Other edge cases: an index that does not match the sort makes every page a full sort; a missing tie-breaker skips or repeats rows; a stale, edited or mismatched cursor should get a clear error (Slack returns invalid_cursor and documents that cursors expire); and a null in a PostgreSQL row comparison makes the result null, so keep sort columns non-null or handle nulls explicitly.

Where it still goes wrong

  • Sort column not in the index: every page is a full sort again
  • No unique tie-breaker: rows skipped or repeated
  • Old, tampered or mismatched cursor: reject it clearly
  • Nullable sort column: row comparison returns null

6 · Trade-offs

What it costs, when not to use it, and its main variants.

Cursors give stable cost per page and correct results under writes. They give up random access (“jump to page 57”) and cheap totals: a count over a large table is a separate, often expensive query, which is why APIs such as Stripe's list endpoints return has_more rather than a total. Stripe's search API offers an optional total_count that is only accurate up to 10,000. Offset remains fine for small or rarely changing lists, admin screens that need page numbers, and searches where people rarely go deep.

7 · In the wild

Real implementations and where our own systems use it.

Stripe list methods take limit (1 to 100, default 10), starting_after and ending_before (object ids, reverse chronological order) and return has_more. Slack's Web API takes cursor and limit and returns response_metadata.next_cursor; an empty, null or missing next_cursor means the end; Slack recommends 100 to 200 results per call, with a maximum of 1,000 that may vary by method. GitHub's REST API returns a link header with next, prev, first and last relations; endpoints page with page, before/after or since, and per_page is at most 100 for most endpoints. GitHub's GraphQL API uses first/last (1 to 100) with after/before and pageInfo.endCursor/hasNextPage, following the Relay Cursor Connections spec (edges with node and cursor; PageInfo with hasPreviousPage, hasNextPage, startCursor, endCursor).

8 · Related patterns

What it is confused with or combined with.

Sharding makes offsets meaningless and keysets essential. Cache-aside suits the first page, which most readers only ever see. An API gateway is a natural place to enforce page size limits. For a client that pages through everything to keep a copy in sync, a change feed or change data capture is usually a better fit than repeated full scans.

9 · Recap

Three takeaways.

Offsets count rows: slow when deep, wrong when rows move. Seek past the last row using the sort key plus a unique id, backed by an index. Hand out an opaque cursor with has_more and a capped page size.

Recap

  • Offsets count rows: slow when deep, wrong when rows move
  • Seek past the last row: sort key plus unique id, with an index
  • Hand out an opaque cursor, with has_more and a page size cap
