API gateway

Give every client one front door that routes, combines and protects requests, so services stay private and simple.

1 · The problem

What goes wrong without it, shown happening.

When clients call services directly, every client has to know every endpoint, and one screen can need several round trips. On a high-latency mobile network that is slow and fragile. Every public service also has to terminate TLS, check tokens and limit greedy callers itself, and every one of them is an endpoint someone can probe. Microsoft's guidance lists the costs: complex client code, tight coupling between clients and the way the back end is split, extra latency, the same cross-cutting work repeated in each service, protocol limits, and a larger attack surface.

2 · The naive fix

The obvious approach and why it breaks.

A shared library for authentication, throttling and logging looks like a fix, but it copies the same code into every service, and the copies drift apart as services upgrade at different times. Clients still make one call per service, and every service is still public. Changing a certificate or a token format still means changing every service.

3 · The pattern

Its parts and the role of each.

An API gateway is a single entry point for all clients: a reverse proxy that sends each request to the right service, or fans it out to several and combines the results. It also takes on cross-cutting work so services do not have to. Microsoft names three gateway patterns that describe these jobs.

PartJob
TLS terminationOne public certificate and host name; re-encrypt to the services
AuthenticationValidate the caller's token once, and pass a trusted identity on
Rate limiterA budget per caller, rejected with 429 before any service does work
RouterLayer 7 routing by path, host or header (Gateway Routing)
AggregatorOne client call, several back-end calls, one reply (Gateway Aggregation)
TelemetryLogs, metrics and correlation ids for every request

Moving TLS, authentication, throttling, logging and compression into the gateway is what Microsoft calls Gateway Offloading.

4 · How it works

The normal flow, step by step.

A product page needs the item, its reviews and the stock level. The client sends one HTTPS request with a token. The gateway checks the token's signature with keys it has cached from the identity provider, checks the caller's budget, then calls the three services in parallel and merges their answers into one compressed response, logging it with a trace id. The services only see trusted, decrypted requests on a private network.

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

Aggregation means one slow service can hold up the whole reply. Microsoft's aggregation guidance suggests timeouts, returning a partial set of data when that is acceptable, cached data as a fallback, and bulkheads, circuit breakers and retries. Greedy clients are turned away with 429 Too Many Requests, which may carry a Retry-After header (RFC 6585).

The bigger risk is the gateway itself: it is on every request's path, so it can become a single point of failure and a bottleneck. Run several instances behind a health-checked load balancer, size them for peak rather than average load, drain connections on restart, and keep shared state such as rate-limit counters outside the instances. Make services accept traffic only through the gateway, so nobody can bypass its checks, and never put business logic in it.

6 · Trade-offs

What it costs, when not to use it, and its main variants.

Every request takes an extra network hop, and each offloaded check adds some processing time. The gateway is another moving part to develop, deploy and manage, and because it centralises TLS and authentication, it is a high-value target. Microsoft notes that gateway routing may not be worth it for a simple application with one or two services, and that offloading fits badly when the gateway must hold service-specific logic that couples every back-end release to a gateway change.

The main variant is one gateway per kind of client. microservices.io calls this the Backends for Frontends variation; Sam Newman describes a general-purpose API backend as a possible bottleneck for delivery, and recommends one BFF per user experience, owned by the team that builds that interface.

One gateway or one per client

One gatewayPer-client gateways (BFF)

What it costs, and when to skip it

  • An extra network hop on every request
  • Another critical system to deploy, scale and secure
  • Skip it for one or two services
  • Coupled releases if it knows service internals

7 · In the wild

Real implementations and where our own systems use it.

microservices.io (Chris Richardson) describes the pattern and lists the Netflix API gateway as a known use. Microsoft's Azure Architecture Center splits it into Gateway Routing, Aggregation and Offloading, and lists NGINX and HAProxy as reverse-proxy options, mesh ingress gateways, Azure Application Gateway, Front Door and API Management. Amazon API Gateway is a managed service for REST, HTTP and WebSocket APIs that AWS says can accept and process up to hundreds of thousands of concurrent API calls. Kong Gateway is an Apache-2.0 open-source gateway extended through plugins. Envoy is an L7 proxy well suited to edge use, and Envoy Gateway runs it as a standalone or Kubernetes-based API gateway implementing the Kubernetes Gateway API. Netflix describes Zuul as the front door for all requests from devices and websites to its streaming back end; the open-source repository is still active, with 4.x releases.

8 · Related patterns

What it is confused with or combined with.

Backends for frontends is a gateway per client experience. Rate limiting is usually enforced at the gateway, where callers are identified. Timeouts and circuit breakers protect aggregation from slow services. A service mesh handles east-west traffic between services; the gateway handles north-south traffic coming in, and a mesh's own ingress gateway can play that role, usually with fewer API-management features.

9 · Recap

Three takeaways.

One front door, so clients see one API and not your topology. Route, aggregate and offload, but keep business logic out. It is on every path, so run several instances and allow no bypass.

Recap

  • One front door: clients see one API, not your topology
  • Route, aggregate, offload; keep business logic out
  • It is on every path: run several, and allow no bypass
