Idempotency keys

Make retries safe: the client labels each operation with a unique key, and the server does the work once per key and replays the same answer to every repeat.

1 · The problem

What goes wrong without it, shown happening.

A caller sends a request, the server does the work, and the response is lost: a dropped connection, or a timeout that fires just too early. The caller cannot tell whether the work happened. If it gives up, a payment may silently have gone through; if it retries, the server sees what looks like a brand new request and does the work again. For a payment, that is a double charge.

Some requests are safe to repeat. RFC 9110 calls a method idempotent when “the intended effect on the server of multiple identical requests with that method is the same as the effect for a single such request”, and names PUT, DELETE and the safe methods (GET, HEAD, OPTIONS, TRACE) as idempotent. POST is not, and the RFC says a client SHOULD NOT automatically retry a non-idempotent request unless it has some means to know the request is in fact idempotent.

Which requests are safe to repeat?

MethodSent twice
GET, HEADSafe: nothing changes
PUTIdempotent: same final state
DELETEIdempotent: gone either way
POSTNot idempotent: may create a second charge

2 · The naive fix

The obvious approach and why it breaks.

The obvious fix is to check for a similar recent operation before doing the work, for example the same amount for the same customer in the last minute. It fails twice over. A slow first attempt and its retry can run concurrently, both find nothing and both proceed: check-then-act is a race unless something enforces uniqueness. And the heuristic is a guess, so a customer who genuinely buys two identical items is blocked. Not retrying at all is no better: the caller is left not knowing whether it happened.

3 · The pattern

Its parts and the role of each.

The client, which knows which attempts belong to the same operation, generates a unique key per operation and sends it on every attempt, typically in an Idempotency-Key header. The server records the key with the outcome and replays that outcome to repeats.

PartJob
Client keyOne random value (e.g. a UUID v4) per operation, reused on every retry
Idempotency layerLooks up the key: claims it the first time, replays or rejects a repeat
Key storeKey, request fingerprint, status (started or completed), saved response, expiry
FingerprintA checksum of the request payload, to catch a key reused for a different request
HandlerDoes the real work, and passes a key on to downstream calls

The key, the side effect and the saved response must be committed atomically. AWS's Builders' Library describes recording the request identifier and the resource changes as an “all or nothing” operation, so a crash can never leave a key without its effect or an effect without its key.

4 · How it works

The normal flow, step by step.

The first request inserts the key and fingerprint with status started; a unique constraint means only one request can win. The handler does the work and, in the same transaction, stores the response and marks the key completed. A retry with the same key and the same body finds the completed record and gets the saved status code and body back, with no new side effect. Stripe flags these replays with an Idempotent-Replayed: true response header. AWS describes the goal as a “semantically equivalent response” for the same request identifier: the meaning is the same even if other state has moved on.

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

Concurrent duplicates. If a retry arrives while the first attempt is still running, there is nothing to replay yet and the work must not start again. The IETF draft says the server SHOULD reply 409 Conflict; Stripe documents 409 for a request that conflicts with another using the same key, and tells clients to wait and retry with the same key, because a new key can start a second operation.

Mismatched payloads. The same key with a different body is a client bug, not a retry. Stripe compares incoming parameters with the original and errors if they differ; the draft suggests 422 Unprocessable Content. AWS describes returning a validation error for a parameter mismatch.

Expiry. Keys are not kept for ever. Stripe (API v1) keeps keys for at least 24 hours and may then prune them; a key reused after pruning runs as a new request. So retries should stop inside the window and the client should reconcile instead. The draft leaves the policy to each server but says it should be published.

Errors. Stripe saves the result once endpoint execution begins, including 500 errors, so a retry with the same key gets the same 500. Requests that fail validation or conflict with a concurrent request are not saved and can be retried.

Other traps. Clients that make a new key per retry defeat the scheme. Downstream calls must be idempotent too, so pass a key along. The draft warns that low-entropy keys can leak other clients' cached responses, and suggests scoping the key with something only the server knows, such as the account.

Where it still goes wrong

  • The key is saved, but not in the same transaction as the side effect
  • The client makes a new key on every retry
  • A downstream call is not idempotent, so the key must travel with it
  • Keys are global, so one client can collide with another's

6 · Trade-offs

What it costs, when not to use it, and its main variants.

The cost is a write per operation, storage for the expiry window, and the discipline of committing the key with the side effect. Choices: a random UUID or a key derived from a user-facing object such as a cart id (Stripe suggests both; the latter also stops double submits); a key store in the same database as the side effect, which makes atomicity easy, or a faster separate store, which can lose keys; a longer or shorter window. GET, PUT and DELETE that are naturally idempotent do not need a key: Stripe says sending one with GET or DELETE has no effect.

The same idea applies to messaging. Most brokers deliver at least once; Amazon SQS standard queues can occasionally deliver a message more than once, and AWS tells you to design applications to be idempotent. An idempotent consumer records each processed message id in a table with a unique key, in the same transaction as its business update, and skips a message whose id is already there.

The choices

ChoiceTrade-off
Random or derived keyUUID is simple; a cart id also stops double submits
Key storeSame database gives atomicity; a cache is faster but can lose keys
Expiry windowLonger is safer; costs storage

7 · In the wild

Real implementations and where our own systems use it.

RFC 9110 (June 2022) defines idempotent HTTP methods. The IETF HTTPAPI working group's draft, “The Idempotency-Key HTTP Header Field”, aimed to make POST and PATCH fault-tolerant; its last revision (-07, October 2025) has since expired without becoming an RFC. It lists Stripe's Idempotency-Key and PayPal's PayPal-Request-Id among existing implementations. Stripe accepts idempotency keys on all API v1 POST requests, up to 255 characters, and its SDKs can generate keys and retry automatically. AWS APIs use a caller-provided client request token, such as EC2's ClientToken. Chris Richardson's microservices.io catalogue documents the idempotent consumer pattern for messaging.

8 · Related patterns

What it is confused with or combined with.

Retry is why this pattern exists: retries are only safe for idempotent operations. The transactional outbox publishes events at least once (a relay that crashes after publishing but before marking the event sent will publish it again), so its consumers must be idempotent. Saga steps and compensations are retried after failures, so each needs a key too.

9 · Recap

Three takeaways.

A lost response makes a retry look like a new request. Give each operation one client-made key, sent on every attempt. Store the key, fingerprint and result atomically with the side effect, and replay the result to every repeat.

Recap

  • A lost response makes retries look like new requests
  • The client sends one key per operation, on every attempt
  • Save the key, fingerprint and result with the side effect, atomically
