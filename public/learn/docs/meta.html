Meta: serving the social graph

How a social network serves a billion reads a second: TAO's objects and edges, followers and leaders, a full copy of the graph per region, memcache leases, and caches invalidated from the database's own log.

1 · Overview

What it is, who uses it, and the one idea everything depends on.

Meta runs Facebook, Instagram, WhatsApp, Messenger and Threads. This case study looks at one part: how Facebook serves the social graph, the people, posts, photos, comments and likes (nodes) and the links between them (edges).

Pages are not precomputed. Each view is assembled from hundreds of small pieces of the graph, each filtered by privacy rules for the person looking. The idea everything depends on: reads vastly outnumber writes, so reading the graph must be cheap. In the 2013 TAO paper, 99.8% of requests were reads.

2 · Requirements and scale

What users need, the quality targets, and back-of-envelope numbers.

Scale, from Meta's own publications. Meta's second-quarter 2026 results (29 July 2026) report 3.60 billion daily active people (DAP) across its family of apps, on average for June 2026, up 3% year on year. The TAO paper (USENIX ATC 2013) says TAO could process a billion reads and millions of writes a second over many petabytes, that 99.8% of requests were reads, and that rendering one page commonly queried hundreds of objects and associations. The memcache paper (NSDI 2013) describes billions of requests a second over trillions of items.

Back of the envelope: at roughly a thousand reads for every write, a cache that answers 96% of reads (TAO's 2013 hit rate) still misses tens of millions of reads a second (1 billion × 3.6%), which is why leaders, leases and per-region copies matter. Our arithmetic.

The functional requirements in the video are ours: reads from memory in milliseconds; read-your-own-writes; others may briefly see stale data but never lose a write; survive the loss of a server, cluster or region; and change behaviour safely many times a day.

3 · Context

Who and what the system talks to (C4 level 1).

People use the apps from phones and browsers. They find Meta through DNS, and the internet routes to Meta's addresses using routes Meta announces over BGP; Meta's edge facilities run the DNS servers and connect its backbone to the internet. Advertisers create and measure campaigns. Third-party developers use the Graph API, which Meta describes as nodes, edges and fields.

5 · Deep dive

Inside the most interesting component (C4 level 3).

Inside TAO, from the 2013 paper.

  • Data model. Objects: a 64-bit id → (type, key-value data). Associations: (id1, type, id2) → (32-bit time, key-value data); at most one association of a type between two objects. Association lists are kept newest first. Queries are a fixed set: obj_get, assoc_get, assoc_range, assoc_time_range, assoc_count, plus adds and deletes.
  • Sharding. Each object id embeds its shard id; an association lives on the shard of id1, so any association query is served by one server. Shards far outnumber servers. Each shard is a logical MySQL database with an objects table and an associations table.
  • Followers and leaders. Clients talk only to a nearby follower tier, which caches objects, association lists and counts (LRU). Misses and writes go to the leader tier, where one leader hosts each shard and is the only cache server that talks to MySQL. That serialises writes and protects the database from thundering herds. Leaders send invalidations (objects) and refills (association lists) to followers asynchronously.
  • Regions. The graph cannot be partitioned so that cross-partition requests are rare, so each region keeps a complete copy. Per shard, one region is the master. Reads are served in-region; writes are forwarded from the local leader to the master region's leader and written synchronously to the master database. Invalidations ride in the MySQL replication stream, so a replica region's caches change only after its database has the data. The master is switched automatically if a database fails.
  • Hit rate and latency (2013). 96.4% of reads were hits; median hit latency about 1 ms, misses about 5–8 ms at the median.

6 · Core flows

Two or three requests that matter, step by step.

Read: the 50 newest comments on a post. The paper's own example is assoc_range(632, COMMENT, 0, 50). The follower answers from memory; for commenters whose objects are missing, it forwards to its leader, which queries the region's MySQL replica and fills the cache on the way back.

Write: a comment from a replica region. assoc_add goes to the follower, its leader, then the master region's leader, which writes to the master database synchronously. In the paper's measurement the two data centres were 58.1 ms apart; average write latency was 12.1 ms in the master region and 74.4 ms from the remote one. The follower that took the write is updated synchronously, so the author sees the comment at once. Other followers are refilled when the change replicates; replicas lagged under 1 second 85% of the time, under 3 seconds 99%, under 10 seconds 99.8%. An edge with an inverse touches two shards with no atomicity; an asynchronous job repairs hanging associations.

7 · Data and caching

What is stored where, for how long, and what is never stored.

Memcache (NSDI 2013) is a demand-filled look-aside cache: read memcached, on a miss query MySQL and set the value; on a write, update MySQL and delete the key. Gets go over UDP directly to memcached; sets and deletes go over TCP through mcrouter. Leases are 64-bit tokens issued on a miss, at most once every 10 seconds per key; they stop stale sets and thundering herds (one measured peak fell from 17K to 1.3K database queries a second). Web and memcached servers are split into frontend clusters that share a storage cluster in a region. mcsqueal daemons read the MySQL commit log and broadcast batched deletes through mcrouter to every frontend cluster. In non-master regions, remote markers send reads for recently written keys to the master region.

Per Meta's engineering posts: a command issued during routine maintenance to assess global backbone capacity unintentionally took down all backbone connections; a bug in the audit tool failed to stop it. 10 · Patterns used

The named patterns, each linked to its pattern walkthrough.

  • Cache-aside: memcache's demand-filled look-aside design.
  • Read replicas: a full copy of the graph per region; writes go to the shard's master.
  • Sharding: the shard id is embedded in every object id.
  • Change data capture: mcsqueal and Wormhole turn MySQL logs into cache invalidations.
  • Consistent hashing: keys across memcached servers; shards across TAO cache servers.
  • Feature flags: Gatekeeper rollouts.
  • CDN caching: popular photos served from a CDN.

12 · What we would build first

An MVP cut and our recommendations.

Our recommendations for a small social product, not Meta's:

  • Two Postgres tables, objects and edges, indexed by (source, type, time).
  • A graph API with a handful of fixed queries; no ad-hoc SQL from product code.
  • A cache in front, invalidated from the database's change log, not from application code.
  • Leases or request coalescing so one miss does not become a thousand database queries.
  • Shard bits in every id from day one, even with one shard.
  • Feature flags and staged config rollout with automatic rollback.

What we would build first

  • Two tables: objects and edges, indexed by (source, type, time)
  • A graph API with a few fixed queries, no ad-hoc SQL
  • A cache in front, invalidated from the database's change log
  • Leases or request coalescing on cache misses
  • Shard bits in every id from day one
  • Feature flags and staged config rollout
