Dropbox: keeping files in sync

How a saved file reaches every device: 4 MB blocks named by their SHA-256 hash, a metadata journal read from cursors, long-poll nudges that carry no data, Dropbox's own block store, and a sync engine rewritten in Rust.

1 · Overview

What it is, who uses it, and the one idea everything depends on.

Dropbox keeps a folder of files the same on every device a person uses and on the devices of everyone they share it with: the desktop app, mobile apps, the web, and third-party apps through the Dropbox API.

Everything depends on one idea: a file is stored as a list of blocks of up to 4 MB, each named by the SHA-256 hash of its contents (the “blocklist”). Because a block's name is its content, a device only ever needs to send or fetch the blocks the other side lacks, re-sending a block is harmless, and file contents can be stored apart from the metadata that describes them.

2 · Requirements and scale

What users need, the quality targets, and back-of-envelope numbers.

Scale, from Dropbox's own publications. The second-quarter 2026 results (6 August 2026) report 18.19 million paying users, average revenue per paying user of $139.68, and, in the company description, more than 700 million registered users across about 180 countries. In March 2020 Dropbox's engineers wrote that it holds hundreds of billions of files, trillions of file revisions and exabytes of customer data, on hundreds of millions of devices.

Back of the envelope (ours): hundreds of billions of files across 700 million registered accounts is a few hundred files per account on average, most rarely touched; a 200 MB video is fifty 4 MB blocks, and a small edit at the start of it typically changes one or two of them.

The functional requirements in the video are ours, written from the product: never lose a file; changes reach other devices within seconds; send only what changed; work offline and merge safely; one consistent view of shared folders; keep old versions.

The original title, “syncing a billion files”, was dropped: the only dated official figure is “hundreds of billions of files” (2020), so “a billion” would have understated the scale by two orders of magnitude.

3 · Context

Who and what the system talks to (C4 level 1).

Two kinds of user: a person with several devices, and the collaborators who share folders and links with them. Third-party apps reach the same files through the public API.

Amazon Web Services is drawn as a neighbour because it used to hold file contents: Dropbox calls itself an early adopter of Amazon S3, and moved user data to its own Magic Pocket storage in 2015. In March 2016 it wrote that Amazon remained a partner, for example for storing data in Germany for European business customers. How much still lives on AWS today is not published.

5 · Deep dive

Inside the most interesting component (C4 level 3).

Inside the desktop sync engine. In March 2020 Dropbox wrote that it had rebuilt the engine from scratch over four years, in Rust, under the codename Nucleus, and shipped it to all users. The old engine, Sync Engine Classic, had “fundamental issues with its data model that only showed up at scale”; files, for example, had no stable identifier across moves. In Nucleus, shared folders and files have globally unique identifiers.

  • Three trees (April 2020): the Remote Tree is the latest state in the cloud; the Local Tree is the last observed state on disk; the Synced Tree is the last state where both agreed, and acts like a merge base that tells which side changed.
  • Planner: decides which operations move the three trees towards convergence.
  • Concurrency: almost all code runs on a single control thread, using Rust futures; network I/O goes to an event loop, file-system I/O to a dedicated thread, and hashing to a thread pool. The control thread is deterministic for given inputs and scheduling, which is what makes seeded random testing possible.

6 · Core flows

Two or three requests that matter, step by step.

Saving a file. The client splits the file into 4 MB blocks (the last may be smaller), hashes each with SHA-256, and commits the path and blocklist to the metadata server. The server checks whether it knows the hashes and the user has access; if not, it returns “need blocks” naming the missing ones (for a brand-new file, often all of them). The client uploads them with PutBlock, sending each block with its hash so the server can confirm nothing was corrupted, then commits again; this time the commit succeeds and a new journal entry is written. That uploading a block twice is harmless, because its name is its hash, is our observation rather than Dropbox's wording.

Reaching other devices. Idle clients hold a long-poll connection to the notification server. When something changes, it tells them; they call list with a cursor for each namespace, so only new entries come back, then fetch the blocks they lack. With streaming sync (2014), a downloading client prefetches blocks of files that are not yet committed; Dropbox reported up to 2× faster multi-client sync in theory and about 25% in its two-machine test. The client writes the file and updates its trees.

Later posts add compression on the wire: Broccoli (August 2020), a modified Brotli encoder, saved about 30% of upload bandwidth and about 15% on downloads.

What is stored where, for how long, and what is never stored.

DataWhereNotes

Inside Magic Pocket (May 2016): frontends accept puts and gets; on a put they check the Block Index to see whether the block exists, choose a volume, find its storage nodes (OSDs) in the Replication Table, and write the block, which the OSDs flush to disk before answering; only then is the Block Index entry added. Each cell holds about 50 PB raw. Every block is stored in at least two zones (western, central and eastern US); cross-zone replication aims for a remote copy within a second. New blocks are first replicated on several machines, then buckets are aggregated and erasure-coded by the Volume Manager. A Master per cell triggers repairs once an OSD has been offline for 15 minutes. The 2019 cold-storage post describes a cross-region 2+1 scheme that cuts disk usage by 25% for rarely read data.

Edgestore originally grew by splitting each MySQL machine in two, each keeping half its shards, which doubled the fleet each time. By 2019 Dropbox judged that too costly, and also feared an outlier shard outgrowing a single machine. Panda splits the key space into ranges, moves ranges between storage nodes, and offers global ACID transactions with two-phase commit and multi-version concurrency control. Dropbox evaluated FoundationDB (tuned for up to 500 storage processes; Edgestore and Filesystem each run on more than 10,000 cores) and Vitess (no production-ready cross-shard ACID transactions) and rejected both.

Testing detail (April 2020): CanopyCheck generates random trees, runs the planner and checks invariants such as termination (a 200-iteration cutoff), shrinking any failure to a minimal case. Trinity tests the whole engine with mocked file system, network and timers, injecting failures, reordering responses and simulating crashes; its in-memory file system allows about ten times more runs than the native one.

10 · Patterns used

The named patterns, each linked to its pattern walkthrough.

  • Sharding: the Block Index, file metadata and Edgestore all run on sharded MySQL.
  • Two-phase commit: Panda's global transactions across storage nodes.
  • Cache-aside: Edgestore's caching layer, invalidated on writes for strong consistency.
  • Idempotency: content addressing makes re-uploading a block harmless (our framing).
  • Strangler fig: the move from S3 to Magic Pocket, from dark launch to 90% in-house, a piece at a time (our framing).

12 · What we would build first

An MVP cut and our recommendations.

Our recommendations for a small sync service, not Dropbox's:

  • Content-addressed blocks (SHA-256, up to 4 MB) in an ordinary object store such as S3; no custom storage until the bill demands it.
  • One Postgres database for namespaces, an append-only journal per namespace, and per-client cursors.
  • The commit → need blocks → upload → commit protocol, with the hash checked on every upload.
  • Long-poll or WebSocket nudges that carry no data; clients list from their cursor.
  • On the client: three trees (remote, local, synced) and a deterministic core.
  • Seeded random tests from the first week, so every failure can be replayed.

What we would build first

  • Files as blocks named by SHA-256 hash, in an object store
  • One Postgres database: namespaces, journals, cursors
  • Commit, need blocks, upload, commit again
  • Long-poll or WebSocket nudges; clients list from a cursor
  • Three trees on the client, and a deterministic core
  • Randomised tests with seeds from the first week
