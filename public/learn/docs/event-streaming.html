Event streaming

Producers append each event once to a durable, partitioned log; every consumer reads it at its own offset, at its own pace, and can replay.

1 · The problem

What goes wrong without it, shown happening.

When one service calls every interested service directly, it has to know all of them. Each new consumer means a code change and a deploy in the producer, and with synchronous calls the slowest consumer sets the latency for everyone. Jay Kreps describes LinkedIn heading towards O(N²) point-to-point pipelines between systems before it built a central log instead.

2 · The naive fix

The obvious approach and why it breaks.

A queue per consumer removes the waiting, but not the coupling: the producer still fans out a copy per team. A classic queue also deletes a message once it has been consumed and acknowledged (SQS once the consumer deletes it; a RabbitMQ classic queue once acked), so a team that arrives later cannot read the history.

3 · The pattern

Its parts and the role of each.

A topic is a durable, replicated, append-only log split into partitions. Producers append; the broker assigns each record the next offset in its partition. Events with the same key go to the same partition, and any consumer of a partition reads its events in exactly the order they were written. There is no global order across partitions.

Committed offsetThe group's position: one number per partition, stored in Kafka

4 · How it works

The normal flow, step by step.

The idempotent producer gets a producer id and sends a sequence number with every message, so the broker can discard a retried duplicate. With acks=all, the leader acknowledges once all current in-sync replicas have the record. A consumer fetches from its offset, processes, then commits the next offset. Retention defaults to seven days (retention.ms); a new group starts at the latest offset unless auto.offset.reset=earliest. Offsets such as 1207 in the walkthrough are illustrative.

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

Rebalancing. If a consumer stops polling for longer than max.poll.interval.ms (default five minutes) it is considered failed and its partitions are reassigned. The new owner restarts at the last committed offset, so work done after that commit is redelivered: at-least-once. Kafka 4.0 made the incremental next-generation rebalance protocol (KIP-848) generally available.

Delivery semantics, precisely. Kafka's design docs say it guarantees at-least-once by default; at-most-once is possible by disabling producer retries and committing before processing. Exactly-once is supported in Kafka Streams, and the transactional producer plus read_committed consumers give exactly-once when reading, processing and writing Kafka topics. Exactly-once to other systems generally requires cooperation from those systems.

Poison messages. Because a partition is consumed in order, a record that always fails stops progress on that partition. Route it, after bounded retries, to a dead-letter topic with error context, and commit past it. Kafka Connect supports this with errors.deadletterqueue.topic.name; in plain consumers you build it yourself (illustrative design).

6 · Trade-offs

What it costs, when not to use it, and its main variants.

Pick a log when several independent consumers need the same events, per-key order matters, or replay is valuable. Pick a queue (SQS, a RabbitMQ queue) for a pool of workers sharing jobs, with per-message acknowledgement, retry and dead-letter queues. The boundary is blurring: RabbitMQ streams are append-only logs with non-destructive reads; Pulsar subscriptions can be exclusive, failover, shared or key_shared; Kafka's share groups allow more consumers than partitions with per-record acknowledgement.

Costs: operating a cluster or paying for a managed one; eventual consistency for every reader; partition count caps a group's parallelism, and adding partitions changes which partition a key maps to; and event schemas become a public contract. Confluent Schema Registry checks compatibility per subject; its default is BACKWARD, under which consumers should be upgraded before producers.

Log or queue?

Log (Kafka, Kinesis)Queue (SQS, RabbitMQ queue)
Many independent readersWork shared out, one reader per message
Kept after reading; replayDeleted once acknowledged
Order per partition or shardOrder only with FIFO or groups
Parallelism capped by partitionsAdd consumers freely
One bad record blocks a partitionPer-message retry and DLQ

What it costs

  • A cluster to run, or a managed service to pay for
  • Eventual consistency: readers are always a little behind
  • Choose keys and partition counts up front
  • Schemas become a contract: use a registry

7 · In the wild

Real implementations and where our own systems use it.

Jay Kreps' essay The Log (LinkedIn Engineering, 16 December 2013) defines a log as an append-only, totally ordered sequence of records ordered by time, and reports over 60 billion unique message writes a day through Kafka at LinkedIn at the time. Amazon Kinesis Data Streams divides a stream into shards selected by an MD5 hash of the partition key; a shard takes up to 1 MB/s or 1,000 records/s of writes, and retention is 24 hours by default, up to 365 days. Apache Pulsar uses stateless brokers with Apache BookKeeper for storage, and supports dead-letter topics on shared and key_shared subscriptions. Redpanda is a C++ platform compatible with the Kafka API, using Raft.

8 · Related patterns

What it is confused with or combined with.

The transactional outbox publishes to the log without a dual write. Idempotent consumers absorb at-least-once duplicates. Event sourcing makes the log the system of record; CQRS builds read models from it and can rebuild them by replay. Pull-based consumption gives natural backpressure, with consumer lag as the signal.

9 · Recap

Three takeaways.

Append once, read many times at independent offsets. Key by entity for per-key order. Expect at-least-once: idempotent consumers and a dead-letter topic.

Recap

  • Append once; every consumer reads at its own offset
  • Key by entity: order per partition, not per topic
  • At least once by default: make consumers idempotent
