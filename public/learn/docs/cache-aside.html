Cache-aside

Read the cache first, load from the database on a miss and store it with a time to live, and on every write update the database and then delete the key.

1 · The problem

What goes wrong without it, shown happening.

Many reads are expensive and repeated: the same product page, profile or configuration is built from the same query thousands of times a second. The database does identical work for identical answers, its CPU saturates, and every other query on it slows down. Most of that load is redundant.

2 · The naive fix

The obvious approach and why it breaks.

The obvious fix is a cache that keeps values forever and is updated on every write. Concurrent writes make this fragile: two writers can commit to the database in one order and update the cache in the other, leaving the cache wrong. With no expiry, nothing ever corrects it. Updating the cache from every write path also caches data nobody reads.

3 · The pattern

Its parts and the role of each.

In cache-aside (also called lazy loading) the cache sits beside the data store and the application manages it. Microsoft describes it as emulating read-through caching for caches that do not provide it.

PartJob
Read pathTry the cache; on a miss, read the data store, add the item to the cache with an expiry, return it
Write pathWrite the data store first, then invalidate (delete) the cached item
CacheRedis, Memcached or an in-process map; holds copies and may evict them
Data storeThe source of truth; the cache is never authoritative
TTLBounds how long any copy can be wrong

4 · How it works

The normal flow, step by step.

On a hit the application gets the value from the cache. On a miss, AWS counts three trips: the cache request, the database query, and writing the result to the cache. Microsoft's example sets a five-minute expiry; AWS's pseudocode uses 300 seconds. On a write, the order matters: update the data store before removing the cached item, otherwise another reader can miss, load the old row and put it back. Facebook deletes rather than updates cached data because deletes are idempotent.

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

Stale sets. A slow reader can read an old row, a writer can update and delete in the meantime, and the reader then stores the old value. A TTL bounds the damage. Facebook's leases fix it: on a miss memcached issues a 64-bit token bound to the key, a delete invalidates it, and a set with an invalid token is refused.

Stampedes. When a hot key expires or is repeatedly invalidated, many requests miss together and all query the database. Fixes: coalesce rebuilds within a process (Go's singleflight) or across servers (a short lock such as Redis SET key value NX EX seconds, or Facebook's leases, issued once every 10 seconds per key by default, with other clients told to wait briefly); serve a stale copy while one request revalidates (Facebook returns recently deleted values marked stale; HTTP's stale-while-revalidate does the same for responses); add random jitter to TTLs so keys do not expire together; or recompute early with a probability that rises near expiry (XFetch). On keys prone to thundering herds, Facebook measured peak database query rates of 17K/s without leases and 1.3K/s with them.

Cache failure. Lazy loading survives losing a cache node, with higher latency while the new node fills. But a database sized for the miss rate can be overwhelmed when every read falls through: use short timeouts on cache calls, cap concurrent fallback queries, and shed load. Facebook sends requests for a failed server to a small Gutter pool (about 1% of servers) with short-lived entries, rather than rehashing keys onto the remaining servers, because a single hot key (up to 20% of a server's requests) could overload whichever server inherits it.

When the cache itself struggles

  • Cache down: every read hits the database at once
  • Fall back carefully: timeouts, concurrency limits, shed load
  • Facebook's Gutter: a small spare pool takes a failed server's keys
  • Hot keys: one key can overload one cache node; replicate or keep a local copy

6 · Trade-offs

What it costs, when not to use it, and its main variants.

Cache-aside caches only what is requested and tolerates cache loss, at the cost of a miss penalty and possible staleness. Write-through updates the cache on every write, so it is never stale, but every write costs two trips, a new node is empty until data is rewritten, and much of what is cached is never read; AWS recommends combining either strategy with a TTL. Read-through and write-behind move the logic into the cache provider. Negative caching (storing "this does not exist" for a short time, as DNS does) stops repeated misses for absent keys. Microsoft advises against the pattern for sensitive or security data, for workloads where most requests miss, for small static data sets (prime the cache instead), and for session state in a web farm.

Cache-aside and its alternatives

StrategyTrade-off
Cache-asideOnly requested data cached; miss penalty; can be stale
Read-throughSame loading, but the cache library or service does it
Write-throughFresh after writes; writes slower; caches data never read
Write-behindFast writes; data lost if the cache dies first

What to cache, and what not to

  • Cache read-heavy data that changes rarely and tolerates staleness
  • Cache 'not found' briefly too, or misses keep hitting the database
  • Not sensitive or security data, especially in a shared cache
  • Not data where most reads would miss anyway

7 · In the wild

Real implementations and where our own systems use it.

Microsoft's Cache-Aside pattern page uses Azure Managed Redis with a five-minute expiry and an update-then-delete write path. AWS's ElastiCache strategies page contrasts lazy loading with write-through and adds TTLs. Redis supports expiries on SET (EX, PX) and eviction policies such as allkeys-lru and allkeys-lfu. Memcached describes itself as a distributed memory object caching system for alleviating database load. Facebook's NSDI 2013 paper uses memcache as a demand-filled look-aside cache serving billions of requests per second. Vattani, Chierichetti and Lowenstein's VLDB 2015 paper, “Optimal Probabilistic Cache Stampede Prevention”, introduces XFetch.

8 · Related patterns

What it is confused with or combined with.

CDN caching applies the same idea at the edge to whole HTTP responses. CQRS builds a dedicated read model rather than caching on demand. Consistent hashing places keys on cache nodes so that adding or removing a node moves only some keys. Timeouts stop a slow cache from slowing every request.

9 · Recap

Three takeaways.

Load on demand with a TTL. Update the database, then delete the key. Protect the database: coalesce rebuilds, jitter expiry, and limit the fallback when the cache is down.

Recap

  • Read the cache; on a miss, load from the database and set a TTL
  • On write, update the database, then delete the key
  • Protect the database: coalesce rebuilds, jitter expiry, limit fallback
