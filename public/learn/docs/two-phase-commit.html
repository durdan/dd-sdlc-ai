Two-phase commit

Make one change commit atomically in several databases: every participant prepares and votes, then a coordinator tells all of them to commit or all of them to abort.

1 · The problem

What goes wrong without it, shown happening.

Some changes touch two databases that each run their own transactions: debit an account in one, credit an account in the other. Each database can make its own half atomic, but nothing makes the pair atomic. If the first commits and the second fails, or the process crashes between them, the system is left half done: each database is consistent on its own, and the two together are wrong.

2 · The naive fix

The obvious approach and why it breaks.

Committing one database and then the other, carefully ordered, only moves the gap. Once the first commit has happened it cannot be rolled back, so a failure in the second leaves only a compensating transaction, which can itself fail. Neither database knows the other is involved, so neither can wait for it.

3 · The pattern

Its parts and the role of each.

Two-phase commit adds a coordinator (the transaction manager) in front of the participants (resource managers, usually databases). Participants make their changes durable before committing, and the coordinator makes the single commit-or-abort decision and logs it.

PartJob
CoordinatorSends prepare, collects votes, decides commit or abort, sends the decision

ParticipantDoes the work, then on prepare writes it to stable storage, keeps its locks and votes

Transaction idNames the global transaction and its branches so any session can finish it

4 · How it works

The normal flow, step by step.

Phase 1, prepare. The coordinator asks each participant to get ready to commit. Each records its changes in stable storage, keeps its locks, and votes yes or no. A yes is a promise that it can commit whatever happens to it next. Phase 2, decide. If every participant voted yes, the coordinator logs commit and tells everyone to commit; if any voted no (or timed out), it tells everyone to roll back. MySQL's XA documentation describes exactly these two phases. In PostgreSQL the commands are PREPARE TRANSACTION, COMMIT PREPARED and ROLLBACK PREPARED; after PREPARE TRANSACTION the transaction's state is fully stored on disk and it is no longer tied to the session.

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

The weak point is the window after a participant votes yes. It may no longer abort on its own, and it cannot commit until it hears the decision. If the coordinator fails then, participants are in doubt and block, holding their locks; Gray and Lamport's paper opens with this: the classic protocol blocks if the coordinator fails. Recovery is from logs: the restarted coordinator re-sends any logged decision, and with no logged decision it can safely abort, since no participant can have been told to commit. Prepared state is durable at the participants too, so a database restart does not lose it; PostgreSQL can list in-doubt transactions in pg_prepared_xacts, and MySQL in XA RECOVER. Decisions may be re-delivered, so applying commit or abort must be idempotent.

A prepared transaction that is never finished is an operational hazard. PostgreSQL warns that leaving transactions prepared for a long time interferes with VACUUM and in extreme cases can force a shutdown to prevent transaction ID wraparound.

6 · Trade-offs

What it costs, when not to use it, and its main variants.

The cost is latency and lock time. Gray and Lamport count four message delays before participants learn the outcome in the normal case, and three stable-storage writes (two if all participants prepare concurrently). Locks are held from prepare until the decision arrives, so the slowest participant sets the pace, and any one participant or the coordinator can stall the transaction.

Mitigations. Three-phase commit, attributed to Dale Skeen, adds a pre-commit state so participants can finish without the coordinator, but it assumes bounded network delays and response times, which real networks do not guarantee. The robust fix is consensus: Gray and Lamport's Paxos Commit (2006) uses 2F+1 coordinators and makes progress while F+1 are working, at the cost of one extra message delay and the same stable-storage writes; two-phase commit is Paxos Commit with F = 0. Spanner runs two-phase commit between Paxos groups, storing each transaction manager's state in its replicated Paxos group, which its authors say mitigates the availability problems.

When not to use it. Across independently owned microservices, two-phase commit means every service must support prepare and hold locks on behalf of others. microservices.io lists “2PC is not an option” as a force behind the saga pattern; sagas and the transactional outbox give up atomic isolation to avoid global locks.

7 · In the wild

Real implementations and where our own systems use it.

The X/Open XA specification standardises the interface between a transaction manager and resource managers; MySQL's XA support (InnoDB) is based on it, and PostgreSQL follows its model without implementing some less-used parts. PostgreSQL's documentation is blunt: PREPARE TRANSACTION is not intended for applications; unless you are writing a transaction manager you probably should not use it, and max_prepared_transactions defaults to zero, which disables the feature. Google's Spanner paper (OSDI 2012) argues that it is better to let programmers deal with the cost of transactions than to code around their absence, and reports that two-phase commit scales reasonably to about 50 participants, with latency rising noticeably at 100.

8 · Related patterns

What it is confused with or combined with.

A saga is the usual alternative between services: local commits plus compensations, no cross-service locks, no isolation. The outbox makes a database write and a message atomic with one local transaction, removing a common reason to reach for XA. Leader election and consensus are what let a replicated coordinator take over safely. Distributed locks give exclusive access, not atomic commit. The protocol relies on a write-ahead log for durable votes and decisions, and on timeouts to turn a silent participant into an abort.

9 · Recap

Three takeaways.

Prepare and vote, then all commit or all abort. Log every vote and decision so crashes can be recovered. A lost coordinator blocks everyone, so replicate it with consensus or keep transactions short and local.

Recap

  • Prepare and vote, then all commit or all abort
  • Log every vote and decision so crashes can be recovered
  • A lost coordinator blocks everyone: replicate it with consensus
