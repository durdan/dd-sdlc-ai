Figma: real-time collaboration

1 · Overview

What it is, who uses it, and the one idea everything depends on.

Figma is a design tool that runs in the browser (and a desktop app). Its defining feature is multiplayer: many people editing the same file at the same time, each seeing the others' changes within moments. Designers work there alongside developers, product managers, researchers and writers.

Everything depends on one modest idea: a central server holds each open file and is the authority on every property's value. That lets Figma avoid operational transforms and settle conflicts with one simple rule, last writer wins, applied in one place.

2 · Requirements and scale

What users need, the quality targets, and back-of-envelope numbers.

Scale, from Figma's own filings and posts:

  • More than 13 million monthly active users in the three months ended 31 March 2025, two-thirds of them non-designers (S-1, 2025). Figma counts the peak month in a quarter.
  • 95% of the Fortune 500 and 78% of the Forbes Global 2000 used Figma in March 2025 (S-1).
  • Revenue of $1.056 billion in 2025, up 41% (results published 18 February 2026; 10-K).
  • The multiplayer journal took in more than 2.2 billion changes a day, and 95% of edits were saved within about 600 ms (October 2022).

Back of the envelope: 2.2 billion ÷ 86,400 seconds ≈ 25,000 changes a second on average, in 2022; today's figure is not published.

The functional requirements in the video are ours, written from the product: your own edit appears instantly; everyone converges on the same document; crashes and deploys lose no work; editing continues through a flaky connection; one huge file cannot slow others; and non-canvas data such as comments stays live.

3 · Context

Who and what the system talks to (C4 level 1).

Collaborators sign in (organisations can use SAML single sign-on through their own identity provider), open a file, and keep a WebSocket open to Figma's servers; changes flow both ways over it. Plugins and REST API clients read and change files. Figma's annual report says the platform is hosted on Amazon Web Services; the engineering posts name Postgres on Amazon RDS, S3 and DynamoDB.

5 · Deep dive

Inside the most interesting component (C4 level 3).

Inside a multiplayer session. Each piece is documented; the wiring shown is our reconstruction.

  • A process per file (May 2018). The multiplayer server was single-threaded TypeScript, so one slow operation, such as encoding a very large file, stalled every file on that worker. Figma kept a Node.js host for WebSockets and HTTP, and moved the performance-sensitive part to Rust: one child process per document, talking over stdin and stdout. Serialisation became more than 10× faster.
  • The document model (October 2019). A tree of objects, like the DOM, best pictured as Map<ObjectID, Map<Property, Value>>. Different properties never conflict; on the same property the server keeps the last value it received. New object IDs include a client ID, so objects can be created offline. Child order uses fractional indexing: a position between 0 and 1, stored with the parent link as one property. The server rejects parent changes that would form a cycle. Deleted objects are not kept on the server; the deleting client's undo buffer holds them.
  • Durability (October 2022). Before the journal, multiplayer checkpointed every 30–60 seconds (encode, compress, upload to S3), so a crash could lose up to a minute. Now each change gets a rising sequence number; batches with start and end sequence numbers are written asynchronously to a DynamoDB journal, safe because of last writer wins. A lock table ensures one writer per file; writes are conditional on the lock and reads are strongly consistent. Before rollout Figma rebuilt checkpoints from prior checkpoints plus journal entries and compared them byte for byte, about 400,000 times in a row.

6 · Core flows

Two or three requests that matter, step by step.

Two people change the same property. Clients apply their own changes immediately. When the server's broadcast of someone else's value arrives for a property the client has an unacknowledged change to, the client discards it to avoid flicker. When its own change is acknowledged, later broadcasts apply normally. Everyone converges on the last value the server received. The same rule applies to text: simultaneous edits to one text value do not merge (Figma's example: "B" edited to "AB" and "BC" ends as one or the other, never "ABC").

Reconnect after a crash or deploy. A new process loads the latest S3 checkpoint, which records its sequence number, and replays journal entries after it. The client, as for any reconnect, downloads a fresh copy, reapplies its unsent edits and resumes over a new WebSocket. During deploys, waiting for unsaved changes to reach the journal takes under one second at p99. Taking the lock first is our ordering.

Postgres. In 2020 Figma ran most metadata on one large RDS database (upgraded r5.12xlarge → r5.24xlarge, CPU above 65% at peak), with traffic growing about 3× a year. It added read replicas and PgBouncer, then vertically partitioned by table group using logical replication; each move cost about 30 seconds of partial availability (~2% of requests), and by the end of 2022 there were about a dozen databases. When single tables reached several terabytes and billions of rows, it sharded horizontally on RDS Postgres (first table in September 2023, after about nine months): tables sharing a shard key (UserID, FileID or OrgID) form a colo, keys are hashed, and DBProxy (Go: parser, logical and physical planners) routes or scatter-gathers queries. Logical sharding through Postgres views came before the physical split; the first failover caused ten seconds of partial availability on primaries. No atomic cross-shard transactions.

LiveGraph. Subscribes to the Postgres replication stream (originally distributed via Kafka), breaks each view into simple subqueries, and updates them within milliseconds; in 2021 each instance processed the full stream, about 10,000 writes a second.

10 · Patterns used

The named patterns, each linked to its pattern walkthrough.

  • Write-ahead log: the multiplayer journal, replayed on top of the last checkpoint.
  • Sharding: Postgres colos behind DBProxy.
  • Read replicas: added early to spread read load.
  • Change data capture: LiveGraph tails Postgres's write-ahead log.
  • Last-writer-wins registers: CRDT-inspired, but settled by a central server.
  • Fractional indexing: ordering children without renumbering.

12 · What we would build first

An MVP cut and our recommendations.

Our recommendations for a small collaborative editor, not Figma's:

  • One WebSocket server process per open document, with clients routed by file ID (for example by consistent hashing).
  • The document as object → property → value, last writer wins per property, validated by the server.
  • Client-prefixed object IDs and fractional indexes, so clients never wait for the server.
  • An append-only change log with sequence numbers, plus periodic snapshots to object storage.
  • Postgres for metadata, on one database until it hurts; then partition.
  • Text as a plain property first; a text CRDT only if co-typing matters.

What we would build first

  • One WebSocket server process per open document, routed by file ID
  • Document as object → property → value; last writer wins per property

  • An append-only change log with sequence numbers, plus snapshots in object storage
