Backend for frontend

Give each user experience its own thin backend, owned by the team that builds the client, instead of bending one general-purpose API to suit everyone.

1 · The problem

What goes wrong without it, shown happening.

One general-purpose API serving web, mobile and TV clients becomes a compromise. It is shaped around resources rather than screens, so a mobile screen needs many round trips over a slow network and downloads full objects when it shows a fraction of the fields. Worse, every client team queues behind one API team and one deployable: Microsoft's guidance describes competing demands, conflicting updates, and changes requested by one frontend that must be validated with the others.

2 · The naive fix

The obvious approach and why it breaks.

The obvious fix is to add client-specific options to the shared API: query flags, slim variants, embedded resources. Each one must be tested against every client and released together, so the API team becomes the bottleneck, and the API accumulates flags and versions that are hard to remove. Calçado's SoundCloud write-up lists the same pains with a generic public API: many fine-grained calls for one profile page, and changes that needed coordination to avoid breaking clients.

3 · The pattern

Its parts and the role of each.

A backend for frontend (BFF) is a server-side component dedicated to one user experience. It aggregates calls to downstream services and shapes the response for that client's screens. It is owned by the team that builds the client, so the client and its API change together.

PartJob
Client appAsks for what a screen needs, in one call where possible
Edge gatewayShared cross-cutting concerns: TLS, authentication, rate limits, routing to the right BFF
BFFFans out to downstream services, combines and trims the results, decides what is essential
Downstream servicesOwn the domain and its business rules; shared by every BFF

One BFF per experience, not per platform: Newman quotes Stewart Gleadow's guideline “one experience, one BFF”, and notes SoundCloud's iOS and Android listener apps used the same BFF.

4 · How it works

The normal flow, step by step.

The client asks for a screen. The BFF calls the downstream services it needs, in parallel where the calls are independent, keeps only the fields the screen uses, adapts things such as image sizes, and returns one response. The numbers in the sequence (six calls, forty fields, eight used) are illustrative.

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

A BFF that fans out to several services must decide, per call, what happens when that call fails or is slow. Newman's example: if only the inventory service is down, degrade the response (drop the stock indicator) rather than fail it, and make sure the client can render a partial response. Essential data, such as a price, still produces an error. Give each downstream call its own timeout, and remember the BFF is itself an extra network hop (Microsoft) that needs timeouts, circuit breakers and monitoring.

6 · Trade-offs

What it costs, when not to use it, and its main variants.

The main cost is duplication across BFFs; Microsoft calls it a probable outcome. Newman is relaxed about duplication and more wary of the coupling shared code brings; his options are a shared library, a new downstream service for the shared concept, or pushing aggregation further down, and he suggests abstracting on the third occurrence. Calçado describes duplicated profile-merging logic at SoundCloud being pulled down into a UserProfileService. Keep business rules out of the BFF: Microsoft says it should handle only client-specific logic, with cross-cutting features handled separately. Microsoft also says the pattern may not suit cases where interfaces make the same or similar requests, or only one interface uses the backend.

7 · In the wild

Real implementations and where our own systems use it.

Phil Calçado's September 2015 post describes SoundCloud building a separate backend per frontend after its generic public API got in the way of a new iOS app; the term was coined by SoundCloud's web tech lead, Nick Fisher, and at one point about five BFFs were in production. Sam Newman's article (November 2015) describes the pattern as used at REA and SoundCloud. Microsoft's Azure Architecture Center page is based on Newman's, and its example places API Management in front of a BFF per client running on Azure Functions. AWS's January 2023 post describes “one backend per user experience” with a REST variant on API Gateway and a GraphQL variant on AppSync; its micro-frontends guidance has each BFF belong to one micro-frontend, not shared across bounded contexts.

8 · Related patterns

What it is confused with or combined with.

An API gateway is one shared entry point for routing, authentication and rate limits; it commonly sits in front of the BFFs. GraphQL lets clients choose their fields; Microsoft notes that with frontend-specific resolvers a separate BFF may add no value. Server-driven UI goes further and lets the backend decide layout as well as data. Graceful degradation is how a BFF handles a failed downstream call.

9 · Recap

Three takeaways.

One API for every client suits none of them. Give each experience one thin backend, owned by its team. Shape and combine data there, and keep business rules downstream.

Recap

  • One API for every client suits none of them
  • One thin backend per experience, owned by its team
  • Shape and combine; keep business rules downstream
