Stripe payments

How a payments API makes every charge happen exactly once: idempotency keys, rate limiters, a payment state machine, 3-D Secure and signed webhooks, on a sharded database that moves data while it runs.

1 · Overview

What it is, who uses it, and the one idea everything depends on.

Stripe gives businesses (merchants) an API for taking payments online. A merchant's server talks to the API with a secret key. The customer's card details go from the checkout page straight to Stripe through Stripe.js and Elements, so the merchant never handles the full card number. Behind the API sit acquiring banks, card networks and the banks that issue cards.

Everything in the design depends on one promise: a payment happens exactly once, even when connections drop, clients retry, banks are slow and outcomes arrive days later. Idempotency keys, the PaymentIntent state machine and webhooks with retries all exist to keep that promise.

2 · Requirements and scale

What users need, the quality targets, and back-of-envelope numbers.

Scale, from Stripe's own publications. The 2025 annual letter (published 24 February 2026) reports $1.9 trillion of total volume in 2025, up 34% from 2024 and roughly 1.6% of global GDP, from more than five million businesses using Stripe directly or through platforms. In August 2026 Stripe wrote that it targets 99.9995% reliability for its public API.

Back of the envelope: $1.9 trillion ÷ 31.5 million seconds in a year ≈ $60,000 a second on average; peaks such as Black Friday are much higher.

The functional requirements in the video are ours, written from the product: retries never double-charge; card numbers stay off merchant servers; strong customer authentication runs when a bank or law requires it; old integrations keep working; merchants hear about every outcome; and one noisy merchant cannot slow the others.

3 · Context

Who and what the system talks to (C4 level 1).

Two kinds of user: the merchant (its website, app and server) and the customer paying it. Stripe answers each API call and also pushes signed webhooks for things that happen later, such as a bank debit clearing or a dispute.

The money side is simplified in the diagram. A card authorisation travels via an acquirer and the card network to the issuing bank, which approves or declines it and may ask the customer to authenticate with 3-D Secure. Settled funds are paid out to the merchant's bank. The exact acquiring arrangement varies by country and is not shown.

5 · Deep dive

Inside the most interesting component (C4 level 3).

Inside the API edge. Stripe has written about each mechanism separately; the order they run in is our reconstruction.

  • Versions. Each account has a default API version; a request can override it with the Stripe-Version header. Breaking changes are wrapped in version change modules, and the API walks the current response back through them to the caller's version (2017 post). Since the 2024-09-30.acacia release, Stripe ships monthly releases with no breaking changes and two named major releases a year.
  • Rate limiters and load shedders (March 2017): a request rate limiter (token bucket, Redis), a concurrent requests limiter, a fleet usage load shedder that keeps capacity for critical requests such as creating charges and rejects others with 503, and a worker utilisation load shedder that sheds lower-priority traffic, starting with test mode. Stripe's advice: start with the request rate limiter, and dark-launch each limiter first.
  • Idempotency. Clients send an Idempotency-Key header (up to 255 characters; a V4 UUID is suggested) on POST requests. For API v1, Stripe saves the status code and body of the first request once the endpoint starts executing, and replays it for retries, including 500 errors. Keys can be pruned once at least 24 hours old. Mismatched parameters are rejected. Requests that fail validation or clash with a concurrent request are not saved and can be retried.

6 · Core flows

Two or three requests that matter, step by step.

A PaymentIntent with 3-D Secure. The merchant creates a PaymentIntent as soon as it knows the amount; it starts in requires_payment_method. The browser confirms it with card details. Stripe decides whether 3-D Secure is needed (regulation such as SCA in Europe, an issuer soft decline, Radar rules, or a manual request). If so, it contacts the issuer's access control server and the PaymentIntent moves to requires_action; Stripe.js shows the challenge. The issuer decides the flow, which may be frictionless. After authentication Stripe attempts the charge; the PaymentIntent ends in succeeded, requires_capture or, on failure, back in requires_payment_method so the customer can try again. Bank debits can sit in processing for days.

Webhook delivery with retries. Stripe posts each event to the merchant's HTTPS endpoint with a Stripe-Signature header: a timestamp and an HMAC SHA-256 signature. Non-2xx responses and timeouts are retried for up to three days with exponential backoff in live mode (three times over a few hours in a sandbox), each with a fresh timestamp and signature. Stripe's guidance for handlers: verify the signature (libraries allow five minutes of clock difference by default), record event IDs because duplicates happen, return 2xx before slow work, process from a queue, and do not rely on ordering; fetch the latest object if needed.

7 · Data and caching

What is stored where, for how long, and what is never stored.

Stripe chose MongoDB when it launched in 2011 and built DocDB, a database-as-a-service on MongoDB Community, because no off-the-shelf service met its needs. In June 2024 Stripe described over five million queries per second, 10,000+ distinct query shapes, petabytes of financial data in 5,000+ collections across 2,000+ shards. Applications go through database proxies written in Go, which handle admission and access control and use a chunk metadata service to route each query. Each shard's oplog is shipped to Kafka and archived to object storage such as Amazon S3.

10 · Patterns used

The named patterns, each linked to its pattern walkthrough.

  • Idempotency keys: retries never repeat a side effect.
  • Retry with backoff and jitter: what Stripe recommends to clients, and how webhooks are delivered.
  • Rate limiting and load shedding: token buckets per user; critical traffic first.
  • Timeouts: webhook endpoints must answer quickly; 3-D Secure screens must allow at least five minutes.
  • Sharding: DocDB, with live chunk migration.

12 · What we would build first

An MVP cut and our recommendations.

Our recommendations for a small payments platform, not Stripe's:

  • One service and Postgres; payments as a strict state machine with allowed transitions only.
  • Idempotency keys stored with a unique constraint on (account, key), kept for at least 24 hours, rejecting mismatched parameters.
  • A token-bucket rate limiter per API key; add load shedding when there is a fleet to protect.
  • Webhooks from a transactional outbox, signed with HMAC and a timestamp, retried with exponential backoff and jitter.
  • Hosted card fields from a card processor, so card numbers never reach our servers.
  • A dated API version on every account from day one.

What we would build first

  • One service and Postgres; payments as a strict state machine
  • Idempotency keys with a unique constraint, kept 24 h or more
  • A token-bucket rate limiter per API key
  • Signed webhooks from a transactional outbox, retried with backoff
  • Hosted card fields from a processor: never hold card numbers
  • A dated API version on every account from day one
