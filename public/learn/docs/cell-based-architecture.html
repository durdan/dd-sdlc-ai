Cell-based architecture

Split the whole stack into identical, independent cells behind a thin router, so a bad release, a poison request or a noisy customer hurts one cell instead of every customer.

1 · The problem

What goes wrong without it, shown happening.

Most services start as one deployment: one load balancer, one fleet, one database, serving every customer. Every request shares the same code version, the same data store and the same capacity. So the failures that are hardest to contain, a bad release, a poison pill request that triggers a crash, a customer whose traffic suddenly surges, reach everyone at once. The blast radius is 100%. AWS frames the choice as: “Is it better for 100% of customers to experience a 5% failure rate, or 5% of customers to experience a 100% failure rate?”

2 · The naive fix

The obvious approach and why it breaks.

More replicas across more availability zones protect against a machine or a zone dying, but not against failures carried by the request or the code. Every replica runs the same version, so a poison request crashes the first replica it reaches; the client retries, the load balancer picks another replica, and that one crashes too. Redundant copies of the same thing fail the same way. Bigger machines (scaling up) do not help either: they meet non-linear scaling cliffs and service limits, and the system becomes too big to test at full size.

3 · The pattern

Its parts and the role of each.

A cell-based architecture runs several isolated instances of the whole workload. Each instance, a cell, is independent, shares no state with other cells, and handles a subset of requests chosen by a partition key such as a customer ID. AWS describes three parts:

PartJob
Cell router“The thinnest possible layer”: maps the partition key to a cell and forwards the request, and nothing else. Presents a single endpoint to clients.
CellA complete workload, services and data, able to operate on its own.
Control planeAdministration: provision and remove cells, deploy, migrate customers between cells.

The router is the one component with a view of every cell, so it must be simple and itself highly resilient. Keep everything else that is global as small as possible. AWS recommends static stability: the data plane (router and cells) keeps working on its last known state even if the control plane is impaired, for example by loading routes into memory so routing continues when the control plane or the map's store is unavailable.

Cells need not mean multiplying infrastructure: AWS notes an application with 30 hosts might keep the same 30 hosts, regrouped into cells behind a router.

4 · How it works

The normal flow, step by step.

A request carries its partition key. The router looks the key up in its mapping and forwards the request to that cell, which serves it entirely from its own services and data. AWS lists several mapping approaches: a full mapping table, prefix or range-based mapping, naïve modulo, and consistent hashing, plus an override table for testing, quarantining and pinning heavy keys. Assigning a new customer to a cell and registering it with the router is the control plane's job.

Growth is scale-out: each cell has a capped, tested maximum size, and you add cells rather than enlarge them. When a customer must move, for example because it has outgrown a shared cell, AWS outlines four phases: clone the data to the new location as a non-authoritative copy, flip the new copy to authoritative, redirect from the old location to the new one, and forget the old data. AWS's best practices are to treat your current stack as “cell zero”, to run more than one cell from day one, and to build the migration mechanism from day one too.

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

A poison request or a noisy customer reaches only the cell that owns that key, so only that cell's customers are affected. AWS's example: with 10 cells serving 100 requests, a failure in one cell leaves 90% of requests unaffected. Roughly, the blast radius is 1/N.

Bad releases are contained the same way if you deploy in waves: one cell first, then progressively more, with monitoring between waves and automatic rollback. AWS calls for deploying “cell by cell or set of cells”, and Microsoft notes you can roll updates out to some stamps first. A failing cell must also protect itself from overload: know its limit through load testing, and shed load beyond it (AWS mentions token buckets and API Gateway rate limits).

Two shared pieces need special care. The router is a potential single point of failure and must be built with maximum reliability. A regional outage still takes down every cell in that region unless cells are placed across regions or availability zones accordingly.

6 · Trade-offs

What it costs, when not to use it, and its main variants.

Cell size is a balance. AWS names three forces: big enough for the largest workload, small enough to test at full scale and stay under service limits, and big enough for economies of scale. Smaller cells mean a smaller blast radius (10 cells → 10% each, 100 cells → 1%) but more copies to deploy and operate; larger cells use capacity better.

The costs: more infrastructure and per-cell overhead (Microsoft: deploying copies “substantially increases the cost”), a routing layer to build and keep highly available, specialised tooling and fully automated pipelines, harder cross-cell operations (to count customers you query every stamp or aggregate into a central warehouse), and difficult tenant migration. Microsoft suggests not using it when the solution is simple, can scale within one instance, needs data replicated across all instances, or only needs some components scaled, in which case shard the data store instead.

Shuffle sharding is a variant from the AWS Builders' Library. With eight workers in four fixed shards of two, one bad customer affects 25% of customers. Giving each customer its own pair of the eight workers (28 possible pairs) cuts the scope of impact to 1/28, provided clients are fault tolerant and retry. Route 53 assigns each domain four of 2,048 virtual name servers, about 730 billion possible shuffle shards.

7 · In the wild

Real implementations and where our own systems use it.

AWS published Reducing the Scope of Impact with Cell-Based Architecture on 20 September 2023 as Well-Architected guidance, and says its service teams have used cell-based architecture for more than a decade. The AWS Builders' Library covers shuffle sharding (Route 53) and static stability. Microsoft's Deployment Stamps pattern describes the same structure; a stamp is “sometimes a service unit, scale unit, or cell”, and stamps can implement deployment rings. Slack described its migration in August 2023: after a June 2021 network fault in one availability zone in us-east-1, it treated each AZ as a cell, siloed services to their own AZ, and set a goal of draining an AZ's traffic within five minutes using Envoy weighted clusters controlled by its own xDS control plane. The most critical user-facing services took about 1.5 years to migrate.

8 · Related patterns

What it is confused with or combined with.

A bulkhead partitions resources inside one process; AWS presents cells as the bulkhead idea applied to the whole workload. Sharding splits only the data; Microsoft notes stamps implicitly shard data, and suggests sharding alone when only the data store needs to scale. Consistent hashing is one of the mapping approaches for the router. Shuffle sharding overlaps shards per customer. Graceful degradation decides what users of an impaired cell still get.

9 · Recap

Three takeaways.

Split the whole stack into independent cells, so a failure hits about one in N customers. Keep what is shared, the router and the control plane, tiny and statically stable. Grow by adding cells of a tested size, deploy in waves, and build customer migration from day one.

Recap

  • Split the whole stack into independent cells: blast radius about 1 in N
  • Keep the shared router and control plane tiny and statically stable
  • Grow by adding cells, deploy in waves, build migration from day one
