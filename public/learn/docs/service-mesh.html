Sidecar and service mesh

Move TLS, retries, timeouts and telemetry out of every service and into a proxy that runs beside it, configured centrally by one control plane.

1 · The problem

What goes wrong without it, shown happening.

Every service that calls another needs the same networking plumbing: TLS, retries, timeouts, metrics and tracing. When each service implements these itself, in its own language and with its own library versions, the behaviour drifts. One service retries three times, another not at all; one encrypts, another speaks plain HTTP; monitoring receives metrics in several formats. A single organisation-wide change, such as a new security rule, means patching every code base. Microsoft's sidecar guidance names the root cause: in-process features must be written in the parent application's language, and each component needs language-specific libraries.

2 · The naive fix

The obvious approach and why it breaks.

A shared library looks like the fix, but a library exists per language. It is written once, ported by hand to the others, and upgraded by each team on its own schedule. Until every port ships and every service redeploys, some calls are encrypted and some are not, and some have timeouts and some do not. The library approach is still right when every service uses one language: Microsoft notes that language-specific libraries give deeper integration and less network overhead.

3 · The pattern

Its parts and the role of each.

The sidecar pattern deploys a helper as a separate process or container alongside each instance of an application. Microsoft describes it as attached to its parent and sharing its life cycle, so the two are created and retired together; each application instance gets its own sidecar instance. A service mesh puts a proxy sidecar beside every service. In Linkerd's words, the proxies make up the data plane and are controlled as a whole by the control plane.

PartJob
Sidecar proxy (data plane)Handles every inbound and outbound call: mTLS, retries, timeouts, load balancing, metrics
Control planeService discovery; turns routing rules into proxy configuration and pushes it at runtime
Certificate authorityIssues each workload an identity for mutual TLS (in Istio, part of istiod)
Ingress gatewayNorth-south: traffic entering the mesh from outside
Telemetry backendReceives metrics and spans in one format from every proxy

The mesh's main job is east-west traffic, between services. Traffic entering from outside (north-south) goes through a gateway first.

4 · How it works

The normal flow, step by step.

The control plane pushes routes and a certificate to each sidecar. The application makes a plain HTTP call on localhost; its sidecar opens mutual TLS to the destination's sidecar, and both check each other's identity. Istio's routing can split traffic by weight between versions (its example uses 75% and 25%), which is how canaries and gradual rollouts work; the 90/10 split in the video is illustrative. Every call produces metrics and a trace span, but Istio's docs say applications must still propagate trace headers (such as traceparent) from incoming to outgoing requests for spans to join into one trace.

What the mesh adds, with no code change

  • Mutual TLS and a workload identity for every service
  • Traffic splitting by percentage: canaries and gradual rollouts
  • Retries, timeouts and circuit-breaking limits as config
  • Outlier detection: stop sending to a misbehaving pod
  • Metrics and trace spans for every request

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

When one instance misbehaves, the proxy can retry on another and eject the bad one. Envoy's outlier detection defaults to ejecting a host after 5 consecutive 5xx responses, for a base time of 30 seconds that grows with each repeat ejection, and never ejects more than 10% of a cluster by default. Retries are where meshes hurt: Istio's default retries an HTTP request twice, and if the application also retries, attempts multiply (three app tries × three mesh attempts = nine calls, an illustrative case). Istio warns that application and mesh timeouts can conflict, and that applications still need their own fallback when every instance fails. Linkerd retries only requests known to be idempotent, within a retry budget. Choose one layer to own retries and timeouts.

6 · Trade-offs

What it costs, when not to use it, and its main variants.

Every call passes through two extra proxies, every pod carries a proxy's CPU and memory, and the control plane is another critical system to run and upgrade. Microsoft says a sidecar might not be suitable when inter-process latency matters, when the application is small, when the component must scale independently, when the platform already provides the capability, or when a sidecarless data plane meets the need. Sidecarless designs reduce the per-pod cost: Istio's ambient mode (generally available in Istio 1.24, November 2024) uses a per-node ztunnel for L4 work such as mTLS, authentication and telemetry, and adds an Envoy-based waypoint proxy only where L7 features are needed. Cilium uses eBPF as its in-kernel datapath and per-node Envoy proxies to parse HTTP, gRPC and DNS.

7 · In the wild

Real implementations and where our own systems use it.

Envoy, originally built at Lyft, is a C++ L7 proxy designed to run alongside each application server, with retries, circuit breaking, outlier detection, statistics and distributed tracing; it is a CNCF graduated project. Istio uses Envoy sidecars or ambient mode, with istiod as its control plane, and became a CNCF graduated project on 12 July 2023. Linkerd was rewritten around Rust micro-proxies in 2018 and graduated from the CNCF in 2021. Cilium provides mesh features on an eBPF datapath. Kubernetes added native sidecar containers (init containers with restartPolicy: Always) in v1.28, on by default from v1.29 and stable in v1.33; they start before the app containers and stop after them.

8 · Related patterns

What it is confused with or combined with.

An API gateway handles north-south traffic entering the system; a mesh handles east-west traffic between services, and many systems run both. Retries, timeouts and circuit breaking are patterns the mesh implements as configuration. The ambassador pattern is a sidecar-style proxy that sends requests on behalf of its client, useful for legacy applications that are hard to change.

9 · Recap

Three takeaways.

Take networking plumbing out of the code. Let one control plane configure the proxies. Pay for it knowingly, and retry in one layer only.

Recap

  • Move network plumbing out of the code, into a proxy beside it
  • Proxies are the data plane; one control plane gives rules and identity
  • It costs hops, CPU and operations: own retries in one layer
