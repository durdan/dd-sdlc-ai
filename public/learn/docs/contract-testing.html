Contract testing

Each consumer records the requests and responses it relies on; the provider proves it still honours them in its own build; and nothing deploys until the versions are known to work together.

1 · The problem

What goes wrong without it, shown happening.

Two services are built and deployed by different teams. The provider changes its API in a way that looks harmless from the inside, such as renaming a field, and its own tests stay green because none of them know what consumers read. The consumer breaks in production. The walkthrough's example (an orders API renaming total to totalAmount) is illustrative.

2 · The naive fix

The obvious approach and why it breaks.

Two obvious fixes each solve half the problem.

  • A shared end-to-end environment. Deploy everything and test whole journeys. It catches integration bugs, but late: you must deploy before you find them, the suites are slow, environments are shared and hard to keep healthy, and failures are often environmental rather than real. Pact's docs list building and maintaining test environments and fixing flaky integration tests as the time sinks; Spring Cloud Contract's docs note that testing one service can mean deploying six others and a couple of databases.
  • Mocks in the consumer's tests. Fast and reliable, but written by the consumer. In Spring Cloud Contract's words, such stubs “might have nothing to do with reality”, and “you can go to production with passing tests and failing production.”

3 · The pattern

Its parts and the role of each.

Consumer-driven contracts keep the speed of mocks but make the mock accountable. Ian Robinson's 2006 article distinguishes the provider contract (everything a provider exposes), consumer contracts (what each consumer actually expects), and the consumer-driven contract, derived from the union of existing consumer expectations.

PartJob
Consumer testsDrive the real client code against a mock provider; each request and the minimal response it needs becomes an interaction
Contract (a “pact” in Pact)The recorded interactions: only what this consumer uses
BrokerStores contracts and verification results by version, triggers provider builds by webhook, and records what is deployed where
Provider verifierReplays each request against the real provider and checks the response contains at least what was expected
Provider statesNamed preconditions (“order 42 exists”) the provider sets up before an interaction is replayed
Can-I-deploy checkAsks the broker whether a version has passing verification against every version already in the target environment

4 · How it works

The normal flow, step by step.

The consumer test registers the expected request and response with Pact's mock provider, calls it through the real client, and on success writes the pact. The pact is published to the broker against the consumer's version. A webhook can start the provider build, which replays each interaction; extra fields in the response are allowed. The verification result is published back. Before deploying, pact-broker can-i-deploy --pacticipant Checkout --version 23 --to-environment production consults the matrix of tested version pairs and exits 0 (“Computer says yes”) or 1. After deploying, record-deployment tells the broker what is now in production.

Events. Pact supports message contracts independent of the transport (Kafka, SNS, RabbitMQ and so on); in the test Pact stands in for the message broker. Pact recommends separating transport adapter code from the code that builds or handles the message body, and testing the latter on each side.

Events have contracts too

  • The producer is the provider; each subscriber is a consumer
  • Contract is the message body, not the transport
  • Test the code that builds and handles the message
  • Same broker, same can-i-deploy check

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

When the provider makes a breaking change, verification fails in the provider's own build, naming the consumer and interaction, and can-i-deploy returns a non-zero exit code so the pipeline stops. The fix is to sequence the change: add the new field alongside the old one, let consumers migrate, and remove the old field once no deployed consumer's contract uses it.

Edge cases: contracts that over-specify (exact values, the reasons a validation fails) break on harmless changes, and Pact advises testing how validation fails rather than why. A consumer with no contract gets no protection. Pass-through services that forward requests without validating them can hide breakage downstream.

6 · Trade-offs

What it costs, when not to use it, and its main variants.

Consumer-driven versus schema-based. In the provider-driven alternative the provider publishes a schema and a tool rejects breaking changes between versions: oasdiff for OpenAPI, buf breaking for protobuf, and schema registries for Avro, Protobuf and JSON Schema. These work when consumers are unknown, such as public APIs, but they check the schema rather than the running code, and they block changes to fields nobody uses. Pact's docs point out that provider-only contract testing gives no assurance that consumers call the provider correctly. PactFlow, the hosted broker, also offers bi-directional contract testing, comparing consumer contracts with a provider's OpenAPI document; it relies on that document matching the code.

Not covered. Contract tests check the format and content of requests and responses, not behaviour: side effects and business rules belong in the provider's functional tests. Pact lists performance and load testing, public APIs and pass-through APIs as poor fits, and is described as best for integrations where you control both sides. A small number of end-to-end smoke tests is still worth keeping.

Consumer-driven or schema-based

Consumer-driven (Pact)Schema-based (OpenAPI, protobuf, Avro)
Checks what consumers actually useChecks the whole published schema
Provider may change anything unusedAny breaking schema change fails
Needs consumers you know and can reachWorks for public APIs too
Proves the provider's real responsesProves the schema, not the code

What contract tests do not cover

  • Business rules and side effects: the provider's own tests
  • Performance and load
  • Public APIs with unknown consumers
  • Pass-through APIs that forward without checking
  • A few end-to-end smoke tests still earn their keep

7 · In the wild

Real implementations and where our own systems use it.

Ian Robinson's “Consumer-Driven Contracts: A Service Evolution Pattern” was published on martinfowler.com in June 2006. Pact implements consumer-driven contracts for HTTP and messages; the open-source Pact Broker (or the hosted PactFlow) shares pacts and results, keeps the compatibility matrix and answers can-i-deploy. Spring Cloud Contract defines contracts (the docs show Groovy and YAML), generates provider-side tests and WireMock stubs for consumers, and covers HTTP and messaging; its GitHub repository was archived in July 2026 with a note that it is no longer actively maintained there and that Stubborn.sh has taken over maintenance. On the schema side, buf breaking compares protobuf against a previous version (a Git branch, a BSR module and more), with FILE, PACKAGE, WIRE_JSON and WIRE rule categories (FILE by default). Confluent Schema Registry checks each new schema for compatibility, with BACKWARD as the default. oasdiff detects breaking changes between two OpenAPI documents.

8 · Related patterns

What it is confused with or combined with.

A tolerant reader reads only the fields it needs, which keeps contracts small; Robinson's article cites the robustness principle (“conservative in its sending behaviour and liberal in its receiving behaviour”). Expand and contract is how a provider changes safely once contracts tell it who depends on what. API gateways and backends for frontends are both consumers and providers, so they need contracts on both sides. A strangler-fig replacement must keep honouring the contracts of the system it replaces.

9 · Recap

Three takeaways.

Consumers record exactly what they rely on. Providers verify those contracts in their own build. Ask before you deploy, every time.
