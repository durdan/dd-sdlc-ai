Rate limiting

Give every caller its own budget, reject the excess early with a clear 429, and keep one noisy client from taking everyone else's share.

1 · The problem

What goes wrong without it, shown happening.

A shared API serves many clients from one pool of capacity: threads, database connections, CPU. Nothing in that arrangement guarantees fairness. When one client misbehaves (a script retrying in a tight loop, a batch job running far faster than intended, a retry storm after an outage) it can consume the whole pool, and well-behaved clients start timing out even though they did nothing wrong.

2 · The naive fix

The obvious approach and why it breaks.

A single global cap protects the server but not the other clients: whoever sends the most uses most of the budget, so the innocent client's request is the one refused. Adding servers has the same flaw, because a runaway client simply grows to fill them. The fix has to be per caller.

3 · The pattern

Its parts and the role of each.

A rate limiter sits in front of the work (in a gateway, proxy or middleware) and gives each caller its own budget. It rejects over-budget requests before they cost anything.

PartJob
Key extractorWho is asking: API key, user, tenant, or IP address for anonymous traffic
PolicyWhat that key may do, e.g. 100 requests per minute, or a rate plus a burst
Counter storeWhere counts live: memory per instance, or a shared store such as Redis
DecisionForward, or reject with 429 Too Many Requests and a Retry-After hint

Five algorithms are common:

AlgorithmHow it countsCatch
Fixed windowOne counter per window (e.g. per minute)Up to double the limit across a window boundary
Sliding window logA timestamp per request; count those in the last windowMemory grows with traffic
Sliding window counterCurrent count plus the previous window's count weighted by its overlapAssumes the previous window's traffic was even
Token bucketTokens refill at a steady rate up to a bucket size; each request spends oneTwo knobs to tune: rate and burst
Leaky bucketRequests drain at a fixed rate; excess is queued (delayed) or droppedBursts wait or are refused

Cloudflare's write-up gives the sliding window counter's formula with an example: with a limit of 50 a minute, 42 requests in the previous minute and 18 in the current one (15 s in), the estimate is 42 × 45/60 + 18 = 49.5.

4 · How it works

The normal flow, step by step.

The sequence shows a token bucket at an API gateway with its state in Redis. The gateway takes a token for the caller's key in one atomic operation (in Redis, typically a script), so two gateways cannot both spend the last token. Allowed requests are forwarded, and the response can tell the client how much budget remains. When the bucket is empty, the gateway answers 429 with Retry-After set to when the next token will arrive. The bucket size, counts and two-second wait are illustrative.

429 Too Many Requests is defined in RFC 6585 (section 4); MDN notes that a Retry-After header may say how long to wait. The IETF httpapi working group's draft (draft-ietf-httpapi-ratelimit-headers-11, May 2026, still an Internet-Draft) defines a RateLimit-Policy field (quota q, window w) and a RateLimit field (remaining r, reset t), e.g. RateLimit: "default";r=50;t=30. Many APIs still use their own X-RateLimit-* headers, as GitHub does.

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

With many gateway instances, per-instance counters let a client spread across N instances use N times its limit. A shared counter fixes this at the cost of a network hop per request and a new dependency: if the store is unreachable, the limiter must fail open (serve without limits) or fail closed (reject, turning a cache outage into an API outage). Envoy recommends combining a local token bucket, which absorbs bursts cheaply, with its global rate limit service for the finer decision.

Other edge cases: fixed windows allow bursts at boundaries; IP-based keys lump together everyone behind one NAT or office network; clients that retry 429s immediately amplify the load; and read-then-write counters race, so the check and the increment must be one atomic operation.

Where it still goes wrong

  • Fixed windows let through double the limit at a boundary
  • Many users behind one office IP share a single budget
  • Clients that ignore 429 and retry at once make it worse
  • Read-then-write counters race; use one atomic operation

6 · Trade-offs

What it costs, when not to use it, and its main variants.

Rate limiting is about fairness per client and applies even when the server is idle. Load shedding is about survival: it drops low-priority work when the server itself is overloaded, whoever sent it. Stripe runs both. Limits set too low turn away good traffic, so publish them, return clear headers, and monitor rejections. For slow, expensive endpoints a concurrency limit (requests in flight) often fits better than a rate: Stripe's example allows 20 concurrent requests per user.

Choosing an algorithm

AlgorithmTrade-off
Fixed windowCheapest; up to double the limit at a boundary
Sliding window logExact; stores a timestamp per request
Sliding window counterTwo numbers; small error from assuming even traffic
Token bucketAverage rate plus controlled bursts
Leaky bucketSmooth output; queues or drops bursts

Rate limiting is not load shedding

  • Rate limiting: fairness per client, even when the server is idle
  • Load shedding: protects the server, judged by its own health
  • Limits too low turn away good customers; publish and monitor them
  • Concurrency limits suit slow, expensive endpoints better than rates

7 · In the wild

Real implementations and where our own systems use it.

Stripe (Paul Tarjan, 2017) describes four limiters: a request rate limiter, a concurrent requests limiter, a fleet usage load shedder that reserves capacity for critical methods (their example: 20% for critical requests), and a worker utilisation load shedder as the last line of defence. They use the token bucket algorithm with state in Redis. Envoy has a local rate limit filter (a token bucket per Envoy process, answering 429 by default) and global rate limiting, which calls an external gRPC service; the reference implementation is written in Go with a Redis backend. NGINX limit_req uses the leaky bucket method: excess requests are delayed up to burst, nodelay serves them without delay, and rejections return 503 unless limit_req_status changes it. AWS API Gateway throttles with a token bucket: a rate (tokens per second) and a burst (bucket capacity), defaulting to 10,000 requests per second with a burst of 5,000 per account per Region in most Regions, applied on a best-effort basis. GitHub allows 5,000 REST requests an hour for an authenticated user and 60 an hour for unauthenticated requests per IP, plus secondary limits such as 100 concurrent requests, and returns 403 or 429 when exceeded.

8 · Related patterns

What it is confused with or combined with.

Client-side throttling is the polite twin: the client keeps its own budget and slows down before the server has to refuse. Retries must honour Retry-After and back off with jitter, or they recreate the storm. Backpressure carries the same "slow down" signal inside a pipeline. Bulkheads give each tenant a separate pool. A circuit breaker is the caller choosing to stop calling something that keeps failing.

Neighbours

PatternRelationship

9 · Recap

Three takeaways.

Give every caller its own budget. Count it reliably: a token bucket for bursty APIs, in one shared, atomic place across instances. Reject early and clearly, with 429 and Retry-After.

Recap

  • Give every caller its own budget, by key, user or IP
  • Token bucket for bursty APIs; count in one shared, atomic place
  • Reject early with 429 and Retry-After, and let clients slow down
