SDLC.dev: from idea to specification

How an open-source Next.js app turns a one-paragraph idea into business, functional, technical and UX specifications: one streamed AI call per document, earlier documents summarised by a cheaper model, prompts kept as data, and a wizard that retries and switches provider.

1 · Overview

What it is, who uses it, and the one idea everything depends on.

SDLC.dev is the web front of dd-sdlc-ai, the author's own open-source project, published under the MIT licence. You describe a product idea in plain words and it writes the documents a team needs to start building: a business analysis, a functional specification, a technical specification, a UX specification and Mermaid diagrams. Users are product owners on the website, and developers through a command-line tool and an MCP server that ship in the same repository.

The one idea everything depends on: each document is its own streamed AI call, and each later document is given a short summary of the earlier ones. That keeps the set consistent without pasting whole documents into every prompt, and it is where both the speed and the cost of a project come from.

2 · Requirements and scale

What users need, the quality targets, and back-of-envelope numbers.

The numbers in the video are read from the code, not from usage data. The repository README lists platform statistics (documents generated, users, uptime) that we could not verify, so we leave them out.

  • The dashboard writes up to five documents in order: business, functional, technical, UX, then diagrams. The Document API accepts eight types: business, functional, technical, ux, mermaid, wireframe, coding and test.
  • A signed-out session may generate 10 documents per 24 hours (5 for meeting transcripts).
  • vercel.json lets every API function run for up to 300 seconds.
  • The context optimiser budgets 3,000 characters of earlier context for functional and technical specs, 2,500 for UX and 2,000 for diagrams.

Back of the envelope (our arithmetic): five writing calls, plus summary calls only when an earlier document is over budget: one for the functional spec, two for the technical spec, three for the UX spec. So up to eleven model calls per five-document project.

The functional requirements are ours, written from the product: ideas in plain words, visible progress, documents that agree with each other, a trial without signing up, prompts that change without a release, and hand-off to existing tools.

3 · Context

Who and what the system talks to (C4 level 1).

Two kinds of user: the product owner in the browser, and developers using the CLI or the MCP server, both published as npm packages from the same repository. The README says these call the platform's REST API; we have not traced that path in the code.

Outside systems: OpenAI (GPT-4o writes documents, GPT-4o-mini summarises), Anthropic Claude (code tasks, and the fallback for the Idea-to-Spec wizard), Supabase (Postgres and sign-in), GitHub, and delivery tools with their own integration routes: Jira, Confluence, ClickUp, Trello, Notion and Slack.

5 · Deep dive

Inside the most interesting component (C4 level 3).

Inside /api/generate-document, in order:

  1. Validate: an OpenAI key is configured, the input is not empty, and the type is one of the eight.
  2. Anonymous limit: if there is no signed-in user, check the session (from the x-session-id header) against 10 documents per 24 hours; return 429 with the reset time when used up.
  3. Resolve the prompt: a custom prompt in the request wins; otherwise an active A/B experiment (a hash of the user id against traffic_split picks control or variant); then the user's personal default; then the system default; finally a prompt built into the route. Database prompts are cached in memory for five minutes.
  4. Optimise context (not for business or diagrams): each earlier document over the budget is summarised with GPT-4o-mini at temperature 0.3, up to 1,500 tokens, using a prompt tuned to the target (for example "business for technical"). If summarising fails, the text is cut at the last sentence break instead.
  5. Generate and stream: streamText with GPT-4o; the route writes server-sent events of type chunk, then complete with the cleaned-up document, or error.

6 · Core flows

Two or three requests that matter, step by step.

One project. The owner types an idea and picks documents. The dashboard posts the business analysis request; the API loads the business template and streams GPT-4o's answer into the page. For the functional spec the dashboard sends the business analysis along; the optimiser summarises it and the summary goes into the prompt. Technical and UX specs follow with more earlier documents each; diagrams come last. Only then does the dashboard save the project and documents through the Projects API. There is no step that asks the owner clarifying questions before writing.

The Idea-to-Spec wizard has five steps (Spark, Expand, Structure, Architect, Spec), each producing Mermaid diagrams: a mind map, use-case and journey diagrams, architecture, C4 and sequence diagrams, then an entity-relationship diagram and a flowchart. Each diagram is one call to /api/idea-to-spec/generate, which streams events start, chunk, retry, complete and error. It tries OpenAI GPT-4o first; on 429 or 5xx it retries up to three attempts with 1 s then 2 s delays, then falls back to Claude Sonnet 4 with the same rule.

7 · Data and caching

What is stored where, for how long, and what is never stored.

Durable data is in Supabase Postgres (schema in initial-setup.sql): sdlc_projects holds the idea and status; documents holds one row per document with a version; prompt_templates and prompt_experiments hold prompts and A/B tests; prompt_usage_logs can record tokens, timing and success; anonymous_project_sessions holds a session's count, IP address and user agent, reset after 24 hours.

The only server-side cache is the prompt cache: five minutes, in each function instance's memory, so a prompt edit can take up to five minutes to reach every instance. The dashboard keeps recent results in the browser's localStorage. Generated text is not cached on the server, so every regeneration is a fresh model call.

8 · Growth

How the same design grows from launch to its current scale.

From the commit history (about 200 commits, July 2025 to January 2026): repository created 2 July 2025 with a Jira integration the next day; the Claude code API on 12 July, the Document API on 19 July and the context optimiser on 22 July; anonymous limits on 6 August; the CLI on 17 August and the MCP server on 18 August; the Idea-to-Spec wizard on 31 December 2025. There are no published usage figures we could verify, so we do not describe its scale.

How we would grow it (our design): run generation as a background job and save each document as it completes; cache summaries by a hash of the source document; write independent documents in parallel once the business analysis exists; move the prompt cache to a shared store; and budget tokens per user rather than only documents per day.

10 · Patterns used

The named patterns, each linked to its pattern walkthrough.

  • Retry with exponential back-off: the wizard, three attempts, 1 s then 2 s, only on 429 and 5xx.
  • Rate limiting: 10 anonymous documents per session per day; a daily free allowance for Claude code projects.
  • Timeouts: 300 seconds for every API function.
  • Fallback: a second AI provider in the wizard; truncation when summarising fails; a built-in prompt when the database has none.
  • Cache-aside: prompt templates, five minutes in memory.

12 · What we would build first

An MVP cut and our recommendations.

Our recommendations for building something similar today, not the project's:

  • Idea in, three clarifying questions back, then documents. The current code has no questions step; better input beats a longer prompt.
  • Two documents first: functional and technical specifications.
  • One provider with retries and back-off; add a fallback provider later.
  • Prompts in a versioned table from day one.
  • Save each document on the server as it completes.
  • A per-user token budget, enforced on the server.

What we would build first (our recommendations)

  • One provider with retries and back-off; fallback later
  • Prompts in a versioned table from day one
