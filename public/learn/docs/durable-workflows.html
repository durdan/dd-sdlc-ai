Durable workflows

Write a long-running business process as ordinary code; an engine records every step, so the code resumes exactly where it stopped after a crash or a wait of days.

1 · The problem

What goes wrong without it, shown happening.

Many business processes are several steps long and must finish: charge a card, send a receipt, then pay someone out after a holding period. Run in memory, the process is lost when the server restarts mid-way: the first step has happened, the rest never will, and nothing remembers the wait that was supposed to end next week. The walkthrough uses an illustrative end-of-trip flow for a taxi app.

2 · The naive fix

The obvious approach and why it breaks.

The usual fix is a scheduled job that scans status columns for stuck rows, plus a queue and handler per step. Each handler grows its own retry counts, timeouts and dead-letter queue. It works, but the process is now spread across a table, a scheduler and several services; long waits become next_try_at columns; and no one can read the whole flow in one place.

3 · The pattern

Its parts and the role of each.

A durable workflow engine persists the progress of every run as an event history, “a complete and durable log of everything that has happened in the lifecycle of a Workflow Execution” (Temporal). Your code runs in workers that poll the engine for tasks.

PartJob
Workflow codeDecides what happens next; must be deterministic so it can be replayed
ActivitiesDo the real side effects (charge, email, payout); retried by the engine; should be idempotent
Event historyEvery start, scheduled activity, result, timer and signal, per run
Task queuesHand workflow and activity tasks to whichever worker is free
Durable timersWaits of seconds to years that survive restarts and cost no worker resources
SignalsAsynchronous messages into a running workflow, such as “dispute raised”

The workflow reads like a script

Line of workflow codeWhat the engine does
charge = chargeCard(trip)Runs an activity, retries it, records the result
sendReceipt(trip, charge)Another activity, another recorded result
sleep(7 days)A durable timer: no process waits
await signal or timerA dispute can arrive at any time
payDriver(trip)Runs a week later, on any worker

4 · How it works

The normal flow, step by step.

The trip service starts a workflow. A worker runs the workflow code until it needs an activity and returns a command; the engine records it and hands out an activity task. If the activity fails or times out, the engine retries it according to its retry policy. In Temporal, activities retry by default with a 1-second initial interval, backoff coefficient 2.0, a maximum interval of 100× the initial interval, and unlimited attempts; every activity needs a Start-To-Close or Schedule-To-Close timeout. Each result is recorded. A seven-day sleep becomes a durable timer; when it fires, the workflow continues on any available worker. The 10-second timeout and £18 charge in the walkthrough are illustrative.

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

When a worker dies, another worker receives the workflow with its full history and replays the code from the start. Completed activities are not re-run: their results are read from the history, so local state is rebuilt to the moment of the crash. Temporal: the Worker “uses the Event History to replay the code and recreate the state of the Workflow Execution”.

Replay imposes rules. Workflow code must make the same decisions given the same history: no reading the system clock, no random numbers or GUIDs, no direct network or database calls, no thread sleeps; use the SDK's replay-safe equivalents or put the work in an activity. Microsoft's Durable Functions documentation states the same constraints. Changing code under running workflows can cause a non-determinism error, so long-running workflows need patching or versioning. Activities can still execute more than once, so they should be idempotent. Histories have limits (Temporal: 51,200 events or 50 MB, with a warning at 10,240 events or 10 MB), so endless workflows should periodically continue as a fresh run.

Replay has rules

Do not, in workflow codeDo instead
Read the clockUse the engine's replay-safe time
Generate random numbers or IDsUse the SDK's helper, or an activity
Call a network or databasePut it in an activity
Sleep the threadUse a durable timer
Change running code freelyPatch, or version the workflow

Where it still goes wrong

  • An activity can run twice: make it idempotent
  • No timeout set means a hung call is never retried
  • Unlimited retries by default can hide a real bug
  • Histories have limits: start a fresh run for endless loops
  • The engine is now critical infrastructure

6 · Trade-offs

What it costs, when not to use it, and its main variants.

You gain one readable function per process, retries, timeouts and timers built in, and a complete history for debugging. You pay with a stateful platform to operate (or a managed service), determinism rules your team must learn, versioning discipline, and latency on every step. It is the wrong tool for single-transaction work, for one write plus one message (use an outbox), for millisecond-critical paths and for high-volume streaming.

AWS Step Functions makes the trade-off explicit: Standard workflows run up to one year with exactly-once execution, persisted state and per-transition billing, recommended for non-idempotent actions such as payments; Express workflows run up to five minutes, at-least-once (asynchronous) or at-most-once (synchronous), billed by executions, duration and memory.

What you gain, what you pay

You gainYou pay
The whole process in one readable functionA new platform to run, or a managed service to pay for
Retries, timeouts and timers built inDeterminism rules your team must learn
A full history of every run, for debuggingVersioning care for long-running code
Waits of days or months cost nothingExtra latency on every step

When not to use it

  • One request, one database write: a transaction is enough
  • One write plus one message: use an outbox
  • Latency-critical paths where each step must take milliseconds
  • High-volume streaming: use a stream processor
  • A team with no capacity to run another platform

7 · In the wild

Real implementations and where our own systems use it.

Uber built Cadence and open-sourced it in 2017; it is now a CNCF project. Temporal “originated as a fork of Uber's Cadence” and is MIT licensed. Azure Durable Functions orchestrators use event sourcing and replay, so they must be deterministic, and they can run for days, months or years. Netflix Conductor originated at Netflix; Netflix archived its repository on 13 December 2023, and Conductor OSS is “actively maintained by Orkes and the community”. Restate records each step in a journal and, on failure, replays it, skipping completed steps.

8 · Related patterns

What it is confused with or combined with.

Retries with backoff and timeouts are built into activities; idempotency makes those retries safe. A workflow engine is a natural orchestrator for a saga, with compensations as further activities. The event history is a form of event sourcing. For the simple case of one database write plus one message, the transactional outbox is lighter and needs no engine.

9 · Recap

Three takeaways.

A process that must finish needs its progress written down. Record every step and replay the code to resume. Keep workflow code deterministic and activities idempotent.

Recap

  • A process that must finish needs its progress written down
  • Record every step; replay the code to resume
  • Workflow code deterministic, activities idempotent
