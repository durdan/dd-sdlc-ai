Sharding

Split the rows of one database across many, by a shard key, so writes and storage can grow past what one machine can hold.

1 · The problem

What goes wrong without it, shown happening.

App servers are stateless and easy to multiply. The database usually is not: every write goes to one primary on one machine. Eventually that machine runs out of something: disk space, CPU, I/O, or network bandwidth. Microsoft's pattern page lists storage, compute, network bandwidth and geography as the limits of a single-server data store.

2 · The naive fix

The obvious approach and why it breaks.

Scaling up (a bigger machine) postpones the limit but does not remove it, and the largest machines cost the most. Read replicas spread reads, but each replica is a full copy, so storage does not shrink, and every write still goes to the one primary and is replayed on every replica. Microsoft's guidance is explicit: if the bottleneck is reads, replicas and caches are the better answer; sharding is for when write load or data volume is the problem.

3 · The pattern

Its parts and the role of each.

Sharding divides a data store into horizontal partitions. Each shard has the same schema but holds a distinct subset of rows, chosen by the shard key (also called the partition key). A routing layer sends each request to the shard that owns its key; it can live in the application's data-access code, in a proxy, or inside the database.

PartJob
Shard keyThe column(s) that decide where a row lives
ShardsIndependent databases, same schema, different rows; each usually replicated
Shard mapWhich key range or virtual shard lives on which server; cached by routers
RouterSends a request to one shard, or fans it out to all
BalancerMoves data between shards when they become uneven, then updates the map

Strategies. Range keeps neighbouring keys together, so range queries hit one shard, but sequential keys pile onto the newest shard. Hash spreads keys evenly and needs no map, but range queries fan out. Directory (lookup) keeps a table of where each key lives: the most control, at the cost of a lookup. Microsoft also describes geographic sharding for data residency.

Choosing a key. Microsoft calls the shard key the most critical design decision: it should be immutable, have high cardinality, spread data and load evenly, and match the dominant queries so most requests touch one shard. Avoid monotonically increasing values, low-cardinality fields and volatile fields. Keep related data together (a customer and their orders) by sharding both on the same key.

Choosing the shard key

  • High cardinality: many distinct values
  • Even load: no single value gets most of the traffic
  • Immutable: changing it means moving the row
  • Matches your main queries, so most hit one shard
  • Keeps related rows together: a customer and their orders

4 · How it works

The normal flow, step by step.

A write carries its shard key. The router looks up the owner, usually from a cached copy of the shard map, and sends the write to that one shard, where it commits in an ordinary local transaction. Reads by the same key go to the same shard. Designing so that most operations stay inside one shard is the whole game.

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

Cross-shard queries. A query without the shard key must go to every shard; MongoDB calls this a broadcast or scatter/gather operation. Even run in parallel, the slowest shard sets the latency. Cross-shard transactions. Two-phase commit adds latency and failure modes; Microsoft notes most sharded systems avoid distributed transactions and accept eventual consistency.

Hot shards. Even data does not mean even traffic. One very active key (a celebrity, a giant tenant, today's date) can overload one shard. DynamoDB's guidance is to spread such writes by adding a random or calculated suffix to the key, at the cost of reading every suffix and merging. A large tenant can also be given a shard of its own.

Resharding. With hash(key) mod N, changing N reassigns most keys: from 3 to 4 shards, about three keys in four move. Consistent hashing reduces this to a small fraction. Many virtual shards mapped onto fewer machines let you add capacity by moving whole virtual shards and updating the map, without rehashing everything.

6 · Trade-offs

What it costs, when not to use it, and its main variants.

Sharding adds permanent complexity: monitoring, backups, schema changes and restores now span many databases, and a point-in-time restore of one shard can be inconsistent with the others. Microsoft lists when it may not fit: the data and throughput fit on one instance; the bottleneck is reads; table partitioning in one database is enough; or the dominant queries need joins, multi-entity transactions or aggregations across everything. Before building your own, check what the database already does: many shard for you.

When not to shard

  • Your data and writes still fit on one machine
  • Your bottleneck is reads: use replicas and caches
  • Partitioning inside one database is enough
  • Your main queries join or aggregate across everything

7 · In the wild

Real implementations and where our own systems use it.

MongoDB: a sharded cluster has shards (each a replica set), mongos query routers and config servers. Data is split into chunks by ranged or hashed shard key, and a balancer migrates ranges between shards; since 5.0 a collection can be resharded with a new key. Vitess: a CNCF graduated project that served all YouTube database traffic for over five years; VTGate is a proxy that speaks the MySQL protocol and routes queries to the right shards, and resharding cuts over with only a few seconds of read-only downtime. Citus: a PostgreSQL extension where a coordinator routes each query to one worker or parallelises it across several; distributed tables are split by a distribution column, small reference tables are copied to every worker, and related tables can be co-located. DynamoDB: hashes the partition key to choose a partition and adds partitions automatically as data or throughput grows; each partition supports up to 3,000 read units and 1,000 write units per second. Microsoft's Sharding pattern page describes lookup, range, hash and geographic strategies.

8 · Related patterns

What it is confused with or combined with.

Consistent hashing is how you add shards without moving most keys. Read replicas are often confused with sharding: replicas copy everything to spread reads; shards split data to spread writes and storage, and are usually replicated too. The index table pattern finds rows by a field that is not the shard key. CQRS can maintain a separate read model for queries that span every shard. Leader election matters within each shard, which keeps its own primary.

9 · Recap

Three takeaways.

Shard when writes or storage outgrow one machine, not before. The shard key decides everything. Plan for growth with many small virtual shards.

Recap

  • Shard when writes or storage outgrow one machine
  • The shard key decides everything: choose it with care
  • Plan for growth: many virtual shards, small moves
