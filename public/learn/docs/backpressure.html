Backpressure

Let the slow side set the pace: bound every buffer, signal demand upstream, and decide on purpose what happens when it is full.

1 · The problem

What goes wrong without it, shown happening.

A producer that is faster than its consumer is not a failure of either part; it is a rate mismatch. Put an unbounded queue between them and the mismatch disappears from view: the queue grows by the difference every second. With 1,000 events a second in and 500 out (illustrative numbers), the backlog grows by 500 a second, reaching 1.8 million after an hour, and a new event then waits an hour to be handled (wait ≈ backlog ÷ drain rate). Latency climbs without limit, and the process eventually runs out of memory and loses everything it was holding.

2 · The naive fix

The obvious approach and why it breaks.

A bigger queue or more memory changes when the crash happens, not whether it happens. Every queued item is also older by the time it is handled. Buffers are the right tool for bursts (a temporary excess that the consumer can catch up on); they cannot absorb a sustained excess. Node.js's own guide shows the cost of ignoring the signal: compressing a large file with backpressure disabled used about 1.52 GB of resident memory, against about 88 MB with it.

3 · The pattern

Its parts and the role of each.

Backpressure makes the consumer's capacity visible to the producer, so the producer never sends more than can be handled.

PartJob
Bounded bufferFixed capacity between stages; absorbs bursts but cannot grow for ever
Demand signalThe consumer says how many more items it can take (credit, a window, or a pull)
ProducerSends no more than the outstanding demand; pauses its own source when demand is zero
Overflow policyFor sources that cannot wait: block, reject, drop newest or oldest, or keep only the latest
MetricsBuffer depth, wait time and drop counts, so a slow consumer is seen before users notice

4 · How it works

The normal flow, step by step.

Reactive Streams makes demand explicit. A Subscriber receives a Subscription and calls request(n); requests add up, and the Publisher must never signal more onNext calls than the total requested (rule 1.1). A demand of Long.MAX_VALUE may be treated as effectively unbounded. TCP does the same with bytes: each segment advertises a window, the number of octets the receiver is currently prepared to accept, related to its free buffer space. When the window is zero the sender stops and periodically probes; zero-window probing must be supported. HTTP/2 applies a credit-based scheme per stream and per connection with WINDOW_UPDATE frames; only DATA frames are flow-controlled, and the initial window is 65,535 octets. The numbers in the sequence (16, then 8 at a time) are illustrative.

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

Backpressure only works if it reaches the source. In a pipeline, each stage must have a bounded buffer and stop asking for work when its own buffer is full, so a slow database slows the writer, then the transform, then ingest, then the gateway. At the edge there is nowhere left to push back, so the system sheds load: it rejects new work with a clear retry-later response (for example HTTP 503 with a retry hint; illustrative) rather than queueing it. Common traps: unbounded buffers in library defaults (Reactor's BUFFER overflow strategy, the default for Flux.create, is unbounded and may cause an OutOfMemoryError; RxJava's parameterless onBackpressureBuffer() reintroduces an unbounded buffer); deadlock when both sides block (gRPC's guide warns of it when client and server both read synchronously, or both write a lot without reading under manual flow control); drops nobody counts; and clients that retry rejections immediately.

Where it still goes wrong

  • Unbounded buffers hiding in library defaults
  • Both sides blocked, waiting on each other
  • Drops that nobody counts
  • Clients that retry a rejection at once

6 · Trade-offs

What it costs, when not to use it, and its main variants.

Every overflow strategy trades something. Blocking loses nothing but spreads the wait upstream. A bounded buffer absorbs bursts at the cost of delay. Dropping newest or oldest stays fast but loses data. Sampling or coalescing to the latest value suits state where only the current value matters. Shedding at the edge pushes the problem to clients, who need backoff. Scaling out consumers fixes the rate, but only if the bottleneck itself can scale. Libraries name these choices directly: RxJava's BackpressureStrategy has MISSING, ERROR, BUFFER, DROP and LATEST; Reactor's OverflowStrategy has IGNORE, ERROR, DROP, LATEST and BUFFER. It is unnecessary for plain synchronous request and response, where the caller already waits, and when every item must be kept from a source that never slows, a durable log that consumers pull from can be the buffer.

When the buffer is full

StrategyWhat it costs
Block the producerNothing lost; the wait spreads upstream
Bounded bufferAbsorbs bursts; adds delay

When not to use it

  • Plain request and response: the caller already waits
  • Every item must be kept and the source never slows: use a durable log
  • Short, predictable bursts: a modest bounded buffer may be enough
  • A consumer that is simply too slow: fix or scale it

7 · In the wild

Real implementations and where our own systems use it.

Reactive Streams is “an initiative to provide a standard for asynchronous stream processing with non-blocking back pressure”; its four interfaces are Publisher, Subscriber, Subscription and Processor, and JDK 9's java.util.concurrent.Flow interfaces are 1:1 semantically equivalent. Apache Pekko (a fork of Akka 2.6.x) Streams processes elements “using bounded buffer space” and implements the Reactive Streams protocol, which it describes as “dynamic push / pull”. Project Reactor is based on the Reactive Streams specification. RxJava's Flowable supports Reactive Streams and backpressure; Observable does not. gRPC is carried over HTTP/2 framing and its flow control (for streaming RPCs) relies on the underlying transport. Kafka consumers pull from brokers, so a consumer “simply falls behind and catches up when it can”, where a push system would overwhelm it. In Node.js, write() returns false once the buffer passes highWaterMark (default 16 KB, or 16 objects in object mode), and a 'drain' event signals when to resume; pipe() handles this automatically.

8 · Related patterns

What it is confused with or combined with.

Rate limiting caps traffic at a fixed rate agreed in advance; backpressure follows the consumer's live capacity. Load shedding is what backpressure becomes at the edge. Bulkheads bound resources per dependency, timeouts bound how long a blocked producer waits, and circuit breakers stop calls to a failing dependency rather than slowing them. Autoscaling raises the consumer's rate, while backpressure protects the system until the new capacity arrives.

9 · Recap

Three takeaways.

An unbounded queue hides a rate mismatch until it crashes. Bound every buffer and let the consumer signal demand, end to end. When a buffer fills anyway, choose on purpose: block, drop, sample, shed or scale, and measure it.

Recap

  • An unbounded queue hides a rate mismatch until it crashes
  • Bound every buffer; let the consumer signal demand, end to end
  • When full, choose on purpose: block, drop, sample, shed or scale
