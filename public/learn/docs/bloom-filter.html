Bloom filters

A few bits per item tell you an item is definitely not in a set, so you can skip the expensive lookup.

1 · The problem

What goes wrong without it, shown happening.

Many systems keep asking "have we seen this before?" against a set far too large for memory: does this storage file hold the key, has this URL been crawled, is this username taken? The answer lives on disk or behind a network call. When most of the questions are about things that are not in the set, nearly all of that expensive work comes back empty. A log-structured store makes this worse: a read for a missing key may have to check every file on disk before it can say not found.

2 · The naive fix

The obvious approach and why it breaks.

An in-memory hash set gives exact answers but stores every key in full, so memory grows with the data. Redis's documentation, for comparison, puts a set of IP addresses at around 40 bytes per item (illustrative: 100 million keys would need about 4 GB). Caching past misses only helps with keys that were already asked about; a key nobody has asked for yet still costs a full lookup.

3 · The pattern

Its parts and the role of each.

A Bloom filter trades exactness for space. It never stores the items, only bits derived from them.

PartJob
Bit array (m bits)All zero at the start; shared by every item
k hash functionsMap an item to k positions in the array
AddSet the k bits for the item to 1
QueryCheck the k bits: any 0 means definitely not; all 1 means probably yes

False positives are possible, because other items may have set all k bits. False negatives are not: an added item's bits are never cleared.

4 · How it works

The normal flow, step by step.

In a log-structured (LSM-tree) store, each immutable file carries its own filter, held in memory. Before reading a file, the read path asks the filter. A definitely not skips the file with no disk access; a probably reads the block as usual. The saving comes only from negative answers: for keys that exist, the filter adds a little hashing and saves nothing. Bigtable describes exactly this use, and RocksDB and Cassandra do the same per SST file or SSTable.

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

False positives. A key that is absent but whose bits were all set by other keys gets a probably; the store reads the block, finds nothing, and correctly returns not found. Correctness holds as long as every probably is checked against the real data; the cost is a wasted read.

Overfilling. A filter is sized for an expected number of items. Beyond that, more bits are set and the false-positive rate climbs: from the standard approximation p ≈ (1 − e−kn/m)k, a filter sized for 1% (9.6 bits per item, 7 hashes) gives about 16% at twice its planned items and about 44% at three times. Fixes: rebuild a larger filter from the source of truth, rotate filters (Akamai used a primary and a secondary filter), or use a scalable filter that adds larger sub-filters as it fills, as Redis does by default.

No deletion. Clearing an item's bits may clear bits other items rely on, creating false negatives. Counting Bloom filters replace each bit with a small counter; cuckoo filters store fingerprints and support deletion directly.

6 · Trade-offs

What it costs, when not to use it, and its main variants.

Sizing uses two standard formulas: bits per item = −ln(p) / (ln 2)², and the best number of hash functions k ≈ (m/n) · ln 2. That gives about 9.6 bits and 7 hashes for 1%, 14.4 bits and 10 hashes for 0.1%, and 19.2 bits and 14 hashes for 0.01%. Each extra ~4.8 bits per item cuts the false-positive rate tenfold. Do not use a filter when most lookups find a match (it adds work and saves none), when you need exact answers without a backing lookup, or when items must be deleted and you cannot afford a counting or cuckoo filter. RocksDB also offers a Ribbon filter that saves about 30% of the space for 3–4× the CPU.

7 · In the wild

Real implementations and where our own systems use it.

Burton H. Bloom introduced the structure in "Space/Time Trade-offs in Hash Coding with Allowable Errors", Communications of the ACM 13(7), 1970. Google's Bigtable paper (OSDI 2006) lets clients create Bloom filters for SSTables in a locality group, so most lookups for non-existent rows or columns do not touch disk. RocksDB puts a filter in every SST file; about 10 bits per key gives roughly 1%. Apache Cassandra exposes bloom_filter_fp_chance per table (default 0.01, or 0.1 with leveled compaction). Akamai used Bloom filters to cache objects only on their second request, avoiding one-hit wonders. Redis provides filters through BF.RESERVE, BF.ADD and BF.EXISTS. Fan, Andersen, Kaminsky and Mitzenmacher's cuckoo filter (CoNEXT 2014) adds deletion.

8 · Related patterns

What it is confused with or combined with.

With cache-aside, a filter can skip cache and database lookups for keys that exist nowhere, and a cache can admit only items it has seen before. LSM-tree storage, which pairs a write-ahead log with sorted immutable files, is the classic home: one filter per file. Consistent hashing decides which server owns a key; a filter decides whether asking is worthwhile. HyperLogLog is a sibling sketch that estimates how many distinct items there are rather than testing membership.

Related patterns

  • Cache-aside: skip lookups for keys that exist nowhere
  • Cache admission: store only items seen before
  • LSM-tree storage and write-ahead logs: one filter per file
  • Consistent hashing: which server, not whether it exists
  • HyperLogLog: counts distinct items instead

9 · Recap

Three takeaways.

Definitely not, or probably yes, in a few bits per item. It pays off when most lookups miss, and every yes must be checked. Size it for growth, about 10 bits per item for 1%, and rebuild as it fills.

Recap

  • Definitely not, or probably yes, in a few bits per item
  • Pays off when most lookups miss; always check a yes
  • About 10 bits per item for 1%; rebuild as it fills
