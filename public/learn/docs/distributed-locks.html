Distributed locks

Let only one worker at a time touch a shared resource across machines: a shared, owned, expiring lock, plus fencing tokens when correctness is at stake.

1 · The problem

What goes wrong without it, shown happening.

Two workers on different machines take the same job, perhaps because the queue delivered it twice or a user clicked twice. Both read version 1 of report 42, both build a version 2, and the second write silently replaces the first. No error is raised; an update is simply lost. With an account balance or a file instead of a report, the result is a wrong balance or a corrupted file.

2 · The naive fix

The obvious approach and why it breaks.

A mutex or synchronized block only excludes threads in the same process. Each machine has its own, so each worker is granted its own lock and the race is unchanged. To exclude another machine, the lock must live in a place every machine can see.

3 · The pattern

Its parts and the role of each.

A distributed lock is a record in a shared service, keyed by the resource being protected.

PartJob
Lock keyNamed after the resource; exists only while someone holds the lock
Owner valueA random, unguessable string per acquisition, so only the owner can release it
Lease (expiry)The key expires on its own, so a crashed holder cannot block others for ever
Fencing counterA number that rises on every grant, for locks that protect correctness
The resourceChecks the fencing token on every write and rejects stale ones

4 · How it works

The normal flow, step by step.

With a single Redis node, acquire with SET resource_name my_random_value NX PX 30000: set only if the key does not exist, expiring after 30,000 ms. A nil reply means another client holds it; retry after a random delay. Release by deleting the key only if its value still matches, with a short Lua script or, from Redis 8.4, DELEX key IFEQ value. Plain DEL is unsafe: a client whose lease ran out would delete the next holder's lock.

Why each part matters

WithoutWhat goes wrong
NXEveryone "acquires" by overwriting the key
An expiryA crashed holder blocks the resource for ever
A random owner valueA slow holder deletes the next holder's lock
Setting both in one commandA crash between them leaves a lock that never expires

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

A lease can expire while its holder is paused, by garbage collection, a stalled VM or a slow network, and still believes it holds the lock. Kleppmann notes this happened in HBase. The owner value keeps the paused client from releasing the new holder's lock, but not from writing to the data. The remedy is a fencing token: a number that increases on every grant, sent with every write, and checked by the resource, which rejects any token lower than one it has already seen. Chubby's sequencers (2006) are the same idea.

Other ways to get two holders: Redis replication is asynchronous, so a primary may grant the lock and crash before the replica has it; Redis expiry is not based on a monotonic clock, so a clock jump can expire a key early; and a node that restarts without the key persisted forgets the lock. Long-running work must extend the lease or stay well within it.

Other ways two holders appear

  • Primary fails before replicating the key; the replica grants it again
  • A clock jump makes a key expire early
  • A lock node restarts without the key on disk
  • Work outlives the lease: renew it, or keep work short

6 · Trade-offs

What it costs, when not to use it, and its main variants.

Kleppmann's distinction comes first. An efficiency lock avoids doing work twice; an occasional failure costs a little duplicated effort, and a single Redis node is enough. A correctness lock protects data; a failure means corruption or loss. For that he recommends a consensus system such as ZooKeeper and fencing tokens enforced on every access.

Redlock runs the same SET on N independent Redis masters (5 in the docs) and treats the lock as acquired only on a majority (at least 3) within the validity time, minus the time spent acquiring. Kleppmann argued it cannot produce fencing tokens and depends on timing assumptions, calling it “neither fish nor fowl”. Antirez's reply, “Is Redlock safe?”, accepted using monotonic clocks but disputed the rest. The Redis page links both and advises fencing tokens for consistency-sensitive use.

Often the better answer is no lock service at all: optimistic concurrency (a version column and compare-and-set), a database row lock (SELECT … FOR UPDATE) or PostgreSQL advisory lock when the data lives in one database, or making the operation idempotent.

7 · In the wild

Real implementations and where our own systems use it.

Redis documents the single-instance lock on the SET page and Redlock on its distributed locks page, with client libraries in many languages. ZooKeeper's lock recipe creates an ephemeral sequential node; the lowest sequence number holds the lock, and each waiter watches only the next-lowest node to avoid a herd effect. etcd's Go client offers concurrency.Mutex, bound to a Session whose lease defaults to a 60-second TTL. PostgreSQL offers advisory locks at session or transaction level (pg_advisory_lock, pg_advisory_xact_lock, pg_try_advisory_lock). Google's Chubby (Mike Burrows, OSDI 2006) is a coarse-grained lock service built on Paxos, with sequencers and a lock-delay for servers that cannot check them.

8 · Related patterns

What it is confused with or combined with.

Leader election uses the same machinery for a long-held role rather than one operation. Timeouts and leases free a dead holder. Optimistic concurrency and database locks often replace a distributed lock. Idempotency makes the rare duplicate harmless. Two-phase commit holds locks across several resources while participants agree.

9 · Recap

Three takeaways.

Share the lock, own it with a secret, and let it expire. A lease can end while the holder still thinks it owns it. For correctness, fence at the resource, or design the lock away.

Recap

  • Share the lock, own it with a secret, and let it expire
  • A lease can end while the holder still thinks it owns it
  • For correctness, fence at the resource, or avoid the lock
