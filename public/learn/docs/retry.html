Retry with backoff and jitter

Retry faults that fix themselves, wait longer and a little randomly each time, and know when to stop.

1 · The problem

What goes wrong without it, shown happening.

Remote calls fail for reasons that clear up on their own: a reset connection, a database failover, a timeout while a service is busy, a 503 or a 429. Without a retry, every one of these brief, transient faults becomes an error the user sees, although trying again a moment later would have worked. Other faults are persistent (bad input, no permission, not found) and give the same answer every time; retrying those only adds load.

2 · The naive fix

The obvious approach and why it breaks.

The obvious fix is to retry straight away, in a loop. When many clients fail at the same moment (because the same dependency blipped for all of them), they all retry at the same moment too, and the recovering service receives a synchronised wave of traffic that knocks it over again. Retrying at every layer makes it worse: the Amazon Builders' Library notes that five layers each retrying three times multiply the load on the bottom service 243×, and recommends retrying at a single point in the stack.

3 · The pattern

Its parts and the role of each.

A retry policy wraps one remote call and decides, for each failure, whether to try again and when.

PartJob
TimeoutTurns a slow attempt into a failed one, so there is something to retry
ClassifierRetries only transient errors, and only operations that are safe to repeat
Attempt limitA small total number of attempts
Retry budgetA token bucket shared by a client: retries spend tokens, successes earn them back; when it is empty, fail fast
BackoffWait min(cap, base × 2ⁿ) before attempt n
JitterRandomise the wait so clients spread out

Marc Brooker's 2015 AWS post compares the variants: full jitter sleeps random(0, min(cap, base × 2ⁿ)); equal jitter keeps half of that and randomises the other half; decorrelated jitter sleeps min(cap, random(base, last sleep × 3)). Un-jittered backoff was the clear loser; equal jitter did slightly more work than full jitter and took much longer; full jitter did the least work, decorrelated took slightly less time.

4 · How it works

The normal flow, step by step.

The sequence charges a payment with an idempotency key. The first attempt succeeds at the server but the reply is lost, so the client sees a timeout. Because the error is transient and the request carries a key, the policy sleeps a random time below its first ceiling and retries with the same key; a 503 doubles the ceiling; the third attempt returns the result the server saved for that key, so the customer is charged once. The 100 ms base and the £20 charge are illustrative. Stripe, for example, saves the status code and body of the first request made with a key and returns it for retries with the same key.

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

Two signals mean wait longer, or stop. When a 429 or 503 carries a Retry-After header (a number of seconds or an HTTP date), honour it instead of your own backoff. When an outage is real, most retries fail and only add load: a retry budget empties and the client fails fast, and if a circuit breaker has opened, retries must not go around it. Writes are the other danger: a lost reply is not a failed write, so retrying a non-idempotent call can do it twice unless it carries an idempotency key.

6 · Trade-offs

What it costs, when not to use it, and its main variants.

More attempts rescue more requests but add latency and load; interactive requests should give up sooner than batch jobs. A short base delay recovers quickly from blips; a long cap spares a struggling service. A budget fails fast in outages at the cost of a few requests it might have saved. Do not retry persistent errors, non-idempotent writes without a key, or long outages (the circuit breaker's job), and do not use retries to hide a service that is simply too small for its traffic.

The knobs

ChoiceTrade-off
More attemptsMore successes; longer waits and more load
Base delay and capShort recovers fast; long spares the service
Where to retryOne layer only, or the load multiplies
Retry budgetFails fast in outages; fewer rescues in a bad minute

When not to retry

  • Persistent errors: bad input, no permission, not found
  • Writes that are not idempotent and have no idempotency key
  • Long outages: that is the circuit breaker's job
  • Constant throttling: scale the service or slow the client

7 · In the wild

Real implementations and where our own systems use it.

Brooker's post (May 2023 update: “a pillar for how Amazon builds remote client libraries”) and the Builders' Library article shaped the AWS SDKs. Their standard retry mode uses exponential backoff with full jitter plus a retry quota (a token bucket); adaptive mode adds a client-side rate limiter that can delay even the first request, and AWS does not recommend it as a general default. AWS's updated retry behaviour (opt-in as of October 2026) documents 3 attempts by default, a 50 ms base for transient errors and 1,000 ms for throttling, a 20-second cap and a 500-token budget. gRPC configures maxAttempts, initialBackoff, maxBackoff, backoffMultiplier and retryableStatusCodes, applies ±20% jitter, and pauses retries when its throttling token count falls below half. Google Cloud Storage classifies operations as idempotent, conditionally idempotent or never idempotent, and Stripe accepts an Idempotency-Key header on POST requests.

8 · Related patterns

What it is confused with or combined with.

A timeout decides an attempt has failed. An idempotency key makes retrying a write safe. A circuit breaker handles faults that last, and retries stop while it is open. Rate limiting with Retry-After tells the client how long to wait. Hedged requests send a second copy before the first fails, to cut tail latency rather than to recover from errors. A queue with a dead-letter retries work that can wait, outside the request path.

9 · Recap

Three takeaways.

Retry only transient faults and safe operations. Back off exponentially with a cap, and add jitter. Retry in one layer, within a budget, and stop when the server or the breaker says so.

Recap

  • Retry only transient faults, and only safe operations
  • Back off exponentially, with a cap, and add jitter
  • Retry in one layer, within a budget; stop when the breaker opens
