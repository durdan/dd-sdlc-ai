Change data capture

Read the change log the database already keeps and turn every committed insert, update and delete into an ordered event, so search indexes, caches and warehouses follow the source of truth within seconds.

1 · The problem

What goes wrong without it, shown happening.

The same data rarely lives in one place. A products database is the source of truth, but search runs on an index, hot reads come from a cache, and reports come from an analytics warehouse. If those copies are refreshed by a nightly export, every one of them is up to a day stale: a price changed at nine in the morning is still wrong in search at five in the afternoon. The copies drift, and nothing reports it.

2 · The naive fix

The obvious approach and why it breaks.

Polling with WHERE updated_at > :last is the first fix. It cannot see deletes, because a deleted row has nothing left to query; it collapses several changes between polls into the final state; it depends on every writer setting the timestamp; and each poll is extra load on the primary database. Dual writes from the application, updating the database and then the index and the cache, are not atomic: a timeout after the commit leaves them disagreeing, concurrent requests can apply in different orders, and any change that bypasses the service (a migration, a manual fix) is never copied. Debezium's documentation contrasts log-based capture with exactly these two approaches.

Or write to every copy from the app?

3 · The pattern

Its parts and the role of each.

Every transactional database already records each committed change, in commit order, in a log it uses for durability and replication. Change data capture reads that log and publishes each row change as an event. The application is unchanged.

PartJob
Change logPostgreSQL write-ahead log, read through logical decoding; MySQL binary log in row format
PositionA PostgreSQL replication slot or a MySQL binlog file and offset: how far the reader has got
ConnectorDecodes the log into change events (e.g. Debezium); takes the initial snapshot
Event streamBy default one topic per table, keyed by primary key, so each row's changes stay in order
ConsumersOne per copy: search indexer, cache invalidator, warehouse loader

4 · How it works

The normal flow, step by step.

A new copy needs existing data, and the log does not hold the full history, so the connector starts with a snapshot. Debezium's PostgreSQL connector takes a consistent snapshot on first connect, emitting each row as an event with op: r (read), then streams from exactly the point at which the snapshot was made. From then on each change is an event with op c, u or d, the row's before and after state, and a key equal to the primary key. A delete is followed by a tombstone (same key, null value) so a log-compacted topic can drop the row entirely. Debezium also supports incremental snapshots that can be triggered while the connector runs. Netflix's DBLog paper describes a related approach that interleaves chunked selects with log events using watermarks, without table locks.

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

A stopped consumer can fill the disk. PostgreSQL replication slots persist across crashes and know nothing about the state of their consumers; they prevent removal of WAL the slot still needs, even when nothing is connected. The documentation warns that slots can retain so many WAL segments that they fill the space allocated for pg_wal. max_slot_wal_keep_size caps this (the default, -1, is unlimited), but a slot that falls further behind may lose required WAL and become unusable (wal_status = lost). Alert on slot lag, and drop slots you no longer need. Debezium also notes that a busy server whose captured tables are quiet can accumulate WAL; heartbeats fix that.

Replays. A logical slot's position is persisted only at checkpoint, so after a crash recent changes can be sent again, and PostgreSQL makes clients responsible for handling duplicates. Debezium delivers exactly once in normal operation but at least once while recovering from a fault. Consumers must be idempotent: apply the latest row state by key.

Other edges. PostgreSQL logical decoding does not support DDL, so the PostgreSQL connector cannot report schema changes as events; the MySQL connector keeps a schema history topic for this. Updating a primary key produces a delete and tombstone for the old key, then an event for the new key. Ordering is per key, not across keys.

Other sharp edges

  • Schema changes: logical decoding does not carry DDL
  • Primary key update: delete and tombstone, then a new key
  • Order holds per key, not across keys
  • Quiet tables on a busy server: use heartbeats
  • Cap retention: max_slot_wal_keep_size, at a price

6 · Trade-offs

What it costs, when not to use it, and its main variants.

Raw CDC captures everything, including changes made outside the application, with no code change, but consumers become coupled to internal table design. The transactional outbox instead writes explicit events into an outbox table in the same transaction; CDC is then a good relay for it. Use raw CDC to keep copies of your own data fresh; use an outbox for events other teams rely on.

Costs: a connector (and usually a stream) to operate; database configuration (logical decoding in PostgreSQL; MySQL's binlog_format=ROW, the default, and Debezium also requires binlog_row_image=FULL); replication privileges; copies that are eventually consistent. Debezium quotes millisecond-range delay for MySQL and PostgreSQL; AWS DMS states its CDC is not real-time and latency can reach minutes. If a nightly batch is fresh enough, it is simpler.

Raw CDC or an outbox?

Raw table CDCTransactional outbox
Captures every change, even by handOnly what the code chooses to publish
Events mirror internal tablesEvents are an explicit contract
No change to the applicationThe service writes an outbox row
Best for copies of the same dataBest for telling other domains

What it costs

  • A connector and a stream to run and monitor
  • Database setup: logical WAL, or binlog in row format
  • Replication privileges and a slot per connector
  • Copies are eventually consistent, not instant
  • Skip it when one nightly batch is good enough

7 · In the wild

Real implementations and where our own systems use it.

Debezium is the common open-source implementation: connectors run on Kafka Connect, in Debezium Server, or embedded via the Debezium engine. Its PostgreSQL connector uses logical decoding (the standard pgoutput plug-in, PostgreSQL 10+), and its MySQL connector requires a row-format binlog. AWS DMS offers full load plus CDC, reading MySQL's row-based binlog and using logical replication slots with test_decoding on PostgreSQL. Netflix DBLog (Andreakis and Papapanagiotou, 2020) is a watermark-based CDC framework used in production at Netflix; its paper lists Databus and Debezium among the offerings it evaluated. LinkedIn Databus was published at ACM SoCC 2012 (“All aboard the Databus!”).

8 · Related patterns

What it is confused with or combined with.

CDC is built on the database's write-ahead log. It is often the relay for a transactional outbox. It publishes into event streaming, and is a common way to keep CQRS read models up to date. Because delivery is at least once, its consumers are idempotent consumers.

9 · Recap

Three takeaways.

Don't poll or dual-write: read the database's own log. Snapshot once, then stream ordered events per key. Watch slot lag, and make every consumer idempotent.

Recap

  • Don't poll or dual-write: read the database's own log
  • Snapshot once, then stream ordered events per key
  • Watch the slot, and make every consumer idempotent
