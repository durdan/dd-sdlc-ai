Strangler fig

Replace a legacy system one slice at a time behind a routing facade, keep every step reversible, and finish by switching the old system off.

1 · The problem

What goes wrong without it, shown happening.

Long-lived systems accumulate coupling. In the example, an order-management monolith runs orders, stock, returns and invoicing as one deployable over one shared database, and modules reach into each other's tables and internals. A change to one capability means retesting and redeploying all of them, so releases slow down and the business waits. AWS's guidance lists the same symptoms: changes cannot be tested in isolation, the whole application must be scaled together, and ageing technology drives up support costs.

2 · The naive fix

The obvious approach and why it breaks.

The obvious answer is a complete rewrite followed by a single cut-over. It rarely goes to plan. The business cannot wait years for new features, so changes land in the old system and then have to be repeated in the rewrite. Much of the old behaviour is undocumented and has to be rediscovered. The cut-over is one large, risky event, and rolling back is hard once data has moved. Martin Fowler writes that he and his colleagues have seen this “simple-sounding plan go down in flames most of the time”; AWS notes that during a big-bang migration it is “extremely hard or even impossible to add new features”.

3 · The pattern

Its parts and the role of each.

Put a facade in front of the legacy system, then move one capability at a time to new services behind it. Clients keep calling the same addresses; the facade decides, per request, which system answers.

PartJob
Facade (router)A reverse proxy or API gateway in front of everything. Starts by sending all traffic to the legacy system.
Routing rulesChoose old or new by path, by user cohort, or by percentage, often driven by feature flags.
New servicesEach owns one slice: a set of URLs, events or a bounded context, with its own data.
Anti-corruption layerLets new and old call each other while translating between their models.
Sync agentKeeps data the other side still needs in step, by change data capture or events.
Legacy systemKeeps serving everything not yet moved, and shrinks until it can be decommissioned.

The facade, the translation layer and the sync are transitional architecture: built to be removed once the migration is done.

4 · How it works

The normal flow, step by step.

A request that matches no rule goes to the monolith, unchanged. A request that matches a migrated slice goes to the new service, which may still read from the monolith through the translation layer. Each slice moves gradually: shadow traffic (dark launching) first, comparing results without serving them; then a flag for staff, then a small cohort of customers, then everyone, with the flag as an instant way back. Only then is the legacy code for that slice deleted.

Microsoft describes four phases for the whole migration: the facade routes most requests to the legacy system; it shifts requests to the new system slice by slice; when nothing depends on the legacy system it is decommissioned; finally the facade is removed and clients call the new system directly (or the facade is kept deliberately as an adapter for legacy clients).

Four phases to the finish

  • The facade sends most requests to the old system
  • Slice by slice, it shifts requests to the new one
  • Nothing depends on the old system: decommission it
  • Remove the facade; clients call the new system directly

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

Data. While both systems run, both may need the same data. Writing every change to two databases from application code (a dual write) is not atomic: one write can fail, or time out after succeeding, and the stores drift apart silently. Prefer one system of record per slice and carry changes across asynchronously, by change data capture or published events, accepting eventual consistency; then reconcile the two stores. Microsoft's database example copies the data with ETL, keeps it in step with change data capture, validates consistency, and only then cuts over; rollback stays possible until the legacy objects are removed. AWS's example uses a queue and a synchronising agent to keep the monolith's database eventually consistent, and calls this a tactical solution. Shopify's dual writes worked because both tables were in the same database and the writes shared a transaction.

The facade. Every request now passes through it, so Microsoft and AWS both warn it can become a single point of failure or a performance bottleneck, and it must keep up with the migration. Run it highly available, test and version its rules, and watch the latency it adds.

6 · Trade-offs

What it costs, when not to use it, and its main variants.

It buys steady delivery, small reversible steps and early learning, at the price of temporary code, running two systems for a long time, and data synchronisation. The common failure is stalling with the hard core still in the monolith. Microsoft lists when it may not suit: requests to the back end cannot be intercepted; you cannot change the legacy source code to redirect internal calls; the system is small and simple to replace whole; or the old system must be decommissioned quickly. AWS adds that premature decomposition is costly when the domain is not clear.

What you gain, what you pay

GainCost
Value ships every few weeksTransitional code you will throw away
Roll back one slice in secondsTwo systems to run, patch and pay for
Learn the real behaviour as you goData kept in step between stores
Features keep flowingRisk of stalling at eighty percent

When not to use it

  • Requests to the old system cannot be intercepted
  • You cannot change the legacy source code
  • The system is small: replace it whole
  • The old system must be switched off quickly

7 · In the wild

Real implementations and where our own systems use it.

Martin Fowler described the idea as “Strangler Application” on 29 June 2004, and rewrote it as “Strangler Fig Application” on 22 August 2024, naming it after the strangler figs he saw in Queensland's rain forests in 2001. Ian Cartwright, Rob Horn and James Lewis's Patterns of Legacy Displacement (2024) catalogue supporting moves such as Event Interception, Legacy Mimic, Dark Launching, Canary Release and Transitional Architecture. Microsoft's Azure Architecture Center and AWS Prescriptive Guidance both document the pattern; AWS's implementation uses Amazon API Gateway as the proxy (via Migration Hub Refactor Spaces, which closed to new customers on 7 November 2025). Shopify applied it inside its Rails monolith in 2020 to move a settings column off the Shop model: new interface, redirect callers, new table, dual writes, backfill, switch reads, then delete the old column.

8 · Related patterns

What it is confused with or combined with.

An API gateway is often the facade itself. The anti-corruption layer lets old and new call each other without the new code adopting legacy semantics. Feature flags steer cohorts and percentages and give instant rollback. Branch by abstraction applies the same incremental replacement inside a single codebase. Dark launching and canary releases exercise the new path safely. Change data capture keeps data in step during coexistence. Contract tests check that the new service still honours the contract the old one offered.

9 · Recap

Three takeaways.

Never stop the world: replace one slice at a time behind a facade. Keep every step reversible. Plan the data and the finish: delete the old code, the old system, and then the facade.

Recap

  • Never stop the world: replace one slice at a time
  • Keep every step reversible: shadow, small cohorts, a flag
  • Plan the data and the finish: delete the old system, then the facade
