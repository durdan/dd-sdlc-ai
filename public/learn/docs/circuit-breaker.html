Circuit breaker

Stop calling a dependency that is failing, answer from a fallback, and test it carefully before trusting it again.

1 · The problem

What goes wrong without it, shown happening.

Services call each other with a fixed number of threads or connections. When a dependency fails fast, callers get an error and move on. When it gets slow, every caller holds a thread while it waits. The pool drains, and requests that never touch the slow service start failing too. This is a cascading failure: one slow dependency takes down everything upstream of it.

2 · The naive fix

The obvious approach and why it breaks.

Retrying looks like resilience but multiplies load on the service least able to take it. If each layer retries independently, the load grows multiplicatively: AWS's Builders' Library gives five layers retrying three times each as a 243× increase at the bottom. Shorter timeouts help free threads sooner, but on their own they still send every request to a service that is failing.

3 · The pattern

Its parts and the role of each.

A circuit breaker is a proxy around calls to one dependency. It records recent outcomes and, when the failure rate crosses a threshold, stops making the call for a while and returns a fallback straight away. After a wait it lets a few trial calls through, and closes again if they succeed.

4 · How it works

The normal flow, step by step.

The sequence uses Resilience4j's documented defaults as concrete numbers: failure-rate threshold 50%, sliding window of 100 calls (count-based by default), minimum 100 calls before the rate is evaluated, 60 seconds open, 10 permitted calls in half-open. Slow calls can count as failures too (slow-call threshold, 60 s by default).

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

The half-open state protects a recovering service from a sudden flood: only a limited number of trial calls pass, and a single failure reopens the breaker and restarts the timer. Some implementations lengthen the wait on each reopen. Microsoft's guidance adds manual override (force open or closed), health-endpoint probing instead of a timer, and separate breakers per shard so a single bad shard does not block healthy ones.

Where it still goes wrong

  • A long timeout ties up threads before the breaker trips
  • One breaker over many shards blocks the healthy ones
  • Retries that ignore an open breaker bypass it
  • A fallback the user cannot accept is just a different failure

6 · Trade-offs

What it costs, when not to use it, and its main variants.

Use it for remote calls whose failures can last long enough to matter. It is the wrong tool for in-process work, as a replacement for business error handling, or where a queue's dead-letter handling or the platform (load balancer, service mesh) already isolates the failure.

The knobs

ChoiceTrade-off
Count or time windowLast N calls, or last N seconds for uneven traffic
Failure thresholdLow trips on noise; high trips late
Open waitShort probes too often; long keeps users on the fallback
Library or proxyLibrary knows the error; proxy needs no code

When not to use it

  • Local, in-memory resources: only overhead
  • Instead of handling errors in business logic
  • Message-driven flows with a dead-letter queue
  • When the load balancer or mesh already does it

7 · In the wild

Real implementations and where our own systems use it.

Michael Nygard popularised the pattern in Release It!; Martin Fowler's 2014 article describes the closed, open and half-open states. Netflix's Hystrix is in maintenance mode, and Netflix recommends Resilience4j for new projects. Polly brings the same strategy to .NET. Envoy applies circuit breaking at the proxy as per-cluster limits (connections, pending requests, requests, retries), and separately ejects misbehaving hosts through outlier detection.

8 · Related patterns

What it is confused with or combined with.

The breaker rarely works alone. Timeouts produce the failures it counts. Retries with backoff and jitter handle brief faults and should go through it and stop when it is open. Bulkheads stop one dependency from taking every thread. Fallbacks decide what the user sees. Health endpoint monitoring can decide when to test again.

9 · Recap

Three takeaways.

Slow is worse than down. Stop calling what is failing. Test before trusting it again.

Recap

  • Slow is worse than down: it holds your threads
  • Stop calling what is failing; answer from a fallback
  • Test before trusting again: half-open, then close
