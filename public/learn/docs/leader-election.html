Leader election

Let exactly one replica do the work: hold leadership as a renewable lease, agree it by majority, and fence off the old leader when it comes back.

1 · The problem

What goes wrong without it, shown happening.

We run several identical replicas of a service so that one crash does not stop it. That is fine for requests, which any replica can answer. It is wrong for work that must happen once: a nightly billing run, sending reminder emails, compacting a table. With no coordination, every replica's timer fires and the job runs once per replica, so customers are charged and emailed several times. The replicas are peers, so there is no natural leader to decide.

2 · The naive fix

The obvious approach and why it breaks.

A lock row in the database stops duplicates until its holder crashes without releasing it: the row stays locked by a process that no longer exists, and the job stops running altogether. “Lowest id wins” fails the other way. When the network splits, a replica that cannot reach the lowest id assumes it is dead and takes over, while the original is still running. Both act as leader: split brain. A replica cannot tell a dead peer from an unreachable one; it only sees silence.

3 · The pattern

Its parts and the role of each.

Replicas compete for leadership held as a lease: a record with a holder and an expiry, kept in a coordination service that itself stays correct through failures by agreeing every change with a majority of its nodes. The leader renews the lease before it expires; followers watch it and take over once it lapses.

4 · How it works

The normal flow, step by step.

The lease sequence uses Kubernetes client-go's documented defaults for core clients: a 15-second lease duration, a 10-second renew deadline for the acting leader, and a 2-second retry period. Token numbers 33 and 34 follow Kleppmann's example.

Inside the coordination service, Raft elects a leader per numbered term. A follower that hears no heartbeat within its randomised election timeout (the paper suggests 150–300 ms) becomes a candidate, starts a new term and requests votes. Each server votes for at most one candidate per term, first come first served, and a candidate needs votes from a majority of the full cluster, so at most one leader is elected per term.

ZooKeeper's recipe uses ephemeral sequential znodes: the smallest sequence number leads, and each candidate watches only the next lower node, which avoids the herd effect. etcd's election API (Campaign, Proclaim, Leader, Observe, Resign) ties leadership to a lease; if the lease expires or is revoked, leadership passes to the next campaigner.

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

A lease alone is not enough. Kleppmann's example: a client holding a lock with token 33 is paused (for instance by garbage collection), its lease expires, another client gets token 34 and writes; when the first client resumes it writes too. With fencing, the storage remembers it has processed token 34 and rejects 33. ZooKeeper's zxid or znode version can serve as the token; etcd's leader key carries a creation revision that can be checked in transactions. Raft's terms play the same role between its own servers: a request with a stale term is rejected, and a leader that sees a higher term reverts to follower. Kubernetes client-go states that it does not guarantee only one client acts as leader (fencing), so the protected resource has to check.

6 · Trade-offs

What it costs, when not to use it, and its main variants.

Consensus needs a majority: quorum is n/2+1, so three nodes tolerate one failure and five tolerate two. Adding a member to reach an even size buys no extra fault tolerance, hence odd sizes. Lease length trades failover speed against false failovers caused by pauses and slow networks. A single leader is simple but can become a bottleneck, and there is a gap while a new one is elected. Microsoft's guidance: you may not need the pattern if there is a natural leader or singleton process, if optimistic or pessimistic locking on the shared resource is enough, or if a third-party solution such as ZooKeeper fits better.

7 · In the wild

Real implementations and where our own systems use it.

The Raft paper (Diego Ongaro and John Ousterhout) appeared at the 2014 USENIX Annual Technical Conference, where it won a Best Paper Award. etcd is built on Raft and offers an election API. Kubernetes uses Lease objects in coordination.k8s.io for node heartbeats and for leader election of kube-controller-manager and kube-scheduler in highly available control planes; client-go's leaderelection package provides the client side, with a leases resource lock. ZooKeeper documents a leader election recipe. Microsoft's Leader Election pattern page uses an Azure Blob Storage lease as a distributed mutex. Martin Kleppmann's 2016 post “How to do distributed locking” explains fencing tokens.

8 · Related patterns

What it is confused with or combined with.

A distributed lock is the same machinery held for one operation. A timeout is how a dead leader is detected; a lease is a timeout on leadership. Idempotency is the backstop that makes an overlapping run harmless. Sharding scales the pattern out with one leader per shard, and consistent hashing can assign work to owners without any leader.

9 · Recap

Three takeaways.

Leadership is a lease: renew it or lose it. Silence is not death: fence the old leader with a token that only goes up. Let a majority decide, on an odd number of nodes.

Recap

  • Leadership is a lease: renew it or lose it
  • Silence is not death: fence the old leader with a token
  • Elect by majority, on an odd number of nodes
