Transactional outbox

Write the event into an outbox table in the same local transaction as the change, and let a separate relay publish it: at least once, never lost.

1 · The problem

What goes wrong without it, shown happening.

A service that changes its database and then tells other services about it by publishing to a message broker is making two writes to two systems, with no transaction spanning both. This is the dual-write problem. If the service crashes, the network fails or the broker is down between the two, the database and the rest of the system disagree: an order exists that nobody ships, or an event announces a change that was rolled back. Nothing reports an error; the inconsistency is silent.

Two writes, four outcomes

What happenedWhat the business sees
Both succeedConsistent
Saved, publish lostAn order nobody ships
Published, save rolled backShipping an order that does not exist
Publish timed out, but arrivedUnknown; a retry may send it twice

2 · The naive fix

The obvious approach and why it breaks.

Moving the publish inside the database transaction swaps one failure for the other: the message is delivered, then the commit fails, and consumers act on data that never existed. A broker message cannot be rolled back once delivered. A distributed transaction (two-phase commit, for example through X/Open XA) could in principle span both, but the database or broker may not support it, it couples the service to both being available at once, and 2PC is a blocking protocol: participants hold locks until the coordinator's decision arrives. microservices.io treats it as not viable for this problem.

Why not a distributed transaction?

  • Two-phase commit (XA) could span database and broker
  • The broker or database may not support it
  • It couples the service to both being up at once
  • Locks are held while a coordinator waits

3 · The pattern

Its parts and the role of each.

Instead of publishing, the service inserts the event as a row in an outbox table in the same database, inside the same local transaction as the business change. The two commit or roll back together. A separate message relay reads committed outbox rows and publishes them to the broker.

PartJob
Business tablesThe change itself, e.g. the new order
Outbox tableOne row per event: id, aggregate type, aggregate id, event type, payload
Local transactionMakes the change and the event atomic, with no broker involved
Message relayPolls the table or tails the transaction log, publishes, then marks or deletes the row
BrokerDelivers to consumers, ideally keyed by aggregate id
Idempotent consumer / inboxRecords processed event ids so duplicates are skipped

4 · How it works

The normal flow, step by step.

The request path only touches the database: begin, insert the order and the outbox row, commit, reply. Later, the relay fetches unsent rows oldest first, publishes each with the aggregate id as the message key, waits for the broker's acknowledgement, and then marks the row sent (or deletes it). If the broker is unavailable the rows wait in the table. The row and order numbers in the walkthrough are illustrative.

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

If the relay crashes after publishing but before recording that it did, it publishes the row again on restart. The pattern therefore gives at-least-once delivery, and consumers must be idempotent. The usual technique is to record each processed message id in the consumer's database in the same transaction as its own work; Microsoft calls this transactional variant the Inbox pattern, the consumer-side companion to the outbox. A unique constraint on the id makes the database reject the second copy.

Ordering matters too: order created must not arrive after order cancelled. Publishing in order is tricky with a polling publisher. Keying messages by aggregate id keeps one aggregate's events together: Debezium uses the aggregate id as the Kafka message key for partition ordering, AWS's sample uses it as the SQS FIFO message group id, and Microsoft's sample uses Service Bus sessions. Watch the outbox's backlog and age, since a stopped relay fails silently. And the pattern is only as good as the discipline of writing an event for every change.

Where it still goes wrong

  • Out of order: key messages by aggregate id
  • Several relays racing over the same rows
  • Relay stopped: the outbox quietly grows
  • A developer forgets to write the event

6 · Trade-offs

What it costs, when not to use it, and its main variants.

A polling publisher works with any SQL database and is easy to build, but adds query load, its latency is the poll interval, and ordering is tricky. Transaction log tailing (change data capture) reads the database's log, such as the Postgres write-ahead log or MySQL binlog, with low overhead in near real time, but needs database-specific tooling, and microservices.io notes it is still tricky to avoid duplicates.

Clean-up is part of the design. AWS's sample deletes rows once SQS accepts them. Microsoft's Cosmos DB sample sets a time to live on event documents and suggests several days, such as 10, so an outage cannot expire unsent events. With log tailing, Debezium's write-up inserts and deletes the outbox row in the same transaction: the insert is captured from the log, and the table stays empty. If no other service needs to learn of a change, the outbox is unnecessary overhead.

Polling or log tailing

Polling publisherLog tailing (CDC)
Any SQL databaseDatabase-specific connector
Adds query load; latency = poll intervalLow overhead, near real time
Easy to build and debugMore moving parts to run
Ordering is trickyReads changes in log order

Costs and clean-up

  • Delete rows once sent, or mark and purge later
  • Or insert and delete in one transaction (CDC)
  • Or let the store expire them (a TTL)
  • Not needed when nothing else must hear of a change

7 · In the wild

Real implementations and where our own systems use it.

Chris Richardson's microservices.io catalogues the pattern with its two relay options, Polling publisher and Transaction log tailing. Debezium provides an outbox event router transformation: its default columns are id, aggregatetype, aggregateid, type and payload; it routes to a topic named outbox.event.<aggregatetype> and uses aggregateid as the message key. AWS prescriptive guidance shows the pattern with Amazon RDS and SQS (a polling service) and with DynamoDB streams (CDC). Microsoft's Azure Architecture Center implements it with a Cosmos DB transactional batch (single logical partition), the change feed and Service Bus, and points to NServiceBus and MassTransit, which have outboxes built in; MassTransit's inbox tracks received messages to give exactly-once consumer behaviour.

8 · Related patterns

What it is confused with or combined with.

At-least-once delivery means the outbox always pairs with an idempotent consumer, whose transactional form is the inbox. Sagas and domain events create the need for it: each step updates local data and must reliably notify the next. Event sourcing is an alternative, since when the events are the stored data there is no second write. Change data capture is one way to implement the relay. It replaces two-phase commit across database and broker.

9 · Recap

Three takeaways.

Never write to a database and a broker separately. Commit the event with the change, in one local transaction. Expect duplicates and out-of-order risk: key by aggregate and make consumers idempotent.

Recap

  • Never write to a database and a broker separately
  • Commit the event in the same local transaction
  • Expect duplicates: consumers must be idempotent
