Read replicas

Send every write to one primary, stream its change log to read-only copies, and spread reads across them.

1 · The problem

What goes wrong without it, shown happening.

Most applications read far more than they write: every page view queries the database, while only a few actions change anything. With one database, reads and writes compete for the same CPU, memory and disk. When it saturates, queries queue, and the writes that matter wait behind thousands of reads. The numbers in the video (10,000 queries a second, nine in ten reads) are illustrative.

2 · The naive fix

The obvious approach and why it breaks.

Scaling up, moving to a larger instance, needs no code changes and works for a while. But each step costs more, there is a largest size, and it remains a single machine: a failure or maintenance restart stops every read and every write together.

3 · The pattern

Its parts and the role of each.

One primary accepts all writes. Every change is already recorded in its log (the write-ahead log in PostgreSQL, the binary log in MySQL). Replicas receive that log and replay it, so they hold copies of the same data and serve read-only queries. A router decides where each query goes.

PartJob
PrimaryAccepts every write; the source of truth
Change logWAL or binlog: the ordered record of changes that is shipped
ReplicasReplay the log; read-only (PostgreSQL hot standby refuses even temporary tables)
RouterSends writes and must-be-fresh reads to the primary, other reads to replicas
Failover toolingDetects a dead primary, fences it, promotes a replica, re-points clients

4 · How it works

The normal flow, step by step.

With asynchronous replication, the default in PostgreSQL and MySQL, the primary commits and answers without waiting for replicas, then streams the change. PostgreSQL describes the delay as typically under one second if the standby can keep up. Routing can live in the application (two connection pools), in the driver (libpq lists several hosts and chooses with target_session_attrs: read-write, primary, standby, prefer-standby and more), or in a proxy (ProxySQL routes by query rules to primary and replica host groups, and warns that a blanket “every SELECT to replicas” rule causes problems with transactions, session state and consistency).

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

Replication lag. Data on a standby is, in PostgreSQL's words, eventually consistent with the primary. Two session guarantees break. Read-your-writes: a process that writes should see that write on later reads. Monotonic reads: once a process has seen a version, later reads should not show an older one. Fixes: read from the primary for a short while after a user writes (sticky reads); or track the log position of the write and read only from a replica that has replayed past it; pin each user to one replica; and read anything that must be exact from the primary. Monitor lag: Amazon RDS exposes it as the ReplicaLag metric.

Failover. Promote a replica (pg_ctl promote or pg_promote() in PostgreSQL). PostgreSQL does not itself detect a failed primary; external tools do. With asynchronous replication, committed transactions not yet replicated are lost, in proportion to the lag at the time. If the old primary comes back without being told it is no longer primary, both accept writes: split brain. PostgreSQL's documentation calls the remedy STONITH, “shoot the other node in the head”. For planned promotions, AWS recommends stopping writes and waiting for the replica to catch up first.

6 · Trade-offs

What it costs, when not to use it, and its main variants.

ModeCommit waits forTrade-off
AsynchronousNothingFast writes; failover can lose recent commits
Semi-synchronous (MySQL)At least one replica to receive and log the events (not apply them)Falls back to asynchronous if no replica acknowledges within rpl_semi_sync_source_timeout (10 s by default)
Synchronous (PostgreSQL)Standby to flush the commit record; with remote_apply, to replay itEvery write pays the round trip; remote_apply allows causally consistent reads on the standby

Replicas do not help writes: every replica replays every write, so the primary's write capacity is the ceiling, and scaling writes needs sharding. Each replica is a full instance (RDS bills them at standard instance rates). Cross-region replicas bring reads closer to users and support disaster recovery, but AWS notes higher lag across regions.

What replicas do not fix

  • Writes: every replica replays every write; the primary is the ceiling
  • To scale writes, split the data: sharding
  • Cost: each replica is a full database instance
  • Cross-region replicas: closer reads and disaster recovery, but more lag

7 · In the wild

Real implementations and where our own systems use it.

PostgreSQL streams WAL records to standbys; hot standby lets them serve read-only queries, and cascading replication lets a standby relay to others. MySQL replicates from the source's binary log, asynchronous by default, with semisynchronous replication as an option. Amazon RDS read replicas use each engine's built-in asynchronous replication, can be created in another region, and can be promoted to standalone instances. Amazon Aurora differs: up to 15 Aurora Replicas share the cluster's storage volume, lag is usually much less than 100 milliseconds, the reader endpoint spreads read connections across them, and Aurora promotes one automatically if the writer fails.

8 · Related patterns

What it is confused with or combined with.

Cache-aside absorbs repeated reads before they reach any database. Sharding splits data so writes scale too, and each shard can have its own replicas. CQRS builds a separate read model shaped for queries rather than copying the same tables. The write-ahead log is the building block replicas replay. Failover depends on choosing one primary safely, which is leader election.

9 · Recap

Three takeaways.

Writes to one primary; stream its log to replicas that serve reads. Replicas lag: read your own writes from the primary and keep each user on one replica. Plan failover: know what asynchronous replication can lose, and fence the old primary.

Recap

  • Writes to one primary; stream its log to replicas that serve reads
  • Replicas lag: read your own writes from the primary; keep users on one replica
  • Plan failover: know what async can lose, and fence the old primary
