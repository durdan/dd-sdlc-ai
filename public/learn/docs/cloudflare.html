Cloudflare: one network at the edge

How one anycast network, where every server runs every service, caches, filters attacks, runs customer code and applies configuration changes worldwide in seconds: Unimog, FL2, Pingora, tiered cache, dosd, Workers and Quicksilver.

1 · Overview

What it is, who uses it, and the one idea everything depends on.

Cloudflare sits in front of websites, APIs and applications. Visitors connect to Cloudflare rather than to the customer's origin; Cloudflare answers from cache, blocks attacks, runs customer code (Workers) and forwards the rest.

The one idea everything depends on is uniformity. Every data centre announces the same IP addresses (anycast), and every server can answer every type of request. Capacity, DDoS defence and new products all grow by adding more identical machines in more cities. The same uniformity is why a bad change can reach everything at once, which is the theme of the failure section.

2 · Requirements and scale

What users need, the quality targets, and back-of-envelope numbers.

Scale, from Cloudflare's own pages, each figure dated:

  • Network page (undated page, checked 14 October 2026): 348 cities; 95% of the world's Internet-connected population within 50 ms; 13,000+ network interconnections.
  • “500 Tbps of capacity” (10 April 2026): 500 Tbps of provisioned external interconnection capacity, explicitly not peak traffic, across 330+ cities in 125+ countries.
  • 2025 Q4 DDoS threat report (5 February 2026): 47.1 million DDoS attacks mitigated in 2025; a record 31.4 Tbps attack lasting 35 seconds, mitigated automatically.
  • Pingora (14 September 2022): over one trillion requests a day. The Pingora README (checked October 2026) says it serves more than 40 million requests per second.

3 · Context

Who and what the system talks to (C4 level 1).

Three outside actors. Visitors resolve a customer's hostname to a Cloudflare anycast address and are routed by BGP to the nearest data centre; if that site goes offline, routing moves them to the next nearest (anycast primer, 2011). Customer teams change settings through the dashboard and API. Botnets send floods, which anycast spreads out: in the 2011 post's words, “a distributed botnet will have a portion of its denial of service traffic absorbed by each of our data centers”. Requests that cannot be answered at the edge go on to the customer's origin.

5 · Deep dive

Inside the most interesting component (C4 level 3).

One request through one edge server. Each stage is described in a Cloudflare post; putting them on one page is our assembly, and posts from 2020 to 2025 may not describe exactly the same moment.

  • l4drop and Unimog (September 2020). Unimog is an XDP program on every server, behind the l4drop DDoS layer. Routers may send a packet to any server; Unimog hashes the 4-tuple into a forwarding table shared by all load balancers and forwards it to the owning server. The table is weighted by measured CPU utilisation, because hardware generations are mixed. Daisy chaining (from the Beamer paper) keeps a current and previous server per bucket so existing connections survive table changes; under 1% of forwarded packets need the second hop.
  • dosd (March 2021). Runs on every server in every edge data centre; analyses sampled packets and HTTP requests; on detection, generates a signature and pushes a rule to the most cost-efficient point: L4Drop for network attacks, the web proxy for HTTP floods, without central consensus. flowtrackd adds stateful TCP inspection for Magic Transit customers (April 2026 post).
  • TLS, then FL (September 2025). Requests terminate at the HTTP and TLS layer and pass into FL, “the brain”, which applies each customer's configuration: WAF rules, DDoS protection, routing to the developer platform. FL1 was built on NGINX, OpenResty and LuaJIT; FL2 is a Rust rewrite, cutting median response time by 10 ms and using less than half the CPU. Cloudflare planned to turn FL1 off in early 2026.
  • Pingora (September 2022; open-sourced under Apache 2.0 in February 2024). Performs cache lookups and origin fetches. It replaced NGINX because per-worker connection pools hurt reuse and per-request worker pinning unbalanced cores. Multithreaded Rust on Tokio, with a shared pool: about 70% less CPU and 67% less memory; one major customer's reuse ratio rose from 87.1% to 99.92%.

6 · Core flows

Two or three requests that matter, step by step.

A cache miss through tiered cache. DNS returns an anycast address; the visitor connects to the nearest data centre; the proxy runs the customer's rules and checks the local cache. On a miss, the lower-tier data centre asks an upper tier; only the upper tier may contact the origin. Smart Tiered Cache (all plans) picks the upper tier closest to the origin by latency; Generic Global (Enterprise) uses a consistent hash of the cache key over regional pools; Regional and Custom topologies also exist. The response is cached in both tiers on the way back.

A setting change. The control plane writes to Quicksilver, which replicates to every edge server “within seconds”; the proxy reads its local copy. In 2020 Quicksilver handled 2.5 trillion reads and 30 million writes a day across more than 90,000 database instances. Fast global propagation is what made the 2019 and 2025 outages global.

9 · Failure modes

What breaks, what users see, and what protects them.

FailureWhat protects usersBasis
A data centre goes offlineAnycast routes to the next nearestDocumented (2011)
One server overloadedUnimog weights the forwarding table by CPU loadDocumented (2020)
Record-size flooddosd on every server; 31.4 Tbps mitigated autonomouslyDocumented
Origin overloadedTiered cache; Pingora connection limits reject with 503Documented (2023 pingora-limits post)
Bad rule pushed globallyStaged rollouts with an emergency global pathDocumented (2019 remediation)
Core data centre loses powerEdge keeps serving; control plane to disaster recovery siteDocumented (2023)

2 July 2019. A WAF managed rule with a badly backtracking regular expression was pushed worldwide at once through Quicksilver; rule changes skipped the staged rollout. CPUs serving HTTP hit nearly 100%, visitors saw 502s, and Cloudflare lost about 80% of its traffic for 27 minutes. Remediation: restore a removed CPU-protection check, review all 3,868 rules, profile rules in tests, move to a regex engine with run-time guarantees (re2 or Rust regex), stage rule rollouts.

2 November 2023. Power failure at Flexential's PDX-04 near Portland, home of Cloudflare's largest analytics cluster and much of its high-availability cluster. Control plane and analytics failed from 11:44 UTC; most control plane services were back from the disaster recovery site by 17:57 UTC; full recovery 4 November. Traffic through the network was not affected. Some pushed logs were lost. Response: “Code Orange”.

18 November 2025. A ClickHouse permissions change made the Bot Management feature file double in size, past a 200-feature limit; the file is regenerated every few minutes and pushed network-wide. FL2 panicked and returned 5xx; FL1 gave every request a bot score of zero. Impact from about 11:28 UTC; core traffic largely restored by 14:30, everything by 17:06. Follow-ups include treating internal config files like user input and more global kill switches.

12 · What we would build first

An MVP cut and our recommendations.

Our recommendations for a small edge network, not Cloudflare's:

  • A handful of cities on anycast, through one or two transit providers.
  • Identical servers running one proxy, perhaps built on the open-source Pingora framework, that caches and forwards.
  • Per-customer configuration in a replicated local store, read on every request.
  • A simple per-server traffic sampler that writes XDP drop rules.
  • Every change, including internally generated files, staged: one server, one city, then everywhere; plus global kill switches.
  • A control plane the edge can live without.

What we would build first

  • A handful of cities on anycast, through one or two transit providers
  • Identical servers: one Pingora-based proxy that caches and forwards
  • Per-customer config in a replicated local store, read on every request
  • XDP drop rules from a simple per-server traffic sampler
  • Every config change staged: one server, one city, then everywhere
  • A control plane the edge can live without
