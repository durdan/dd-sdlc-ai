Consistent hashing

Put servers and keys on the same ring, so adding or removing a server moves only a small share of the keys instead of nearly all of them.

1 · The problem

What goes wrong without it, shown happening.

The simplest way to spread keys over N servers is hash(key) mod N. It balances well until N changes. Going from N to N + 1 servers, a key stays put only if its hash gives the same remainder for both, which is about one key in N + 1; the rest move. From three caches to four, three keys in four move; from ten to eleven, ten in eleven. For a cache, every moved key is a miss, and the misses all reach the database at once. Karger et al. describe exactly this: when the range of a classical hash function changes, “almost every item would be hashed to a new location”.

2 · The naive fix

The obvious approach and why it breaks.

A directory that records the server for every key allows keys to move one at a time, but it adds a lookup to every request, needs a row per key, and becomes a component that must never fail. Doubling the server count with mod hashing is no cure either: half the keys still move.

3 · The pattern

Its parts and the role of each.

Treat the output range of the hash function as a circle. Hash each server onto it, and hash each key onto the same circle. A key belongs to the first server found walking clockwise from its position, so each server owns the arc between its predecessor and itself. Every client with the same list of servers computes the same owner, with no directory.

PartJob
Hash functionPlaces servers and keys on the same circle
TokensEach server's positions; with virtual nodes, many per server
Ring mapA sorted list of tokens, searched for the first token at or after a key's hash
MembershipThe agreed list of servers, which every client must share
Replica placementCopies on the next distinct servers clockwise

Adding a server only takes the arc it now ends; removing one hands its arc to the next server clockwise. Dynamo puts it as: arrival or departure of a node only affects its immediate neighbours. Positions in the walkthrough (0–99) are illustrative; real rings use the full hash range.

4 · How it works

The normal flow, step by step.

A lookup hashes the key and binary-searches the sorted token list for the first token at or after that hash, wrapping to the first token past the end. In Dynamo, the owner (the coordinator) also stores the key at the N − 1 clockwise successor nodes, and the list of nodes for a key, the preference list, skips positions so that it contains only distinct physical nodes. The sequence in the walkthrough is simplified to one replica.

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

When a server fails, its arc falls to the next server clockwise, which, with clockwise replication, already holds copies. With a single random position per server, though, arcs are uneven and a failed server's whole load lands on one neighbour. Dynamo lists both problems with basic consistent hashing (non-uniform load and ignoring differences between machines) and fixes them with virtual nodes: each node takes many positions, its load is spread over many others when it fails, and bigger machines take more positions. Karger et al. already gave each cache several points. Consistent hashing spreads keys, not requests: a hot key still lands on one server, and clients with different server lists send the same key to different places.

What it does not fix

  • One hot key still lives on one server
  • It spreads keys, not traffic
  • Clients with different server lists disagree
  • Moved keys are still cache misses

6 · Trade-offs

What it costs, when not to use it, and its main variants.

The ring needs a sorted token list and membership that every client agrees on. Alternatives make different trades:

  • Rendezvous (highest random weight) hashing, Thaler and Ravishankar, 1996: hash the key with every server and pick the highest score. No ring, but a lookup costs one hash per server.
  • Jump consistent hash, Lamping and Veach (Google), 2014: about five lines of code, no memory, faster than Karger's ring, but buckets must be numbered sequentially, which suits data storage more than distributed web caching.
  • Consistent hashing with bounded loads, Mirrokni, Thorup and Zadimoghaddam: cap each server at (1 + ε) times the average; a key walks clockwise past full servers. Expected moves per change stay bounded, O(1/ε²) for small ε.

When not to use it: a fixed, small number of servers that never changes gains little over mod N; workloads that need range scans are better served by range partitioning.

7 · In the wild

Real implementations and where our own systems use it.

Karger, Lehman, Leighton, Panigrahy, Levine and Lewin introduced consistent hashing at STOC 1997 for distributed web caching and relieving hot spots. Amazon's Dynamo (SOSP 2007) used the ring with virtual nodes and clockwise replication for a key-value store. Apache Cassandra takes its partitioning and replication from Dynamo: nodes own tokens on a hash ring, vnodes give each node several tokens, and the current default is 16 tokens per node (Cassandra 2.x needed 256). The ketama library for memcached clients places about 100–200 points per server, weighted by memory. Google Research reports that Google Cloud Pub/Sub adopted bounded loads, and that Vimeo implemented it in HAProxy, cutting cache bandwidth by a factor of almost 8.

8 · Related patterns

What it is confused with or combined with.

Consistent hashing is one way to pick a shard; range partitioning is the main alternative when order matters. It is usually paired with replication on the ring, and it depends on membership, often backed by a coordination service or leader election, so that every client sees the same servers. Rate limiters and other per-key state can use it to give each key one owner.

Related patterns

  • Sharding: consistent hashing is one way to pick the shard
  • Range partitioning: keeps key order; hot ranges need splitting
  • Replication: copies on the next servers clockwise
  • Rate limiting: one owner per client's counter
  • Membership and leader election: agree who is on the ring

9 · Recap

Three takeaways.

Mod N reshuffles almost everything when N changes. A ring moves only about one key in N. Virtual nodes keep load even, and replicas go to the next servers clockwise.

Recap

  • hash mod N moves almost every key when N changes
  • On a ring, a change moves only about 1/N of keys
  • Virtual nodes even the load; replicas go clockwise
