Competing consumers

Put slow work on a durable queue and let a pool of identical workers each take the next message; scale the pool on queue depth.

1 · The problem

What goes wrong without it, shown happening.

A web request that does slow work inline (resizing an uploaded image, sending an email) holds a request thread for the whole time. Under a burst the thread pool runs out, new requests wait and time out, and a request that times out halfway may leave work half done, so the user's retry repeats it. The work is fine; doing it while the user waits is the problem.

2 · The naive fix

The obvious approach and why it breaks.

Handing the work to a background thread with an in-memory job list makes replies fast, but the list lives in one process: a deploy or crash loses every pending job. Capacity is tied to the number of web servers, so a burst only grows the backlog, and you cannot add capacity for the slow work alone.

3 · The pattern

Its parts and the role of each.

The producer posts each job as a message on a queue. Several identical consumer instances read from the same queue; each message is delivered to one of them. Enterprise Integration Patterns states it as “multiple Competing Consumers on a single channel so that the consumers can process multiple messages concurrently”.

4 · How it works

The normal flow, step by step.

On Amazon SQS a received message stays in the queue but is hidden from other consumers for the visibility timeout (30 seconds by default). The consumer processes it and then deletes it; the delete is the acknowledgement. Visibility can be extended with ChangeMessageVisibility (for example from a heartbeat), up to 12 hours from first receipt. RabbitMQ uses explicit acks instead: an unacknowledged message is re-queued if its consumer dies, and a delivery-acknowledgement timeout (30 minutes by default) catches stuck consumers. Azure Service Bus calls the same idea peek-lock. Job numbers and the four thumbnails in the walkthrough are illustrative.

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

Crashed worker. If the message is not deleted before its visibility timeout expires, it becomes visible again and the same or another consumer receives it. Nothing is lost, but work can run twice. SQS standard queues are at-least-once and can occasionally deliver a copy more than once even without a crash, so handlers must be idempotent: write outputs to deterministic keys and record side effects such as emails before repeating them.

Poison messages. A message that can never succeed would circulate for ever. On SQS a redrive policy sets maxReceiveCount; once a message has been received that many times without being deleted, it moves to the dead-letter queue, from which it can later be redriven. Service Bus dead-letters after MaxDeliveryCount. Alert on the dead-letter queue and set its retention longer than the source queue's.

6 · Trade-offs

What it costs, when not to use it, and its main variants.

Visibility timeout: too short and a slow job is handed to a second worker while the first is still on it; too long and a crashed job waits before its retry. Prefetch: RabbitMQ dispatches round-robin by default; basic_qos(prefetch_count=1) stops a worker being given a new message until it has acknowledged the last, so busy workers are not overloaded. Ordering: consumers finish in any order. SQS FIFO queues keep strict order within a message group and process different groups in parallel; Kafka keeps order within a partition, and same-key events go to the same partition. Downstream limits: more workers help only until whatever they write to becomes the bottleneck.

Microsoft lists when it does not fit: the work cannot be split into independent tasks, the caller must wait for each task, or tasks must run in a specific sequence. Results also need a home, because the worker cannot reply to the user directly.

The knobs

ChoiceTrade-off
Visibility timeoutToo short: a second worker starts a live job; too long: slow retry after a crash
PrefetchHigh: fewer round trips, but one worker hoards work; 1: fair dispatch
OrderingLost across workers; FIFO message groups or partitions keep order per key
More workersMore throughput, until whatever they write to is the bottleneck

When not to use it

  • The work cannot be split into independent tasks
  • The caller must wait for the result before carrying on
  • Tasks must run in a strict sequence
  • Workers cannot reply to the user: results need a shared store or reply queue

7 · In the wild

Real implementations and where our own systems use it.

Enterprise Integration Patterns (2003) named the pattern. Microsoft's Azure Architecture Center implements it with Service Bus queues and Azure Functions, using peek-lock, automatic lock renewal and a dead-letter queue, with Functions scaling on queue depth. Amazon SQS provides visibility timeouts, dead-letter queues with redrive, and FIFO message groups. RabbitMQ's “Work Queues” tutorial introduces acknowledgements, durability and fair dispatch with prefetch. KEDA feeds queue metrics to the Kubernetes Horizontal Pod Autoscaler and can scale to zero; its SQS scaler targets a queue length per pod (default 5) and by default counts in-flight messages. Kafka consumer groups are the partitioned variant: each partition is consumed by exactly one consumer in the group; Kafka's newer share groups allow more consumers than partitions with per-record acknowledgement.

8 · Related patterns

What it is confused with or combined with.

Not to be confused with publish–subscribe: with competing consumers one consumer receives each message; with pub/sub every subscriber receives every message. They combine well: each subscription can be a queue with its own pool of competing workers. The idempotent consumer makes redelivery safe. Queue-based load levelling is the buffering half of this pattern. Backpressure decides what happens when the backlog outruns scaling. Event streaming with consumer groups is the partitioned, order-per-key variant.

9 · Recap

Three takeaways.

Queue the slow work. Let many workers share it, one message each, and scale on queue depth. Delivery is at least once: make handlers idempotent and dead-letter poison messages.

Recap

  • Take slow work out of the request: put it on a durable queue
  • Many workers, one message each; scale them on queue depth
  • Delivery is at least once: idempotent handlers and a dead-letter queue
