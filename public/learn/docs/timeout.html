Timeout

Never wait forever: give every remote call a time limit chosen from real latency, and pass one deadline down the whole call chain.

1 · The problem

What goes wrong without it, shown happening.

Services handle requests with a fixed number of threads and a fixed pool of connections to each dependency. A dependency that crashes returns an error and the caller moves on. A dependency that hangs returns nothing at all, and a caller with no timeout waits indefinitely, holding a thread and a connection the whole time. The pools drain, and requests that never touch the hung service start failing too. AWS's Builders' Library puts it simply: a request that waits longer holds on to its resources for longer, and enough of them make the server run out.

2 · The naive fix

The obvious approach and why it breaks.

The obvious fix is one generous round number, such as 30 seconds, applied at every layer. It still holds threads for far longer than any user will wait. Because every layer has the same limit, the outer caller gives up at about the moment the inner ones are still working, so their work is wasted. And the user's second click lands on top of the first request, which is still in flight.

3 · The pattern

Its parts and the role of each.

A timeout puts an upper bound on how long a caller waits for a remote call, and gives it a plan for when the bound is hit.

PartJob
DeadlineThe time left for the whole request, handed down from the caller
Connect timeoutHow long to wait to open a connection (TCP and TLS handshake)
Request or read timeoutHow long to wait for the answer, capped at the time left
On timeoutCancel, then return a fallback, a clear error, or retry if safe
MetricsTimeouts per dependency, so a slow dependency shows up before users report it

Check what each setting in your client actually covers. In Python's Requests, the read timeout is the time the client waits between bytes from the server, not a limit on the whole response, and neither the connect nor the read timeout is a wall-clock limit. Go's http.Client.Timeout, by contrast, covers connection time, redirects and reading the body.

Which limit covers what

TimeoutWhat it limits
ConnectOpening the connection
ReadWaiting for the answer; in some clients, the gap between bytes
IdleA connection or stream with no traffic
DeadlineThe whole request, across every hop

4 · How it works

The normal flow, step by step.

Choosing the value. AWS's Builders' Library starts from the latency of the downstream service: choose an acceptable rate of false timeouts (for example 0.1%) and use the matching percentile, here p99.9, then add headroom. The figures in the video (40 ms p50, 300 ms p99.9, about 350 ms timeout) are illustrative.

Propagating a deadline. Set the deadline once, at the edge, and pass it down. gRPC does this: a server that calls another server can pass the incoming deadline on, and gRPC converts the deadline into a timeout with the elapsed time already deducted, so clock differences between servers do not matter. Propagation is on by default in Java and Go and must be enabled explicitly in C++.

Choosing the number (illustrative)

40 msp50: a typical call
180 msp99
300 msp99.9: one call in a thousand is slower
≈ 350 mstimeout: p99.9 plus headroom

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

When the deadline passes, the gRPC client fails the call with DEADLINE_EXCEEDED and the server automatically cancels it (CANCELLED). The server application is still responsible for stopping any work it started. More generally, as the Builders' Library notes, a timeout or failure does not mean the side effects did not happen. APIs with side effects are only safe to retry when they are idempotent, typically by sending the same idempotency key on each attempt so the server can return the first result instead of doing the work again. Any retry must also fit inside what is left of the deadline.

6 · Trade-offs

What it costs, when not to use it, and its main variants.

Too short a timeout fails healthy but slower calls, and if those are retried, adds load just when the dependency is struggling. Too long a timeout holds threads and connections, and lets a hang masquerade as a slow call. The Builders' Library cautions that the percentile method needs adjusting when network latency is high or when p99.9 is close to p50. Variants: a per-attempt timeout plus an overall deadline; adaptive timeouts driven by live latency; idle timeouts for streams; and server-side timeouts that drop work nobody is waiting for.

Too short or too long

Too shortToo long
Healthy but slow calls failThreads and connections held for longer
Retries add load at the worst momentUsers give up before you do
Slow but valid work never finishesA hang looks like a wait; alarms fire late

Variants

  • Per-attempt timeout and an overall deadline: usually both
  • Fixed value, or adapted to live latency
  • Idle timeout for streams and long downloads
  • Server-side timeouts: drop work nobody is waiting for

7 · In the wild

Real implementations and where our own systems use it.

gRPC does not set a deadline by default, so a client can wait effectively forever; its guide recommends setting one. Python's Requests does not time out unless a timeout is passed (timeout=(connect, read)). In Go, a zero http.Client.Timeout means no timeout, and http.DefaultClient leaves it at zero. Envoy is stricter by default: a 15-second route timeout, a 5-second connect timeout when none is configured, and a 5-minute stream idle timeout. The AWS Builders' Library article on timeouts, retries and backoff is the standard reference for picking values.

8 · Related patterns

What it is confused with or combined with.

Retries usually follow a timeout and must respect the deadline and idempotency. A circuit breaker counts timeouts as failures and stops calling a dependency that keeps timing out. A bulkhead caps how many threads can be waiting on one dependency, so even a slow-but-within-limits dependency cannot take every thread. A fallback is what the caller returns when time is up.

9 · Recap

Three takeaways.

Every remote call needs a time limit, and many libraries default to none. Choose it from the dependency's real latency and propagate one deadline down the chain. A timeout means you stopped waiting, not that nothing happened.

Recap

  • Every remote call needs a time limit; many libraries default to none
  • Choose it from the dependency's p99.9, and pass one deadline down the chain
  • A timeout means you stopped waiting, not that nothing happened
