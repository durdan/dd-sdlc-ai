CDN and edge caching

Serve shared content from servers near your users, let the origin's HTTP headers decide what may be stored, and keep serving when the origin is slow or down.

1 · The problem

What goes wrong without it, shown happening.

With a single origin, every request from every user travels to one region. Users far away pay a long round trip for each of the dozens of requests a page needs, and the origin rebuilds the same responses again and again. A busy day multiplies the same work until the origin cannot keep up.

2 · The naive fix

The obvious approach and why it breaks.

Putting a cache in front that stores everything by URL is fast and dangerous. A shared cache keys responses on the request method and URL by default, so a personalised page stored under /account is handed to the next person who asks for /account. MDN warns that personalised content stored in a cache other than a private cache may leak to other users. The opposite mistake, caching nothing, leaves the origin doing all the work.

3 · The pattern

Its parts and the role of each.

A content delivery network is a managed shared cache (MDN's term) with servers in many locations. Users reach a nearby edge; misses go to an upper tier or shield near the origin, so the origin sees one request per object rather than one per edge. The origin's response headers decide what is stored.

HeaderEffect
max-age=NFresh for N seconds in any cache
s-maxage=NOverrides max-age for shared caches only (RFC 9111). Not every CDN reads it: Fastly uses Surrogate-Control instead.
privateA shared cache must not store it; the browser may
publicStorable even when the request carried Authorization; otherwise rarely needed
no-cacheMay be stored, but must be revalidated before each reuse
no-storeNot stored at all
immutableNo revalidation even on reload; for fingerprinted files
ETag + If-None-MatchRevalidation: 304 Not Modified with no body if unchanged
VaryAdds named request headers to the cache key

Example header values in the walkthrough (a year for a fingerprinted script, 60 s and 300 s for a product list) are illustrative.

4 · How it works

The normal flow, step by step.

On a miss the edge asks the shield, the shield asks the origin once, and both store the response on the way back. The next nearby request for the same key is a hit and never reaches the origin. When a stored copy goes stale, the cache sends a conditional request with If-None-Match; if the ETag still matches, the origin replies 304 Not Modified and the copy is fresh again without the body being resent. CloudFront documents exactly this behaviour when a file expires.

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

Thundering herd on expiry. Request collapsing combines concurrent requests for the same object into one request to the origin (Fastly; MDN also describes it). Shielding concentrates misses in one location so collapsing works across the whole network. If the response turns out uncacheable or private, queued requests are sent to the origin one after another, and long queues can cause client time-outs.

Slow or failing origin. RFC 5861 (Informational, 2010) defines stale-while-revalidate=N, which lets a cache serve a stale response for up to N seconds while it refreshes in the background, and stale-if-error=N, which lets it serve a stale response when the origin returns an error. CloudFront and Fastly both support the two directives.

Changing content. Purges remove cached copies (Cloudflare offers purge by URL, tag, hostname, prefix and everything, and recommends purge by URL). A purge cannot reach copies already in browsers or corporate proxies, which is one reason AWS recommends versioned file names for files that change often. A new build gets a new URL, so nothing needs purging.

Header mistakes. Cloudflare does not cache a response carrying Set-Cookie by default, nor one marked private, no-store, no-cache or max-age=0, and it does not cache HTML or JSON by default. MDN warns that Vary: User-Agent has so many values it drastically reduces reuse, and recommends private rather than varying on cookies. Note also that CloudFront with a minimum TTL above zero caches for that minimum even when the origin says private or no-store.

Where it still goes wrong

  • Set-Cookie on a response stops many CDNs storing it
  • Vary: User-Agent splits one URL into thousands of copies
  • Uncacheable answers make collapsed requests queue in turn
  • A missing private lets a shared cache store personal data

6 · Trade-offs

What it costs, when not to use it, and its main variants.

Longer lifetimes protect the origin but serve older content; shorter lifetimes with ETags stay fresher at the cost of revalidation round trips. Extra tiers raise the hit ratio but add a hop on a miss, and some are billed separately (CloudFront Origin Shield). Every header or cookie added to the cache key gives more precise answers and fewer hits; Cloudflare warns custom keys can fragment the cache.

A CDN cannot cache writes, per-user responses, data that must never be stale, or content requested so rarely that it expires before a second request; AWS says Origin Shield is a poor fit for dynamic, low-cacheability or infrequently requested content.

The knobs

ChoiceTrade-off
Long time to liveFewer origin hits; stale until it expires or is purged
Short life + ETagFresher; a cheap round trip to the origin each time
Shield or upper tierHigher hit ratio; an extra hop and cost on a miss
More in the cache keyRight variant per user group; lower hit ratio

What a CDN cannot cache

  • Writes: POST, PUT, DELETE go to the origin
  • Responses for one user only: private or no-store
  • Data that must never be even seconds old
  • Rarely requested content: it expires before a second hit

7 · In the wild

Real implementations and where our own systems use it.

RFC 9111 (2022) is the HTTP caching standard; MDN's caching guide explains it for practitioners. Cloudflare's Tiered Cache divides data centres into lower and upper tiers, and only upper tiers contact the origin. Fastly documents request collapsing and per-origin shielding. CloudFront routes each request to the edge location with the lowest latency, adds regional edge caches as a middle tier, and offers Origin Shield as a further layer that consolidates requests. Netflix's Open Connect is a purpose-built alternative: it provides appliances to qualifying internet providers at no charge, embedded in their networks or placed at internet exchange points.

8 · Related patterns

What it is confused with or combined with.

Cache-aside is the same idea inside a service, in front of a database. Graceful degradation is the broader rule that a stale answer often beats an error; stale-if-error is one way to achieve it. Request collapsing is request coalescing (single flight) applied at the edge. Rate limiting is often enforced at the edge too.

9 · Recap

Three takeaways.

Serve shared content from near the user and ask the origin once. Let headers decide what is stored, and mark anything personal private. Change URLs rather than purging caches, and serve stale when the origin fails.

Recap

  • Serve shared content from near the user, and fetch it once
  • Headers decide: s-maxage, private, no-store, ETag
  • Change URLs, not caches; serve stale when the origin fails
