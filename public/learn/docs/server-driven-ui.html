Server-driven UI

Let the server describe each screen as data, and let the app draw it from a fixed library of native components, so layouts change without an app release.

1 · The problem

What goes wrong without it, shown happening.

On mobile, a screen's layout lives in the app's code. Changing it means changing the iOS and Android apps, passing app-store review, and then waiting for users to update. Many never update promptly: Lyft has said it officially supports rider apps up to two years old. So a layout change takes weeks to reach most users, and different users see different screens in the meantime.

2 · The naive fix

The obvious approach and why it breaks.

Remote configuration and feature flags can switch between layouts that are already compiled into the app, but a genuinely new layout is still new code and still needs a release. Rendering a web page inside the app changes instantly, but it loads more slowly, looks out of place next to native screens, and has awkward access to native features.

3 · The pattern

Its parts and the role of each.

In server-driven UI the server sends a description of the screen (which sections, in what order, with what content and what each tap does) and the app renders it from a fixed library of native components. The server owns what appears and where; the app still owns how each component looks and behaves.

PartJob
Screen serviceComposes each screen for a user and client; often a backend for frontend
Component registryThe versioned schema of component and action types both sides agree on
RendererMaps each type in the response to a native view
Native component libraryThe fixed set of building blocks compiled into the app
Action handlersNavigate, open a link, save, track: behaviour described as data
On-device cacheThe last good screen, shown at once and used when the server fails

Keep the vocabulary closed (the server only uses types the app knows) and shallow (a screen is a list of self-contained sections, not an arbitrary tree of boxes). Airbnb's engineers describe choosing the abstraction level early and building mostly around large sections; a Lyft engineer frames the same choice as driving UI at the level of buttons and layouts, or of cards and screens.

4 · How it works

The normal flow, step by step.

The app shows the last good screen from its cache, then requests the screen, sending its schema version and the components it supports. The screen service gathers content, returns sections and actions as plain data, and the app renders them and saves the response. A tap runs an action, such as navigating to another server-described screen. In the walkthrough the schema versions, component names and the cache step are illustrative.

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

An older app declares an older schema. The server degrades for it: it swaps a newer component for an older one that shares its fields, drops the section, or, where nothing sensible fits, shows a prompt to update. The client skips and logs any type it does not recognise rather than crashing. When the screen service is slow or down, the cached last good screen keeps the app usable. Microsoft's Adaptive Cards build this into the format: a card declares a version, and elements can carry a fallback (another element, or "drop") and a requires map that triggers the fallback when a host lacks a feature.

Where it still goes wrong

  • A new type reaches an old client: skip it and log, never crash
  • A section with no sensible fallback: show an update prompt
  • A slow screen service delays every screen: cache and time out
  • A server change breaks an app version nobody tested

6 · Trade-offs

What it costs, when not to use it, and its main variants.

Layouts ship in minutes and one screen logic can serve several platforms, but every server change can now break any live app version, and you build and own a renderer per platform plus the registry. Testing moves to contract tests against the schema, snapshot tests per component and app version, previews, and gradual rollouts. Avoid it for highly interactive screens (maps, editors, games), for small teams on one platform that release often, and as a general-purpose UI language. Thoughtworks' Technology Radar, which places the technique in Trial (April 2026), recommends it for highly dynamic areas rather than all UI and warns against a hard-to-maintain "god-protocol"; earlier editions warned of "horrendous, overly configurable messes".

What you gain, what you pay

GainCost
Layout changes ship in minutesEach change can break every live app version
One screen logic for iOS, Android and webA renderer and registry to build and own
Experiments without a releaseThe screen is now data, so harder to test
Native look and speedRich interaction and animation stay hard

Testing across clients

  • Contract tests: every response validates against the schema
  • Snapshot every component on each supported app version
  • Preview screens before they go live
  • Roll out screen changes gradually and watch crash rates

When not to use it

  • Highly interactive screens: maps, editors, games
  • Small teams with one platform and frequent releases
  • Screens that rarely change
  • As a general UI language with arbitrary nesting

7 · In the wild

Real implementations and where our own systems use it.

Airbnb's Ghost Platform (Ryan Brooks, June 2021) sends sections, screens and actions from a single backend response to web, iOS and Android, using one shared GraphQL schema served through its Viaduct data layer. Lyft's bikes and scooters team described its move to server-driven UI in March 2023, using what a co-author calls "semantic components and actions"; a Lyft engineer has described Canvas, an internal system of primitives defined in protobuf. Microsoft's Adaptive Cards are a public, schema-driven format: JSON cards that hosts such as Teams and Outlook render as native UI in their own style.

8 · Related patterns

What it is confused with or combined with.

The screen service is often a backend for frontend. Feature flags decide which screen a user gets. Contract testing keeps the schema backward compatible. Graceful degradation is how older clients get a simpler screen. Web views and hybrid apps are the alternative that trades native feel for instant changes.

9 · Recap

Three takeaways.

The server describes the screen; the app draws it natively. Keep the vocabulary closed, versioned and shallow. Degrade for old clients, and test every app version still in use.

Recap

  • The server describes the screen; the app draws it natively
  • Keep the vocabulary closed, versioned and shallow
  • Degrade for old clients, and test every live version
