CQRS

Separate the model that changes data from the models that answer questions, and design for the lag between them.

1 · The problem

What goes wrong without it, shown happening.

Most systems start with one model for everything: the same entities and tables serve every write and every read. That works for simple create, read, update and delete. It strains when writes and reads want very different things. Placing an order needs transactional rules (check stock, never oversell); searching the catalogue needs fast, fuzzy, faceted reads at far higher volume; reporting needs scans over history. Microsoft's guidance names the symptoms: a mismatch between read and write representations, lock contention, slow complex queries, and security that is hard to scope. Every change to the shared model has to suit all of them, so it becomes a compromise.

2 · The naive fix

The obvious approach and why it breaks.

The obvious fix is to tune the single model: add indexes for each query and a read replica for the read traffic. Indexes help reads but are maintained on every write, so writes slow down. A replica moves the load but keeps the same schema, so the awkward joins remain, now on another machine. And replicas lag, so the system already serves stale reads without having been designed for them. (A replica or a separate reporting database is still a sensible first step, and sometimes all you need.)

3 · The pattern

Its parts and the role of each.

Command Query Responsibility Segregation (CQRS) splits the model in two. The command side handles writes, expressed as business tasks (“place order”, not “set status”), and enforces the domain rules against a store shaped for transactions. The query side never changes data; it returns ready-made views (data transfer objects) shaped for each screen, with no domain logic. With separate stores, the write side publishes events when it changes, and projectors update one or more read models from them.

PartJob
Command handlerValidates a business task against the rules and changes state
Write storeNormalised, transactional; the source of truth (or an event log, with event sourcing)
Change feedEvents published when state changes, ideally via a transactional outbox
ProjectorsIdempotent consumers that turn events into read models
Read modelsMaterialised views in whatever store suits the query: search index, key-value store, reporting database
Query APIReads views directly; no joins, no domain logic

Microsoft describes two levels: separate models over a single data store, and separate models in different data stores, which can use different technologies (for example, relational for writes and a document database for reads) and scale independently.

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

With separate stores, read models are eventually consistent: both Microsoft and AWS say so plainly. The most visible symptom is read-your-own-writes: a user changes something and the next page does not show it. Common mitigations (general practice, not from a single source): return a version or position from the command and have the next query wait until the read model has reached it; have the client show the result of its own command; or route that user's reads to the write model for a short time after a write.

Other failure modes: the database commits but the event is never published (Microsoft recommends a transactional outbox to persist the state change and the event atomically); events are delivered more than once (make read-model consumers idempotent); a projector bug corrupts a view (be able to rebuild it, which event sourcing makes straightforward by replay); and users act on stale data (the command side must validate every command against current state).

Where it still goes wrong

  • Lost events: save state and event together (outbox)
  • Duplicate events: make projectors idempotent
  • A buggy projector: fix it, then rebuild the view
  • Commands from stale screens: validate on the write side

6 · Trade-offs

What it costs, when not to use it, and its main variants.

CQRS does not require event sourcing. Without it, the write side stores current state and publishes an event with each change. With it, the event store is the write model and the single source of truth, and read models can be rebuilt or newly created by replaying history; Greg Young describes the two as symbiotic. Microsoft warns that the combination adds significant complexity and that long event histories need snapshots.

When not to use it: Martin Fowler cautions that for most systems CQRS adds risky complexity, and that it should be applied to specific parts of a system (a bounded context), not the whole. Microsoft lists simple domains and simple CRUD interfaces as poor fits. AWS suggests it when read and write workloads have different scaling, latency or consistency needs and eventual consistency is acceptable for reads. A reporting database is the lighter step to try first.

With or without event sourcing

Without event sourcingWith event sourcing

When not to use it

  • Simple domain and rules: plain CRUD is enough
  • Across a whole system: keep it to one bounded context
  • When every read must be up to date
  • Before trying a reporting database

7 · In the wild

Real implementations and where our own systems use it.

The name builds on Bertrand Meyer's command-query separation, from Object-Oriented Software Construction: a method either changes state or returns a result, not both. Greg Young's CQRS documents say CQRS originated with that principle, and that the difference is that objects are split into two, one for commands and one for queries. Martin Fowler's 2011 bliki article says he first heard the pattern described by Greg Young. Microsoft's Azure Architecture Center and AWS Prescriptive Guidance both document it; the AWS example uses a DynamoDB stream that triggers a Lambda function to update an Aurora table. Axon Framework is an open-source (Apache 2.0) Java framework built around DDD, CQRS and event sourcing, with Axon Server as an optional event store and message router.

8 · Related patterns

What it is confused with or combined with.

Event sourcing is the most common partner, as the write store. A transactional outbox makes the change feed reliable. Projectors are idempotent consumers. Each read model is a materialised view. Sagas coordinate commands that span several services. A reporting database is the lighter alternative when only heavy queries are the problem.

9 · Recap

Three takeaways.

Give writes and reads their own models. Read models lag, so design for it, especially for users reading their own writes. Use CQRS sparingly, where the split earns its complexity.

Recap

  • Writes and reads want different models
  • Read models are copies, kept current by events
  • Design for stale reads, and use it sparingly
