Write-ahead log

Append every change to a sequential log and flush it before acknowledging the commit; update the data pages later, and replay the log after a crash.

1 · The problem

What goes wrong without it, shown happening.

A single transaction often changes several pages in the data files: table pages, index pages, sometimes pages for different rows. If the machine crashes after some of those writes reach disk and before the others do, the files hold a mixture of old and new state. A page write can even be interrupted partway, leaving a torn page that is part old and part new. With no record of what was in progress, the database can neither finish the change nor undo it.

2 · The naive fix

The obvious approach and why it breaks.

Forcing every changed page to disk before acknowledging a commit makes each commit wait for several flushes of pages scattered across the files, which is random I/O. Throughput is bounded by the device. It also does not solve the crash itself: a failure between two page writes still leaves the files inconsistent.

3 · The pattern

Its parts and the role of each.

PostgreSQL's documentation states the central rule: changes to data files must be written only after WAL records describing them have been flushed to permanent storage. Commit then needs only the log flushed, and because the log is written sequentially, that flush is much cheaper than flushing the data pages.

4 · How it works

The normal flow, step by step.

On commit the engine appends a commit record, flushes the log, and only then reports success. Dirty pages are written later. In PostgreSQL a checkpoint starts every checkpoint_timeout (default 5 minutes) or when max_wal_size (default 1 GB) is about to be exceeded; after it, segments before the redo record can be recycled or removed. With many small concurrent transactions, one fsync of the WAL can commit many of them (group commit); commit_delay lets the group-commit leader wait briefly so more commit records join the flush.

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

After a crash, PostgreSQL reads the latest checkpoint record to find the redo point and replays WAL from there: roll-forward recovery, or REDO. Because a page write can be torn by an operating-system crash, full_page_writes (on by default) logs the whole page on its first change after each checkpoint. InnoDB applies its redo log during start-up, before accepting connections, then rolls back uncommitted transactions in a background thread. ARIES formalised the general approach as analysis, redo and undo passes.

The log only helps if the flush is real. MySQL's manual cautions that some operating systems and disks report a flush that has not happened. PostgreSQL warns that fsync = off can cause unrecoverable corruption after a power failure. Replication slots prevent removal of WAL they still need even with no consumer connected, so an abandoned slot consumes storage until dropped.

Where it still goes wrong

  • Disks that report a flush that has not happened
  • fsync turned off: corruption after a power cut
  • An abandoned replication slot keeps old log forever
  • Long gaps between checkpoints mean slow recovery

6 · Trade-offs

What it costs, when not to use it, and its main variants.

Every change is written twice, and checkpoint frequency trades recovery time against I/O (including more full-page images). Databases expose dials that trade durability for latency:

SettingEffect
PostgreSQL synchronous_commit = offReturns before the flush; up to 3 × wal_writer_delay (default 200 ms) of commits can be lost; no inconsistency. Settable per transaction.
InnoDB innodb_flush_log_at_trx_commit = 1Default; flush at each commit; required for full ACID compliance
InnoDB = 0 or = 2Flush about once per second; up to about a second of transactions can be lost
PostgreSQL fsync = offRisks unrecoverable corruption; only if the database can be recreated from elsewhere
SQLite synchronous = NORMAL in WAL modeSkips the sync at commit; transactions may roll back after power loss

Costs and variants

  • Every change written twice: log, then data files
  • Frequent checkpoints: quick recovery, more I/O
  • Rare checkpoints: less I/O, longer recovery
  • Variants: redo, or redo then roll back

7 · In the wild

Real implementations and where our own systems use it.

ARIES (Mohan, Haderle, Lindsay, Pirahesh and Schwarz, ACM Transactions on Database Systems 17(1), 1992) is the classic write-ahead-logging recovery method. PostgreSQL's WAL, MySQL InnoDB's redo log (by default about 32 files under #innodb_redo, total sized by innodb_redo_log_capacity, default 100 MiB) and SQLite's WAL mode (since 3.7.0, 2010; readers do not block writers; auto-checkpoint at 1000 pages by default) all apply it. Kafka builds on an append-only log on the filesystem and relies on replication rather than an fsync per write; Raft is a consensus algorithm for managing a replicated log, persisting entries to stable storage before responding.

8 · Related patterns

What it is confused with or combined with.

The same log feeds other uses. PostgreSQL standbys receive WAL records streamed as they are generated and apply them continuously (read replicas). Archived WAL plus a base backup gives point-in-time recovery. Logical decoding extracts row-level changes from the WAL, which is how change data capture reads a database. Event sourcing makes an append-only log the system of record in the application, and the outbox pattern is commonly relayed by change data capture.

9 · Recap

Three takeaways.

Committed means the log record is flushed. Pages catch up later, and checkpoints bound recovery. Relaxing the flush trades recent commits for speed.

Recap

  • Committed means the log record is flushed
  • Pages catch up later; checkpoints bound recovery
  • Relaxing the flush trades recent commits for speed
