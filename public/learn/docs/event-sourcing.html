Event sourcing

Store every change as an immutable event, derive current state by replaying them, and keep the whole history as the source of truth.

1 · The problem

What goes wrong without it, shown happening.

Most systems store only current state and update it in place. A bank account row that says the balance is 70 cannot tell you that it got there by a deposit of 100 and a withdrawal of 30, in which order, or why. Every update throws the previous state, and the intent behind the change, away. When a customer or an auditor asks how the number came about, there is nothing to show them.

2 · The naive fix

The obvious approach and why it breaks.

The usual fix is an audit table written alongside the main table. Now there are two records of the truth, written separately: a crash between the two writes, a code path that forgets the audit insert, or a hand-run script against the main table all make them drift. Once the history no longer adds up to the balance, neither can be trusted. Microsoft's guidance names exactly this: CRUD systems lose history unless a separate auditing mechanism records every operation.

3 · The pattern

Its parts and the role of each.

Event sourcing makes the append-only sequence of events the system of record. Each entity (here, an account) has its own stream. Current state is derived by replaying the stream; any other representation is a cache or a projection that can be rebuilt.

PartJob
Event storeAppend-only streams, one per entity; read a stream, append with an expected version
AggregateRebuilt by replaying its events; enforces business rules and emits new events
Command handlerLoads the aggregate, runs the command, appends the resulting events
SnapshotsOptional cache of state every N events, to shorten replay
Projector and read modelsSubscribe to events and maintain query-friendly views; rebuildable from the stream

Events should record intent (FeeCharged 5, two seats reserved) rather than the resulting value (balance changed to 65). Replaying up to a point gives the state at that moment, which Fowler calls a temporal query.

4 · How it works

The normal flow, step by step.

A command loads the stream, replays it, checks the rule, and appends new events while stating the version it read. The store accepts the append only if the stream is still at that version. Projections pick up the new event asynchronously, so read models are eventually consistent. Long streams are loaded from the latest snapshot plus the events after it; Axon's documentation shows a snapshot trigger at 500 events. Snapshots are an optimisation: the stream remains the truth.

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

Concurrent writers. Two handlers that read the same version can both decide to act. Optimistic concurrency on the stream version rejects the second append; the handler re-reads and decides again. Rules that span several streams still need their own reconciliation.

Schema change. Stored events are never edited, so old shapes must still be readable. Options are tolerant deserialisation, explicit event versions, upcasters that convert old versions on read (Axon chains them one revision at a time), and, as a last resort, rewriting events in place.

Personal data. An immutable store conflicts with the right to erasure. Keep personal data outside the events and refer to it by id, or crypto-shred: encrypt it with a per-subject key and delete the key.

Side effects on replay. Fowler warns that replaying events that send messages to external systems will repeat those effects; wrap external systems in gateways that are disabled during replay. Consumers also see events at least once, so handlers must be idempotent.

6 · Trade-offs

What it costs, when not to use it, and its main variants.

You gain a complete audit trail, state at any past moment, new read models from old events and append-only writes without hot-row locks. You pay with immutable mistakes, replay and snapshot management, read models that lag, version conflicts to retry and no ad hoc SQL on current state. Microsoft advises against it for simple CRUD, prototypes and short-lived systems, views that must be consistent in real time, static reference data, and teams new to event-driven design, and suggests applying it selectively, for example to a payment ledger.

  • Prototypes and short-lived systems
  • Views that must be consistent in real time
  • Static reference data
  • Teams new to event-driven design

7 · In the wild

Real implementations and where our own systems use it.

Accounting ledgers are the oldest form of the idea: double-entry records survive from around 1300, and corrections are new entries rather than erasures. Martin Fowler described Event Sourcing in 2005 and cites accounts and version control as examples. Greg Young, from whom Fowler first heard CQRS, originally developed Event Store; it became EventStoreDB and was rebranded KurrentDB with release 25.0 in March 2025. Axon Framework configures aggregates as event-sourced by default. Microsoft's Azure Architecture Center documents it as a cloud design pattern, with CQRS and materialised views.

8 · Related patterns

What it is confused with or combined with.

CQRS is the usual partner: events on the write side, projections (materialised views) on the read side. Sagas coordinate multi-step work by reacting to events. The transactional outbox solves reliable publishing when current state remains the truth. Event notification uses events as messages, not as the record. Audit logs and change data capture keep history beside current state rather than instead of it. Microsoft also warns not to confuse an event store with a message broker such as Kafka, which typically lacks per-entity streams and optimistic concurrency.

9 · Recap

Three takeaways.

Store what happened and derive state from it. Append with an expected version. Plan for schema change, erasure and lagging read models before you start, and use it only where history matters.

Recap

  • Store what happened; derive state by replaying it
  • Append with an expected version to stop conflicting writes
  • Plan for schema change, erasure and lagging read models
