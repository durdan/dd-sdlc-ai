Feature flags

Ship code dark, switch features on at runtime for chosen users, and switch them off again without a deploy.

1 · The problem

What goes wrong without it, shown happening.

When deploying code and releasing a feature are the same event, every deploy is a release to every user at once. Teams respond by keeping unfinished work on long-lived branches, which makes merges large and risky. There is no way to try a change on staff or on a small share of users first, and the only way back from a bad release is to roll back the deploy: rebuild, retest and ship again while users see errors.

2 · The naive fix

The obvious approach and why it breaks.

A switch in a config file or an environment variable lets unfinished code merge early, which helps. But the value is usually read at startup, so changing it means a redeploy or a restart of every server. It is still all or nothing: there is no targeting, no percentage, and turning it off again takes as long as turning it on.

3 · The pattern

Its parts and the role of each.

Feature flags (also called feature toggles) separate deploying code from releasing a feature. New code is deployed dark, behind a flag check, and switched on at runtime. Pete Hodgson's article on martinfowler.com calls the component that decides the toggle router.

PartJob
Flag checkThe if in the code that picks the new or the old path
SDKEvaluates flags for a user or context, usually from rules cached in memory
Flag serviceStores flags, rules and targeting; pushes or serves changes to SDKs
ConsoleWhere people change rules, with an audit trail
Default valueWhat the code uses when no rule can be evaluated

Hodgson names four kinds of toggle, which differ in how long they live and how dynamic they are:

KindPurposeLifetime
Release toggleShip unfinished or held-back work as latent codeTransitional; usually a week or two
Experiment toggleA/B and multivariate tests; each user consistently in one cohortLong enough for significant results: hours to weeks
Ops toggleLet operators disable or degrade a feature quicklyMostly short; some kept as long-lived kill switches
Permissioning toggleFeatures for premium, beta or internal usersCan be years; evaluated per request

4 · How it works

The normal flow, step by step.

LaunchDarkly's server-side SDKs receive the complete rule set when they connect, evaluate flags in-process, and keep a streaming connection open for changes. Unleash's backend SDKs also evaluate locally from an in-memory cache, refreshing every 15 seconds by default. Client-side SDKs work differently: for security reasons they do not download the full rule set, and receive only the evaluated values for one user or context.

Percentage rollouts depend on stable bucketing. Unleash hashes the chosen context field (by default userId, then sessionId) together with a group id (by default the flag name) using MurmurHash to a number between 0 and 100; increasing the percentage keeps existing users in the rollout and adds new ones. LaunchDarkly hashes the context key and kind into 100,000 buckets and extends a variation's bucket range when its share grows. The bucket number in the walkthrough (37) is illustrative.

5 · When it goes wrong

Timeouts, partial failure, edge cases, and what the pattern does then.

Rollback becomes a switch: turn the flag off and users return to the old path on their next request, while the faulty code stays deployed but unused. If the flag service is unreachable, Unleash SDKs that have already initialised keep working on cached data and simply stop receiving updates; an SDK with no data evaluates flags as disabled or as the default supplied in code. LaunchDarkly SDKs likewise return the fallback value from the code when they have nothing else. OpenFeature's specification requires that evaluation never throws and returns the caller's default value on abnormal execution. So defaults should be the safe choice, usually off.

6 · Trade-offs

What it costs, when not to use it, and its main variants.

Hodgson treats toggles as inventory with a carrying cost. Suggested practices: add a removal task when a release toggle is created, set expiry dates, use "time bombs" that fail a test after expiry, and cap the number of active flags. Testing every combination is unnecessary: test the configuration expected in production, the intended release configuration, and the fallback with new toggles off (some teams also test all on). He also warns that per-request overrides via cookies, query parameters or headers increase attack surface. Our guidance (not from a single source): anything a client can read or change is not a security control, so enforce permissions on the server and do not rely on a client-side flag to hide security-sensitive code. Flags also cannot roll back data changes such as schema migrations.

What flags cost

CostWhat to do about it
Flag debt: dead branches pile upOwner, expiry date, removal ticket on day one
Many combinations to testTest production config, release config, and all new flags off
Client-side flags can be read and changedEnforce access on the server, not by hiding
Another system on the request pathLocal evaluation, cached rules, safe defaults

When not to use one

  • A one-line change that is easy to roll back
  • Database migrations: plan expand and contract instead
  • As a permanent if-else nobody owns
  • To hide unfinished security code from attackers

7 · In the wild

Real implementations and where our own systems use it.

Facebook's 2015 paper Holistic Configuration Management at Facebook describes Gatekeeper: code is released early in a disabled mode, then enabled in phases (the engineers building it, employees, a region, everyone) by live config changes, using restraints such as country, locale and device plus a sampling percentage, and can be disabled immediately if problems appear. OpenFeature, a CNCF incubating project, is an open specification for a vendor-agnostic flag evaluation API, with providers as the translation layer to a flag system; LaunchDarkly and Flagsmith both document OpenFeature providers. Unleash is open source under AGPL-3.0; most of Flagsmith is open source under BSD-3-Clause; LaunchDarkly is a commercial service.

8 · Related patterns

What it is confused with or combined with.

Trunk-based development relies on release toggles to merge unfinished work daily. Canary releases send a new version to some servers; flags send a feature to some users, and the two combine. Experiment toggles power A/B testing. Kill switches are a form of graceful degradation. A strangler fig migration can route traffic to the new system by flag, and server-driven UI often uses flag values to choose what each client shows.

9 · Recap

Three takeaways.

Deploy is not release. Roll out by a stable percentage; roll back with a switch. Flags are debt: safe defaults, owners, expiry dates, and delete them when done.

Recap

  • Deploy is not release: ship dark, turn on at runtime
  • Roll out by stable percentage; roll back with a switch
  • Safe defaults, owners and expiry: flags are debt
