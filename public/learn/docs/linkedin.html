LinkedIn: where Kafka came from

Why LinkedIn built Kafka: one shared, ordered log that every system writes to once, feeding search, the social graph, the feed, analytics and caches.

1 · Overview

What it is, who uses it, and the one idea everything depends on.

LinkedIn is a professional network: members build profiles, connect, post, search and apply for jobs, and paying customers such as recruiters and advertisers reach them. Its pressroom (checked October 2026) gives a community of more than 1.3 billion members.

This case study is about a system members never see. In his December 2013 essay The Log, Jay Kreps describes how LinkedIn moved from a monolithic, centralised database to many specialised systems (search, social graph, Voldemort, Espresso, Hadoop and more), and found that connecting each source to each destination would need on the order of N² pipelines. The answer was one central log: an append-only, totally ordered sequence of records that every system writes to once and every other system reads at its own pace. Kafka was built at LinkedIn to be that log, first for activity data, and was open sourced.

The one idea: a log in the middle

2 · Requirements and scale

What users need, the quality targets, and back-of-envelope numbers.

Scale, from LinkedIn's own posts. In October 2019 LinkedIn wrote that its Kafka deployments handled more than 7 trillion messages a day across more than 100 clusters, 4,000+ brokers, 100,000+ topics and about 7 million partitions. In September 2015 it reported more than a trillion messages a day, peaks of 4.5 million a second, and about four consuming applications per message.

Back of the envelope: 7 trillion ÷ 86,400 seconds ≈ 81 million messages a second on average (our arithmetic; peaks are higher).

The functional requirements in the video are ours, derived from what LinkedIn describes: every event and database change lands once in one place; readers join without changing writers; profile edits reach search and caches within seconds; a slow reader never holds back others; any index can be rebuilt by replay; feed reads stay fast for members who follow thousands.

3 · Context

Who and what the system talks to (C4 level 1).

Simplified. Members use the web and mobile apps; paying customers post jobs, run campaigns and search for people; LinkedIn sends emails and push notifications through delivery services. Internal analysts and machine-learning teams are users too: they need every event. That internal need, a central pipeline for activity data, is what Kafka was first built for (The Log).

5 · Deep dive

Inside the most interesting component (C4 level 3).

Inside the log. The drawing is our sketch; the mechanisms come from The Log and LinkedIn's Kafka posts.

  • Partitions. A log is chopped into partitions, each totally ordered. Writers may partition by a key such as user id. Appends need no coordination between partitions, so throughput scales with the cluster. Ordering is guaranteed per partition, for appends from one sender.
  • Replication. Each partition has a configurable number of replicas; one is leader, and a follower takes over if it fails.
  • Efficiency. Batching at every step, and one binary format in memory, on disk and on the network, allowing zero-copy transfer.
  • Retention. Event data is kept for a window, usually a few days, by time or size. Keyed data is compacted: records whose key has a newer value are removed, so the log still holds a complete copy of the latest state and can rebuild a store by replay.
  • Readers. Each subscriber reads at its own rate and tracks its own position; Hadoop may load hourly or daily while a real-time system stays seconds behind. Pull-based reading keeps one faulty job from back-pressuring the whole flow. LinkedIn's SREs built Burrow to monitor consumer lag (2015).
  • Mirroring. In 2013 LinkedIn ran over 60 billion unique message writes a day, and several hundred billion counting mirroring between data centres.

6 · Core flows

Two or three requests that matter, step by step.

A profile edit fans out. The profile service writes the document to Espresso over Rest.li. Espresso storage nodes update secondary indexes synchronously with the base data, so an immediate query is not stale. Within a cluster, replication uses MySQL's binary log, which also feeds Databus; each partition carries a system change number (SCN) giving a timeline-consistent order. Databus delivers committed changes in commit order to subscribers such as search indexes, caches and read replicas. A new or far-behind reader starts from the bootstrap service's snapshot, then catches up from the relay. The final step, the new headline showing in search, is eventual; we do not have a published latency figure.

A post reaches a feed (FollowFeed, March 2016). Activities flow asynchronously through Kafka. A partitioner republishes them to a topic partitioned like the index, over-partitioned into 720 partitions (720 divides evenly into many cluster sizes). Timelines are stored in RocksDB. FollowFeed uses fan-out on read: pre-materialising every viewer's feed made the data about 62× larger and slowed relevance experiments. On read, a broker maps the viewer's followed entities to timeline keys, fans out to index nodes, which filter and score records where they live, then merges, de-duplicates, applies diversity and returns the feed. To cut tail latency it sends duplicate requests to replicas and keeps the first answer. Against Sensei, the older system: ~5× lower p99 latency, a ~20× larger index, about half the servers.

10 · Patterns used

The named patterns, each linked to its pattern walkthrough.

  • Event streaming and publish-subscribe: Kafka, with many independent readers.
  • Change data capture: Databus, then Brooklin, reading committed changes from the database.
  • Write-ahead log: the log as the source every view is built from.
  • Sharding: Kafka partitions; 720 FollowFeed partitions.
  • CQRS (our framing): writes to Espresso, reads from derived views.

12 · What we would build first

An MVP cut and our recommendations.

Our recommendations for a smaller system, not LinkedIn's:

  • Postgres as the single source of truth.
  • A managed Kafka, or a similar log, from the first month for activity events.
  • Change data capture from the database's write-ahead log rather than dual writes.
  • Search, caches and analytics built only as consumers, so they can be rebuilt by replay.
  • Topics keyed by member id; compacted topics for state.
  • Consumer lag on the dashboard from day one; build feeds on read until scale says otherwise.

What we would build first

  • Postgres as the one source of truth
  • A managed Kafka, or similar, for activity events from month one
  • Change data capture from the database log, not dual writes
  • Search, caches, analytics as consumers that can be replayed
  • Topics keyed by member id; compacted topics for state
  • Consumer lag on the dashboard from day one; feeds built on read
